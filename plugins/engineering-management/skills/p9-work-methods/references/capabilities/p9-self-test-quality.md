# 自测用例设计与灰犀牛治理

## R（原文摘引）

> "这种方法基于用户场景列举的完备性来证明代码逻辑的完备性。事实上，与证明逻辑的完备性相比，列举用户使用场景更容易实现。"（4.1.2 用户场景穷举不重不漏）

> "一旦核心逻辑发生不符合预期的修改，都应该立即告警。代码自测用例可以被视为最佳的警报器。在许多重构过程中，首先完善测试用例也是基于这个原因。"（4.1.3 自测用例护航关键设计）

> "这种类型的自测用例比没有编写自测用例的危害更大。因为它会让所有人误以为它是可靠的，从而将信任寄托于它，但实际上它却并不值得信任。"（4.2.1 掩耳盗铃式自测无效果）

> "本质上，自测用例的维护是一个熵增的过程。如果不加以控制，它会逐渐陷入无序状态……解决这个问题的唯一方法就是注入外部力量。"（4.2.2 让伤害来得更猛烈些）

> "对外部服务的依赖应一律进行模拟（mock），没有任何例外，以避免'破窗效应'。"（4.2.2 确保用例的独立性）

## I（解释）

这张卡回答两个问题：研发怎么靠自测把住源头质量，以及自测用例自己怎么不烂掉。

**源头质量的理由**：缺陷发现越晚成本越高（自测改一下就完 → 测试阶段多角色往返 → 生产阶段加故障报告与复盘），而且概率性缺陷（特定条件死循环）和命名/注释类规范问题几乎只能在编码阶段被发现——质量是研发的责任，不是测试的责任。

**自测设计三条路**：①用户故事验证——以用户场景穷举（思维导图、不重不漏）间接证明逻辑完备，再做多功能组合的闭环流程自测（支付→退款及其全部异常分支），最后站在用户可感知角度穷举异常（重复提交/幂等，守"宁愿不做，不错做"）；②护航关键设计——把团队共识的关键业务规则写成断言用例（退款三断言），非功能设计按性能/容量/稳定性三视角固化（如并发幂等用例），关键数据字段必须断言（时区/夏令时双向）；③治理——用例维护是熵增过程，必须注入外部力量：全天候高频运行（目标 10 次过 9 次）、独立性三措施（内存库/mock 一律无例外/测试基类统一清理）、用覆盖率（行+分支）与断言质量（三类输出）度量删用例。自测代码本身按生产代码标准设计。

## A2（情境应用）

**触发场景**：
- 功能开发完成、提测/提交评审之前，要设计一轮自测用例；
- 重构开始前，要先补测试保护关键设计与架构共识；
- 团队 CI 里自测用例越积越多、偶发失败靠重跑、全量跑一次几十分钟，效能被拖垮；
- 接手遗留系统，旧用例测试意图成谜，不敢删也不知道护着什么；
- 写完的用例只断言返回码，被质疑"这用例到底测了什么"。

**语言信号**：
- 中文：自测、自测用例怎么写、提测前检查、用户场景穷举、闭环测试、幂等怎么自测、用例不稳定、用例越滚越多、删用例、覆盖率、断言
- 英文：self-test, unit test, test case design, user scenario, flaky test, test maintenance, coverage, assertion, mock, CI

**与相邻能力的区分**（初稿）：
- 与 p9-clean-code：那卡管代码怎么写（结构/命名/重构底线）；本卡管写完的代码怎么被验证与被保护。
- 与 p9-idempotency-errorcode：幂等的分布式原理（原子性/传递性/三维审查）与失效排障归那卡；本卡的并发幂等自测（10 线程断言 1 笔）是它的验证手段，两卡可配合使用。
- 与 p9-system-analysis：系分把逻辑推导显性化以达成共识，自测用例把关键设计固化成警报器——同为"共识固化物"，前者在事前，后者在事后守护。
- 与专职测试层（六层质量网中的接口契约场景/平台集成/全链路/UAT/A/B）：本卡只覆盖研发自测源头层，不替代其他层职责。

## E（可执行步骤）

1. **用户场景穷举**：从用户视角列举该功能全部使用场景，用思维导图按维度展开（如支付工具 × 成功/失败），做到不重不漏。完成标准：每个场景可指认其维度路径且互不重叠；无法归入任何维度的场景单独列出并与用户确认归属。
2. **闭环流程自测**：把多个功能组合成真实用户链路（如支付成功后的退款），逐条展开正常与异常分支（原路退款/退余额/多次退款超额/退款失败回退/拒付与退款并发）。完成标准：每条主流程都有对应的异常分支清单；组合场景至少覆盖一条跨功能链路。
3. **用户可感知异常验证**：对系统无法处理的行为穷举异常场景（典型为重复提交、重复支付），验证系统明确拒绝且不产生副作用（"宁愿不做，不错做"）。完成标准：每个异常场景有"拒绝 + 无副作用"断言。
4. **护航关键设计**：①关键业务规则写成保障用例（如退款三断言：单据存在、状态成功、退款额<支付额）；②非功能设计按性能/容量/稳定性三视角归类固化（如并发幂等用例：线程池提交同一笔请求 N 次，断言成功单据=1）；③关键数据字段断言（时区/夏令时跳变双向用例）。完成标准：关键设计清单逐条有用例映射，映射表可直接作为评审材料；任何核心逻辑被误改即有用例变红。
5. **灰犀牛治理**：①全天候不间断运行，失败立即修复而非重跑了事，设定务实通过率目标（如 10 次过 9 次）并优化执行时长；②独立性三措施——内存数据库替代公共研发库、外部服务依赖一律 mock 无例外、统一测试基类在 setUp 等模板方法中清理全部 Mock 变量；③建度量体系删用例——逻辑覆盖看行覆盖率+分支覆盖率，校验点断言质量须覆盖三类输出（落库/缓存数据、广播给外部系统的数据、返回给调用方的结果）。完成标准：通过率达标且全量执行时长有基线记录；没有任何用例依赖 Thread.sleep 等预估等待；每个在库用例能一句话说清护什么；三类输出断言齐全。

**输入契约**：必需 = 功能代码 + 用户场景描述（谁、在什么情况下、做什么）+ 关键设计清单（关键业务规则 / 非功能需求 / 关键数据字段）。关键设计清单缺失时，先与需求方/架构对齐再写保障用例，不为"凑用例数"虚构关键设计；治理场景另需 = 现有用例集 + CI 运行记录。
**输出契约**：用户场景思维导图（维度+场景叶节点）；自测用例集（用例名对应场景/设计条目）；关键设计→保障用例映射表；治理报告（通过率实测、全量执行时长、行/分支覆盖率、三类输出断言覆盖清单、建议删除/整改的用例名单及依据）。
**判停点**：步骤 1 场景维度爆炸不收敛 → 停下与用户收窄本次自测范围（先测核心路径）；步骤 5 通过率长期低于目标且根治无进展 → 大概率独立性未达标，回到②逐项排查外部依赖（公共库/真实服务/Mock 污染）；覆盖率目标阈值原书未给数值（p068 登记为缺口）——须与团队显式约定并标注"约定值"，不得冒充原书标准。

## B（边界）

**反场景（何时不用）**：
- 专职测试层职责不在此卡：接口契约场景测试、平台功能集成、全链路、UAT、A/B 属六层质量网的其余层，各有责任人；研发自测是源头层，不越层替代；
- 概念验证/一次性脚本：投入自测资产的回报期不存在；
- 追求 100% 通过率作为目标本身：原书明确"追求 100% 通过率并非总是必要"，目标是可持续的务实通过率（如 90%）。

**书中警告的失败模式**：
- ce035 只敢加不敢减：旧用例不出错就不改、不能证明无用就不删，交接后意图成谜，资产膨胀成负债（治理出口：度量删用例）；
- ce036 十次运行只一次过：不稳定用例靠重跑苟且，"再跑一次就绿了"成为口头禅，失败信号失去可信度，真回归被淹没（治理出口：独立性三措施）；
- ce037 异步用例靠 sleep 等待：等待时间是对"何时完成"的猜测，用例增多后总时长失控且加剧不稳定，成为效能最大卡点（治理出口：自测代码也要设计）；
- ce038 掩耳盗铃式自测：意图与实现不一致（要测契约逻辑关联只测了必填与长度）、校验不完整（只断言返回码不查关键字段与落库）——比没有用例危害更大，制造虚假质量信心；
- ce039 "自测代码不需要设计"：以不跑生产为由放低标准，用例无法复用、无人认领维护，最终丧失检出能力。

**作者盲点/时代局限**：
- "宁愿不做，不错做"与穷举式验证是资金/支付系统的价值观，体验型产品（快速失败重试无资损）未必照搬；
- 六层质量网、全天候 CI、内存库、统一测试基类假设大厂基建与专职测试组织，小团队需按层降配（至少保住 mock 一律无例外与测试基类清理）；
- 覆盖率只给了指标名（行/分支），未给目标阈值与三类输出断言的计数口径（阶段 1.5 已登记 needs-review），执行时必须显式约定；
- 全天候运行的成本（机器资源、维护投入）与团队规模的关系未讨论，小团队可退化为"每次提交必跑+每日定时全量"的降配形态。
