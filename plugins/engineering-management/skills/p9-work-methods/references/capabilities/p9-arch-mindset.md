# 架构师三心魔自检

## R（原文摘引）

> "架构师不应以责任感去对抗不完美，否则只会带来无尽的挫败和痛苦；架构师必须摒弃完美主义，否则只能是哑巴吃黄连，有苦说不出。"（第7章 7.1.1）

> "确定性不等同于完美，仅仅意味着业务能够清晰地看到和感受到架构所能提供的支持。"（第7章 7.1.3）

> "技术风险的本质是一个概率问题。即使硬件出错的概率很低……但随着硬件运行次数和代码逻辑变更次数的增加，出错的概率会逐渐增加，最终趋近于 1。"（第7章 7.2.2）

> "资金风险 = 支付机构系统的账本金额 – 银行实际账户余额。"（第7章 7.2.3）

> "一次故障如果能真正改进一个关键点就已经非常不错了，这意味着需要从技术逻辑上彻底修复漏洞，而不是仅仅依靠流程机制。"（第7章 7.2.4）

> "首先，架构回答不了唯心的问题。……其次，架构回答不了决策性问题。……最后，架构回答不了生产关系问题。"（第7章 7.3.1）

> "如果商业被架构所限制，导致这也不行那也不行，那将是一场灾难，也是架构的失职。"（第7章 7.3.3）

> "技术架构的不变内核应该是客观推理过程、取舍平衡和风险管控。"（第7章 7.3.3）

## I（解释）

架构师先过心态关，再谈方法。三种心魔是对复杂性的系统性认知偏差，各有一套可执行的解药：

**完美主义**（妄想架构全知全能）：世界 VUCA、约束相互制约，完美架构不存在，用责任感对抗不完美只会无尽挫败。解药不是更努力，而是**给业务确定性**：可感知的指标（像体温计一样有数值）、决策树式的简洁 SLA（每个叶子节点一个明确承诺）、紧贴当下的意外（基于资源给出"50 个渠道 3 个人一个月"式承诺）。药效要恰如其分：看三年做一年、架构略大于团队能力（小马拉大车）、经营性思维（算投入产出比）。最后用价值两问验收——因你而不同（业务价值）、因你而更好（可维护/可控风险/降本/可传承）。

**风险主义**（零容忍与风险大棒）：风险是概率，随运行与变更次数累积趋近 1，"零故障"是空中楼阁，零容忍催生"多做多错、不做不错"。解药是概率观加三层底线：尊重规律不设零故障 KPI；从业务原理找恒等式纳入系统实时巡检（资金风险=账本金额−银行余额，非 0 即异常）；按投入产出比只防关键风险（低级/重复性错误、重大但可逆的故障）。避免最坏用"大事化小、小事化了"：事前等份划分（灰度/分库分表/负载均衡）压缩影响面，复盘从技术逻辑彻底根治一个关键点而非列流程清单。同时以先进性（体验数字、代际差异）对抗因惧风险不敢创新。

**单一主义**（架构先进=商业成功）：架构是商业成功的必要而不充分条件。架构答不了三类问题——唯心问题、决策性问题（交业务/管理层）、生产关系问题（交组织设计）。解药是给业务**选择权**：围绕不变的业务实质而非易变目标设计（行星绕太阳）；守住技术恒定底色（成本/效能/风险优势，而非快速上线）；保留解题方法丰富性（不变内核是推理、取舍、风控，不是分层解耦等套路）。配以前瞻双视角：向前展望向后倒推 + 面向过去不断沉淀。

## A1（原书案例 / 合成演练）

**原书案例一：渠道接入 SLA 的决策树与"50 渠道 3 人一月"（worked_example，第7章 7.1.3）**。输入：业务询问接入一个新支付渠道需要多久。执行：直白回答"钱包渠道接入需要 10 个工作日，不包括新接银行、报送监管、外汇兑换等流程"——信息有但条件太多仍令人困惑；按确定性方法重构为简单决策树，每个叶子节点对应一个明确 SLA；面对"50 个渠道要多久"，不做单渠道时长 × 50 的机械推算，而给出"给我 3 个人和一个月，我们可以完成"的资源承诺。结论：确定性让业务可感知、可决策（原书未交代业务方反馈，为话术推演）。

**原书案例二：复盘会上的"抓与帮"（firsthand，第7章 7.2.1）**。输入：作者亲历的项目复盘会，研发、测试、产品、业务、合规、财务互相推诿指责。执行：业务主管说"你们不应该像警察一样来'抓'我，而应该像战友一样来'帮'我。请告诉我做哪些事情、做到什么程度，业务才能成功上线"；全场安静后转向从各自角度提建议，明确达标要求。结论：业务成功上线——风险主义（只抓问题不给出路）被"帮"的态度取代。

**原书案例三：资金风险恒等式（worked_example，第7章 7.2.3）**。输入：客户充值 100 元的第三方支付资金管理。执行：推导"支付机构欠客户 100 元、银行账户增加 100 元"，得恒等式"资金风险 = 账本金额 − 银行实际余额"，此时 100 − 100 = 0；将其纳入系统架构做随时或实时巡检。结论：某日计算结果不为 0 即表明资金管理异常、已对实际业务产生影响——从业务原理层面做风险控制（巡检频率口径原书未给出）。

**原书案例四：唯一索引空值误判幂等的"小事化了"（worked_example，第7章 7.2.4）**。输入：给非空字段传空值触发 DataIntegrityViolationException，被误判为幂等性错误引发生产故障。执行：正确动作不是"操作数据库都要加人工评审"，而是通盘扫描代码是否存在同类异常、把防错规则纳入代码审查流程、甚至作为 Git 提交前置检查。结论：用代码逻辑与架构设计自动检测预防，根除低级与重复性错误（方案演示，结果未说明）。

**原书案例五：支付成功率 70% 被批评与快捷支付（reported_case，第7章 7.3.5）**。输入：支付宝 2010 年因支付成功率低于 70% 受到批评。执行：洞察支付渠道业务的本质是支付成功率（成功率高则商家 GMV 损失少），同年推出快捷支付，并以智能路由在多渠道中选最优路由提升成功率与稳定性。结论：支付成功率提升至 95%（公开资料）——围绕不变的业务实质做架构，为业务创造发展空间。

## A2（情境应用）

**触发场景**：
- 架构方案设计/评审/年度规划启动前，需要做一轮心态与边界自检，防止方法被心态偏差抵消；
- 被业务质疑"架构怎么又出问题"、或发现自己"不是在解释，就是在去解释的路上"；
- 组织在制定故障/风险 KPI，出现"零故障""零风险"字样并压给一线；
- 需要向业务给出 SLA、排期或风险承诺，纠结怎么说得既确定又不夸口；
- 复盘会气氛变成推诿指责（"抓"），或商业成败归因争论（技术背锅/技术甩锅）。

**语言信号**：
- 中文：完美主义、过度设计、零故障、零风险、绝对安全、风险大棒、多做多错不做不错、这也不行那也不行、架构能解决吗、商业成功归因、技术价值、选择权、全知全能
- 英文：perfectionism, over-engineering, zero-downtime, zero-failure KPI, risk aversion, risk of risk, blameless postmortem, necessary but not sufficient, optionality, architecture mindset

**与相邻能力的区分**（初稿）：
- 与 p9-arch-modeling（第8章三式）：本卡管"动笔之前的心理预设与解题边界"，三式管"具体课题的求解操作序列"；自检通过后再进入三式，顺序不可倒。
- 与 p9-arch-stability（第8章 8.4–8.6）：那是在概率观之上展开的具体风险架构设计（E(X) 公式、四大设计、资防四式、变更三板斧）；本卡只提供风险的概率观、底线原则与自检问句，不展开设计。
- 与 p9-arch-evolution（第9章）：演进的极致目标、业务价值论证、决策过程正义是本卡心态落地后的持续经营过程。
- 与 p9-clean-code / p9-domain-modeling：代码质量与领域建模层的问题不触发本卡。

## E（可执行步骤）

本卡是自检卡：输出是自检报告与解药动作清单，不是架构方案本身。

0. **场景确认**：确认对象是架构层面的方案/规划/复盘/承诺（而非纯编码、纯人事议题）。完成标准：能一句话说清自检对象。
1. **完美主义自检（4 问，任答"是"即中魔）**：①是否有人（含你自己）期望这套架构解决过去、现在和未来的所有问题？②是否正在为"可能永远不来的业务量"做设计？③回答业务询问时是否总带一堆前提条件（"不包括……需具体分析"）？④是否觉得"不解释清楚所有不足就没法交代"？
   **解药——确定性三件事**：(a) 提供外部可感知的指标（给风险/状态一个业务能读的数值，如"敞口"）；(b) 把含条件回答重构为简单决策树，每个叶子节点对应一个明确 SLA；(c) 制造紧贴当下的意外——基于团队与资源给具体承诺（"50 个渠道，3 个人一个月"），不机械乘法。
   **验收——恰如其分三问**：看三年做一年（以三年为窗预估扩展/复用/安全/先进性并划里程碑）？架构是否略大于团队能力（小马拉大车，不过大不过小）？每项投入算过投入产出比、有没有更便宜的实现（经营性思维）？
   **终检——价值两问**：因你而不同（创造了离开你就不存在的业务价值）？因你而更好（可维护性/风险可控/成本降低/可传承持续优化）？
   完成标准：三件事各有具体产出（一个指标数值、一棵决策树、一句资源承诺）；价值两问各能举一例。
2. **风险主义自检（4 问）**：①组织是否在追求绝对安全/零故障 KPI 并压给一线？②复盘会上你在"抓"（找问题追责）还是在"帮"（回答"做到什么程度可上线"）？③是否出现"多做多错、少做少错、不做不错"的动作变形？④是否因怕风险不敢创新，架构只在故障时被感知？
   **解药——三层底线**：(a) 尊重规律：接受出错概率趋近 1，把零故障目标改写为可落地目标；(b) 符合业务原理：为本领域找一个恒等式纳入系统实时巡检（资金风险 = 账本金额 − 银行余额，正常为 0，非 0 即异常）；(c) 防范关键风险：按投入产出比优先防低级/重复性错误与"重大影响但可逆"的故障，不为小概率事件不计成本。
   **避免最坏——大事化小、小事化了**：事前用等份划分（A/B、灰度、分库分表、负载均衡）把单份故障影响压到 1/N；复盘只从技术逻辑彻底修复一个关键点（通盘扫描同类问题、纳入代码审查或 Git 提交前置检查），不列大多完不成的流程清单。
   **先进性自检**：说得出去年与今年架构的质的差别吗？能用极致体验数字（如 310 模式：3 分钟申请/1 秒放款/0 人工）或代际差异（每代至少 10 倍收益、3–5 年一次升级）表达吗？
   完成标准：产出一个恒等式或一个等份划分设计；复盘改进项中技术根治项 ≥ 1 且流程类不占多数。
3. **单一主义自检（4 问）**：①是否认为架构先进商业就必然成功（或商业失败全赖技术）？②是否在围绕易变的业务目标（而非不变的业务实质）做抽象？③是否把特定套路（分层/解耦/微服务）当成不变内核？④是否正让架构回答它答不了的问题？
   **解药——三类答不了的问题（逐一转交）**：唯心问题（"完全无 Bug、支持所有需求"→ 向需求方声明不可能）；决策性问题（投不投资、上不上线 → 交业务/管理层，技术只做方案比较）；生产关系问题（功能归属、组织边界 → 交组织设计，逻辑最优解 ≠ 组织可行解）。
   **选择权三角**：业务目标的可变性——围绕不变的业务实质设计（如"高频打低频"），业务目标怎么变都能支撑；技术贡献的持续性——守住成本/效能/风险优势的恒定底色，不把"快速上线"当全部价值；解题方法的丰富性——不变内核是客观推理、取舍平衡、风险管控。
   **前瞻双视角**：向前展望、向后倒推（定终局目标再倒推各阶段目标与措施）+ 面向过去、不断沉淀（历史问题 → 技术复用/技术创新降本/自动化风控三类能力）；阶段分工：短期控风险、中期提效能、长期建地基。
   完成标准：每个越界议题已标类别并指定转交对象；架构描述能指出一个"不变业务实质"；能说出至少两种候选解法。
4. **输出自检报告**：命中的心魔、证据（答"是"的问句）、对应解药动作清单、遗留越界问题及转交对象。完成标准：未参与的同事读后能复述"中的哪个心魔、做什么、不做什么"。

**输入契约**：必需 = 待自检的架构方案/规划/复盘材料，或一个决策情境描述。可选 = 业务方核心诉求、团队规模与能力画像、历史故障清单、业务目标与业务实质的区分线索。缺业务信息时向用户索要，不默认替用户判定"业务实质"。

**输出契约**：三心魔自检表（每心魔：问句命中情况、证据、解药动作）；确定性三件套（指标名 + 数值口径、SLA 决策树、资源承诺句）；风险底线清单（恒等式或等份划分设计、关键风险 Top N 及投入产出判断）；越界问题转交清单（问题 → 类别 → 应交对象）。

**判停点**：自检对象不是架构层议题（纯编码/纯人事）→ 停止，改用对应能力；材料不足以判断业务实质 → 先向用户索要业务输入，勿凭技术想象填充；三心魔均未命中 → 直接进入方法层（arch-modeling / arch-stability），不强行开药。

## B（边界）

**反场景（何时不用）**：
- 代码质量与坏习惯问题 → p9-clean-code；具体领域建模操作 → p9-domain-modeling；
- 高可用/资损/变更管控的具体架构设计 → p9-arch-stability（本卡只给概率观与底线原则）；
- 非技术决策场景（纯管理、纯商务）→ 架构三问不适用；
- 用户只要一个具体技术答案、不涉及取舍与承诺时，先做自检是过度流程。

**书中警告的失败模式**：
- ce115 完美主义——期望架构全知全能：业务把业务问题归咎架构并追责，技术盲目投入、抱怨他人缺乏远见，最终沮丧自责；
- ce116 时间维度失衡——只面向未来导致过度设计，只面向过去导致无效架构；
- ce117 小马拉大车走极端——单机经验团队硬上分布式带来巨大维护风险，或架构过小团队缺乏挑战；
- ce118 无经营思维——为展示技术实力投入大规模架构，不问适配性与更便宜的实现；
- ce119 风险大棒——只强调风险不给解决方案，利用风险阻碍项目（"骂者众，献策者寡，行动者无几"）；
- ce120 零容忍文化——技术人紧绷变形为"多做多错、少做少错、不做不错"；
- ce121 零故障 KPI——空中楼阁式目标强加一线，催生数字游戏与瞒报；
- ce122 用流程改进代替技术根治——复盘清单全是"加强评审"，同类低级错误重复发生；
- ce123 因惧风险不敢创新——架构只在故障时被感知，形成"无事故=无存在感"的贬值循环；
- ce124 单一主义归因错误——商业失利结论只有"技术不行"或"与技术无关"两种；
- ce125 让架构回答生产关系问题——边界之争长期悬而未决，架构评审演变为地盘之争；
- ce126 围绕易变业务目标建模——每次业务目标调整都触发大规模架构改造；
- ce127 技术贡献=快速上线的生存危机——团队述职只能罗列项目清单，被视为可替换劳动力；
- ce128 把方法套路当不变内核——所有方案评审结论都指向同一套熟悉手法，对新问题缺乏第二解法；
- ce129 只有理想主义终局思维——规划全部基于未来假设、无历史数据支撑与能力沉淀。

**作者盲点/边界**：
