# 系统分析文档标准范式

## R（原文摘引）

> "系分是对用户需求实现方式的分析设计文档，是对抽象逻辑思考进行结构化梳理和产出的具象化承载物。"（第2章 开篇）

> "系分的目的不仅是让自己想清楚，更重要的是让项目中的各角色建立共识。"（第2章 2.1.2）

> "最基本的分析逻辑结构包括：达成什么样的目标、达成目标的关键因素是什么、有哪些可选方案、基于什么逻辑选择方案、如何控制风险、如何验证方案的正确性。"（第2章 2.1.3）

> "基于系分在项目中的灵魂地位，我们将好系分总结为四个关键维度：上承需求、下启代码、守住底线和精益求精。"（第2章 2.2）

> "'一句话价值'的表述格式为：'通过建设××系统能力，实现××技术指标，达成××业务效果。'"（第2章 2.2.1）

> "单个任务的工作量最好控制在 3 人日以下，如果超过 3 人日，则需要进一步拆分任务，以防估算不准确导致实际投入与预期投入出现较大偏差。"（第2章 2.2.4）

## I（解释）

系分不是"写文档的流程任务"，它做两件事：把脑内的逻辑推导逼到纸面上（大脑推演有惯性、会跳步；写不明白恰恰说明没想明白——小黄鸭效应），再把产品、研发、测试、项目经理、后续维护者五类角色拉到同一份文档前达成共识。系分工作量是常量，区别只在项目前期主动投入，还是故障后加倍被动偿还（"快就是慢，多就是少"）。

成文的标准范式是四维度：**上承需求**——用自己的话重述需求并请产品二次确认，用"一句话价值"（系统能力+技术指标+业务效果）定义目标，用用户故事梳理业务流程且图文互校；**下启代码**——用功能职责（"应该谁做"而非"谁可以做"）定系统边界，用决策思维写功能设计（列方案、比优劣、记条件/理由/结论），用用户视角挖耗时/安全/可用性等隐性非功能需求；**守住底线**——用思维导图按 正常/异常 × 历史/新增单据 × 新老链路兼容 × 成功/失败/未知三态 穷举测试场景，对每个设计点问"最坏的影响是什么、怎么办"倒推兜底；**精益求精**——修订记录置顶、工作量表格化且单任务不超过 3 人日。

每个分析章节都要有自洽论述骨架：目标→关键因素→可选方案→选择逻辑→风险控制→正确性验证——只罗列改造点、贴代码截图的系分既让自己误判周全，也让他人无法评估。收口靠评审五环节：明确目标清单→先讲全局→厘清架构边界→领域细节会后谈→变更记录修订回文档。

## A1（原书案例 / 合成演练）

**案例一：多专家共创"价值数十万"的系分范式（firsthand，第2章 2.2 引言）**。输入：多位技术专家 + 十几位一线技术主管，覆盖大型/小型/业务型/技术改造型项目。执行：对各类系分做多轮、长时间对比与总结。结果：形成 2.2 节四维度标准范式，仅人力成本即"价值数十万元"——好系分是组织级资产，不是个人文体发挥。

**案例二：账户转账场景系分全流程演示（worked_example，第2章 2.2.1–2.2.3 图2-5~2-8）**。输入：产品需求"账户互转、准实时到账"。执行：技术人重述为"5 分钟内到账、至少 100 TPS、可用性 99.99%"并请产品确认；画 9 步业务流程图与 16 步时序图，图注标出幂等控制点（前端防重+服务端幂等）、三系统职责边界（转账核心/用户中心/账户中心）、3 秒耗时关注点；用例思维导图分业务正常/业务异常/容量幂等三大分支。结论：四维度方法在同一场景可完整走通（教学演示，未说明项目结果）。

**案例三：支付工具额度配置三方案决策（worked_example，第2章 2.2.2 图2-7）**。输入：配置不同支付工具额度的需求。执行：列三方案对比——代码硬编码（工作量少/无扩展性/风险低）、分布式动态配置框架（工作量中/扩展性好/风险较高）、配置表+缓存（工作量大/扩展性中/风险低）。结论：系分记录决策条件、理由与结论供评审集体审查；书中未指定最终选择——要的是决策过程可审，不是唯一正确答案。

**案例四：定时任务系分的四种"最坏可能"（worked_example，第2章 2.2.3）**。输入：定时任务功能的系分。执行：对四问逐项推演——数据被重复调度执行怎么办、处理时效不达标怎么办、无法追踪的原因导致数据积压怎么办、短时间无法诊断的缺陷数据如何阻止执行。结论：明确最坏影响后，倒推监控、处置、系统约束与人工流程四类兜底设计。

**合成演练（原书未提供完整评审案例）**：对一份"兼容性分析只贴代码位置截图+伪代码"的系分（对应 ce020 场景），按六问骨架改写：兼容目标是什么→关键因素（哪些上下游依赖受影响）→可选兼容方案→基于什么逻辑选择→兼容出问题如何兜底→如何验证兼容正确性。按原书规则可复算改写是否达标：改写后测试能否据"影响范围"章节设计用例、维护者能否据"取舍记录"理解当年决策——两者皆能，即达到"可被多角度审视"的标准。

## A2（情境应用）

**触发场景**：
- 接到复杂需求要写系分/技术方案文档，不知道合格标准、章节结构与详略口径；
- 系分被批"空洞""走形式""只有改造点没有分析"，要系统性整改；
- 要组织系分评审，担心讲完没人确认、会后继续吵；
- 跨系统协作要定"这个功能应该哪个系统做"的边界；
- 项目要做工作量评估与里程碑拆分，评审要对齐验收口径。

**语言信号**：
- 中文：系分怎么写、系统分析文档、技术方案文档、方案评审、系统边界、影响范围分析、兼容性分析、工作量评估人日
- 英文：design doc, system analysis, tech spec review, HLD/LLD, system boundary, impact analysis, effort estimation, milestone breakdown

**与相邻能力的区分**（初稿）：
- 与 p9-interface-contract：系分"下启代码"的架构边界要引用接口契约；契约文档的制定、存量治理与契约测试是独立能力，系分只消费其结论。
- 与 p9-clean-code：系分止步于"指导编码的方案"；代码级七步改造与重构执行归 clean-code。
- 与领域建模能力（第3章）：系分中"核心模型"章节需要建模时，实体识别/关系梳理/边界划分的完整方法走第3章能力。
- 与自测用例能力（第4章）：系分的"思维导图用例"是研发侧场景穷举与验收口径；测试资产体系（用例维护、灰犀牛防治）归第4章。
- 与技术规划能力（第12章）："一句话价值"是单项目目标；年度技术规划的高度/深度/锐度与目标-路径-里程碑是另一层。

## E（可执行步骤）

1. **立项三查（动笔前）**。① 受众定位：按五角色清单（产品经理-需求承接确认 / 研发-行动纲领 / 测试-影响分析 / 项目经理-里程碑与风险 / 维护者-方案传承）确认每类读者要从本文档拿到什么；② 一句话价值：按"通过建设××系统能力，实现××技术指标，达成××业务效果"格式写出项目目标，用户价值目标与技术目标都要有；③ 投入确认：系分人力时间在项目早期主动排入。完成标准：一句话价值一句话写完且双目标齐备；五角色清单落到具体人。**判停点：产品需求本身模糊到无法重述 → 停下先做需求澄清**，不带着模糊源头写系分。

2. **上承需求章节**。① 引用原始产品需求（原文或链接）→ 用技术语言重述（时效/吞吐/可用性等指标显性化，如转账 = 5 分钟内 + 100 TPS + 99.99%）→ 请产品经理二次确认并留确认记录；② 用户故事 + 业务流程：用例图/流程图配文字说明相互校验，用颜色标记本次变动范围。完成标准：重述版与产品文档非逐字重复（重复即触发 ce022 检查）；每张图有配套文字；能指出本次改造动的是流程哪个环节、影响面多大。**判停点：产品拒绝二次确认 → 视为源头未对齐，暂停后续章节**。

3. **下启代码章节**。① 系统边界：按"应该谁做"（领域功能职责）而非"谁可以做"（工作量/风险/资源）判定，输出职责划分表 + 时序图（图注标幂等点、边界职责、非功能关注点，图文互校）；② 功能设计：每个设计点列 ≥2 个可选方案，按工作量/扩展性/架构风险/维护成本对比，记录决策条件、决策理由、决策结论（以额度配置三方案为参照格式）；③ 非功能性设计：从用户视角挖操作耗时/安全性/可用性/容量四类隐性需求，每次改造都重新审视。完成标准：任意设计章节能回答六问（目标/关键因素/可选方案/选择逻辑/风险控制/正确性验证）；无"只贴改造点+代码截图"的章节。

4. **守住底线章节**。① 测试用例思维导图：针对变化点按 正常/异常流程 × 历史/新增单据 × 新老链路兼容 × 成功/失败/未知三态 穷举场景，每场景明确输入、输出、检查点，最后做核心要素一致性与完整性平衡检查；② 最坏可能倒推：对每个关键设计点（参照定时任务四问）问"最坏的影响是什么、怎么办"，倒推监控、处置、系统约束、人工流程四类兜底。完成标准：用例导图分支不重不漏、无空白分支；每个关键设计点至少 1 条最坏可能及对应兜底动作。

5. **成文：十节文档结构（书内口径）**。按以下骨架组装：
   1. 修订记录（版本号/变更人/主要变更点说明/时间；置于文档最前；任何改动必须更新）
   2. 需求描述（原始引用 + 技术重述 + 产品二次确认记录）
   3. 项目目标（一句话价值）
   4. 业务流程分析（用户故事 + 流程图 + 变动范围标记）
   5. 系统边界与交互（职责划分 + 时序图 + 文字说明）
   6. 功能设计（决策思维：方案对比 + 决策三要素）
   7. 非功能性设计（耗时/安全/可用性/容量）
   8. 测试用例分析（思维导图 + 检查点）
   9. 风险分析与兜底（最坏可能倒推）
   10. 工作量分析与项目安排（表格：改造内容/负责人/预计人日；单任务 >3 人日必须再拆分）
   完成标准：十节齐全（可按项目规模合并，但要素不可缺）；工作量表每行 ≤3 人日；修订记录与当前版本一致。

6. **评审收口（五环节）**。① 会前：明确评审目标清单——与哪些人达成哪些共识、要哪些明确结论；② 会中：先讲全局方案给整体感知，再进细节；进细节前先厘清架构边界（尤其接口契约）；领域技术细节移到会后专项讨论；③ 会后：任何反馈记录并修订补充回系分，作为待办跟踪与追溯依据。完成标准：会前发出目标清单；会中每个目标得到"同意/修改后同意/否决"的明确结论；会后变更及时更新进修订记录（时限书中未规定，约定：按团队惯例明确一个 SLA 并写进流程）。**判停点：无目标清单不开会；关键相关方（产品/架构/测试）缺席 → 改期**，不"先行讲完"。

**输入契约**：必需 = 产品需求文档（或原始需求描述）+ 涉及系统的现状资料（架构图/核心模型或表结构/现有流程）；缺失时先向用户索取，不虚构系统现状。可选 = 历史系分（演进参考）、既有接口契约、项目资源与时间约束。

**输出契约**：一份十节结构的系分文档（Markdown 或团队模板），每个分析章节含六问自洽论述；另附评审目标清单 + 结论记录 + 修订记录。验收口径：五角色各自所需信息（需求确认/行动纲领/影响范围/里程碑风险/取舍传承）均可在文中指认到具体章节。

## B（边界）

**反场景（何时不用）**：
- 单人小改动、口头或白板即可对齐的方案——强套十节模板就是"形式大于实质"（ce016）；
- 原型探索期、需求剧烈变化——系分速朽，先轻量记录决策即可；
- 纯代码级重构（行为不变）——走 clean-code 的 ROI + 用例流程，系分只在涉及跨系统影响时出场；
- 纯 API 对接与状态码约定——归接口契约能力。

**书中警告的失败模式（含候选反例 id）**：
- ce016 形式大于实质：模板堆默认内容、故障后机械加条目，文档冗长空洞、评审"无人关心"——形式化产出无法承载逻辑；
- ce017 故障—质量恶性循环：质量差→故障多→修复与多轮复盘吞噬时间→质量更差；"没时间写系分"成为常态即是掉入循环的信号；
- ce018 系分只写给自己：缺需求描述、影响分析与里程碑，各角色看完仍各说各话，争议推迟到联调爆发；
- ce019 只在脑内推演："方案在我脑子里"写不出来——写不明白恰是没想明白的证据，逻辑缺陷被拖到编码/生产才暴露；
- ce020 只罗列改造点：贴代码截图代替兼容范围、准确性保障、出错处置的论述，自己误判周全、他人无法评估；
- ce021 评审"最后一公里"走形式：无目标清单、无变更记录，讲的人只管讲完、听的人刷手机，会上"共识"会后继续争论；
- ce022 需求描述照抄产品文档：跳过"真正理解 + 技术补充"两个增值环节，源头偏差无校验点；
- ce023 把产品需求当项目目标：技术目标被忽略，项目缺投入边界与验收焦点，后期撕扯增多；
- ce024 非功能设计"以后再说"："小改动""时间紧"借口累积技术债，系统逆水行舟，集中偿还代价指数放大；
- ce025 "写测试用例是测试人员的职责"：源头质量控制缺失，低级 Bug 流到测试/生产，修复成本多角色叠加。

**作者盲点/时代局限**（阶段 0 批判）：
- 四维度范式出自蚂蚁专家共创（c022），隐含大项目、多团队、有系分评审会与修订记录制度的组织条件；小团队需裁剪为轻量版（建议至少保留：一句话价值 + 决策思维 + 最坏可能三要素），否则模板本身成为新负担；
- "一份优秀系分价值数十万"以专家人力成本折算，是幸存者视角的估值，未讨论过度系分（为小需求写重文档）的浪费边界；
- 与敏捷社区"可工作的软件高于详尽的文档"存在张力：书中流程带明显大厂瀑布式评审语境，未讨论系分与迭代式/滚动式开发的适配方式。
