# 领域建模四招与边界

## R（原文摘引）

> "领域模型包含三个核心要素：目标、实体和关系……目标指的是问题域，即任何模型都是为了回答某个问题，这也意味着领域模型是有明确边界的。"（3.1.2 领域模型的模型）

> "第一招：从问题出发，收集信息……第二招：实例推演，提炼模式……第三招：结构分析，抽象模型……第四招：真实还原，验证场景。"（3.1.3 领域建模的普适四招）

> "我们也许没办法一下子回答'某个实体对不对'的问题，但我们能够快速回答'某个实体坏不坏'的问题。如果实体没有包含全六大要素，那它大概率就是坏的。"（3.1.2 实体构成的必备六大要素）

> "在筛选实体时，应选择那些最接近真实、最简单的内容。找到那些稳定不变、必需的元素，并遵循'如无必要，勿增实体'的原则。"（3.1.3 第三招：结构分析，抽象模型）

> "通过这种方法，模型一旦生成就是可用的，并且一旦存储到数据库中就是可信的……需要注意的是，即使系统在领域模型上进行了检查，也不能认为万事大吉。"（3.3.1 没有一招鲜吃遍天）

## I（解释）

领域建模是把一团模糊的业务叙述，整理成"目标—实体—关系"三层结构的操作过程：目标圈定问题域（模型只回答一个问题，因此天然有边界）；实体是客观存在、可相互区分的对象；关系（依赖/关联/继承/聚合/组合）把实体连成有机体。

操作序列是普适四招：**收集信息**（从问题出发，把原始数据经"明确→描述→定义→统一→还原"五步加工成自洽信息）→**实例推演**（拿真实实例按多维度归类，提炼稳定模式，并拿新案例验证）→**结构分析**（从模式互动中识别实体、关系与层次，克制增实体）→**真实还原**（回到源头场景演绎，通常会暴露出核心模型之外的配套模型需求，如配置模型）。

判断实体质量的快速手段不是证明"对不对"，而是查"坏不坏"：六要素（属性、行为、状态机、完整性检查、平衡性检查、核心逻辑计算）缺任何一项，实体大概率是坏的。

模型的护体价值来自分层布防（model/repository/core service/business service 四层各司其职）与自检兜底，但模型只在"有状态、有不变量、需集中管控风险"的场景里划算——这是它的适用边界，也是锤子效应的防线。

## A1（原书案例 / 合成演练）

**原书案例一：账号记账系统四招全流程（worked_example，3.1.3，图 3-5～3-7）**。输入：缺乏账户模型导致的问题（余额记录不准、明细查询低效、资金变动相关方难确定）。执行：第一招从问题明确账户关键属性（账号、余额、记账明细），抽象出 AccountModel + AccountingLog；第二招对热点账户按"记账金额×账户属性"两维归类，推演出延迟记账/实时记账模式；第三招按时效性抽象出实时/准实时/日末三级记账策略模型；第四招回到源头三问（谁在何时配置、谁判断适用、如何防配置错误），发现必须补 ConfigurationModel/ConfigurationRecord 配套模型。结论：仅核心模型不够，源头验证暴露配套需求。结果未说明（建模推演示例）。

**原书案例二：记账模型四阶段演进（worked_example，3.3.4，图 3-13～3-16）**。输入：业务与技术持续演进（日终结算→冻结解冻→分布式事务）。执行：冻结解冻因有独立业务场景与标准操作，选"新增 FreezeLog 模型 + AccountModel 补 freezeBalance 字段"而非改造原记账逻辑；2PC 适配则新增 TransactionLog 并预留 inTransBalance。结论：新能力与既有操作不同类→新增模型；同类扩展→原模型加属性。结果未说明（演进推演）。

**原书案例三：账户状态查询直连 DAO（worked_example，3.3.3，图 3-12）**。输入：系统 A 管账户余额（需严谨模型），但另需仅提供账户状态查询的服务。执行：查询服务不走 Repository 加载完整模型，直接 DAO 查状态字段返回。结论：建模与否按子服务职责分别判断，防锤子效应。结果未说明（取舍示例）。

（另：全章以汽车演示实体六要素与聚合/组合之分——车架与汽车寿命一致为聚合，车轮可转移他用为组合，3.1.2/3.2.3，类比教学。）

## A2（情境应用）

**触发场景**：
- 接手一个新业务域（账务、支付、库存类），要从模糊需求中抽象出实体、关系与边界；
- 评审他人或团队的领域模型/实体设计，需要快速判断"这个实体坏不坏"；
- 业务新增能力（如冻结解冻），纠结是改老模型还是新增模型；
- 团队想给门户/聚合查询类系统上 DDD，需要判断该不该建模；
- 系统交接后模型里堆满临时 if else，需要判断模型是否已被破窗并制定管控。

**语言信号**：
- 中文：领域建模、怎么找实体、模型边界、抽象模型、实体之间的关系、该不该用领域模型/DDD、状态机怎么设计、加字段还是加模型、模型改不动了
- 英文：domain modeling, DDD, entity identification, aggregate vs composition, bounded context, model evolution, "should this service use a domain model"

**与相邻能力的区分**（初稿）：

## E（可执行步骤）

0. **前置边界判断**（判停点前置）：看系统/子服务职责——纯流程编排、聚合呈现类（如门户），或仅提供简单状态查询 → 不建模，直接编排/DAO 返回，流程到此结束。完成标准：给出"该服务是否有状态、有不变量、需集中管控风险"的明确结论。
1. **第一招：从问题出发，收集信息**。依次执行明确问题（一句话说清要回答什么）→描述问题（全量收集相关数据）→定义信息（分类、多维度、同维度统一）→统一信息（标准化、与业务一致）→还原问题（用信息复述问题做自洽校验）。完成标准：问题可一句话陈述；信息标准化且能自洽还原问题；关键属性清单可指认来源。
2. **第二招：实例推演，提炼模式**。观察真实实例中参与者的特征与行为，至少从两个维度归类，推演出操作模式；与多方对话，并将模式套到未参与提炼的新案例上验证。完成标准：每个模式至少通过 1 个新案例；无"只看局部"的单一维度结论。
3. **第三招：结构分析，抽象模型**。从模式互动中识别实体与关系（依赖/关联/继承/聚合/组合），构建层次结构；筛选时遵循"如无必要，勿增实体"（只留稳定、必需、最接近真实的元素）；对每个实体逐项检查六要素：属性（自有/关联、业务语言）、行为（可交互且闭环）、状态机（行为的前置与后果）、完整性检查（输入输出合法准确）、平衡性检查（多属性/关联实体间匹配）、核心逻辑计算（实体内核）。完成标准：每个实体六要素逐项填写；缺项即判"坏"，补齐或删除；聚合/组合有寿命判断依据（能否独立存在）。
4. **第四招：真实还原，验证场景**。用模型演绎真实与扩展场景，从源头三问验证：谁在何时配置/操作？谁判断适用性？如何防范配置错误？完成标准：三问有答案；暴露出的缺口转化为配套模型（配置模型、操作记录等）并纳入模型清单。
5. **演进决策**（变更场景）：新能力有独立业务场景与标准操作、与既有操作不同类 → 新增独立模型 + 原模型补必要字段；同类扩展 → 原模型加属性方法。同时评估老模型改造与数据兼容成本（代码 + 数据，常以月/年计），兼容性按接口/逻辑/数据三类拆解。完成标准：演进方案含兼容性三拆结论与成本估计。

**输入契约**：必需 = 业务问题描述（一句话 + 背景）+ 实例数据/场景样本（真实案例，非纯逻辑推演）+（演进场景）现有模型定义。实例缺失时应先收集实例并与业务方对话，不凭空建模；问题说不清时先回到第一招的"明确问题"。
**输出契约**：问题定义（一句话）、实体清单（每个实体含六要素逐项内容）、实体关系与层次图（标注聚合/组合及依据）、模型边界声明（回答什么问题、不回答什么）、配套模型清单、（演进场景）演进方案 + 兼容性三拆。
**判停点**：步骤 2 模式在新案例上验证失败 → 退回步骤 1 重新收集信息；步骤 3 实体六要素长期补不齐 → 质疑该"实体"是否真实存在，考虑删除；步骤 4 源头三问答不上 → 模型缺配套，补齐后再验证，不得以"纯逻辑推演自洽"放行。

## B（边界）

**反场景（何时不用）**：
- 流程编排/聚合呈现类系统（门户）：强行建模导致研发流程笨重、响应变慢（3.3.3）；
- 已建模系统中仅提供简单状态查询的子服务：为取一个字段加载整个完整模型是过度复杂化，应直接 DAO 返回（图 3-12）；
- 业务剧烈变化期：模型承载的是当前阶段认知，认知未稳定时建模投入会被反复推翻。

**书中警告的失败模式**：
- ce033 锤子效应：熟悉建模后把一切问题当建模问题——无状态、无不变量可守的场景，模型开销只有成本没有收益；
- ce032 破窗效应：新人与资深者在交付压力下向模型塞临时 if else，无管控机制时模型完整性被渐进瓦解（预警信号：模型中出现带业务 ID 判断的 if else、变更不走评审）；
- ce031 一招鲜：以为实体有自检就万事大吉——直改库绕过校验、跨域一致性都不是模型层能独自解决的，需流程制度（DB 直改审批）+ 跨域核对机制补位；
- ce034 使你成功的也阻止你进步：因未来不确定不敢升级、因代码+数据兼容成本（数月至数年）拖延升级，模型与业务认知脱节（预警信号：新需求都靠旧模型外挂补丁实现）。

**作者盲点/时代局限**：
- 方法与案例全部来自蚂蚁支付/账务语境，隐含严格的模型评审管控、审批流程与配套基建；小团队移植时"模型定义与变更严格管控"可能缺乏组织支撑，至少须以评审与文档约定降配替代；
- 六要素是"坏味道"快检（必要性判断），不是充分性证明——六要素齐全的实体仍可能"不对"，原书自己也承认这一点；
- "四招""六要素"等整齐命名属作者事后归纳（阶段 0 批判），未给严格划分依据；术语体系与 DDD 社区（限界上下文、聚合根）不完全对齐，对接 DDD 生态时需自行翻译。
