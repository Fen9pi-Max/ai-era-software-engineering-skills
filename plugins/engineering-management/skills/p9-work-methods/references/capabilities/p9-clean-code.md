# 好代码构造与安全重构

## R（原文摘引）

> "化繁为简、回归本质，抛去这些复杂概念，基于我十多年的编程经验，我总结出一个评判好代码的标准：'好代码应当能够"一眼看到底"'。"（第1章 1.1.1）

> "好的代码特点是，一个主方法会调用若干个子方法，每个子方法会解决一个子问题。通常一个主方法体里面只有几行代码，但就这几行代码却回答了一个更大问题……整个代码的层次结构就像洋葱一样。"（第1章 1.1.2 第三步）

> "对于任何不清楚或考虑不到的情况，都应该明确拒绝执行。这种'宁愿不做'和'不错做'的策略是编程中最好的安全措施。"（第1章 1.2.1）

> "本质上，代码重构其实是一种技术投资，投入时间和资源以优化代码，从而获得支持业务发展的收益。作为一种投资行为，代码重构的最佳评价模型是投入产出比（ROI）。"（第1章 1.3.1）

> "在生产环境中运行的代码，每一行都有其存在的意义。这是代码重构的一条黄金法则，也是不变的真理。"（第1章 1.3.2）

> "代码重构不是技术主管的一厢情愿，也不是资深程序员的个人炫技，更不是某个人的'代码洁癖'或个人英雄主义行为。"（第1章 1.3.3）

## I（解释）

这套方法把"什么是好代码"从一串抽象维度（可读性/可复用/可扩展/鲁棒/安全/可测试）压缩成一个可操作的单一判据：**读者顺序读一遍就能理解全部逻辑，不需要跳跃定义、回溯上下文**。达成路径是七步：统一规范（公司规范+SOLID+设计模式）→ 团队共识框架（不炫技、不造轮子）→ 洋葱式模块结构（主方法只回答一个大问题）→ 揭示代码外信息的注释（问题/假设/约束/思路/关联）→ 拿捏关键实现细节（如加锁前排序防死锁）→ 充分测试用例（正常+边界+空值）→ 良好协作界面（DSL 封装领域专业性）。能力成长对应三阶段：先功能正确 → 再追求技艺 → 最后回归解决实际问题（看山三重境界）。

坏代码分三档危害：让队友失败（暧昧不拒绝、锁不锁模型根、风险管控不集中）、让团队疲惫（依赖非单调排序、照猫画虎复用、策略写死不留应急后路）、让团队跌份（日志无结构、数字替代语义落库、多表时间轴错乱）。贯穿的安全法则是"宁愿不做、不错做"——对考虑不到的输入显式拒绝，绝不走默认逻辑。

重构被重新定义为团队资产的投资行为而非完美主义冲动：用 ROI 三问（投入能否承担/产出是否足够/受益方是谁）决策，先算物质账再谈精神收益；动手前先补测试用例在旧代码跑通基线，重构后同用例比对，以"相同输入→相同输出"证明逻辑等价；整个过程要量化价值、里程碑推进，不是单人闭环的英雄主义。

## A1（原书案例 / 合成演练）

**案例一：外汇兑换接口的 DSL 改造（worked_example，第1章 1.1.2 第七步 图1-7/1-8，兼 1.1.3 三阶段贯穿案例）**。输入：出国旅游人民币换美元的外汇接口，传统实现要调用方组装汇率、币种、买卖方向等专业参数，买入价/卖出价常被混淆致障。执行：改为 DSL 对话式 API，三行完成——取汇率 `consultQuote().receive(USD).pay(CNY).quote()` → 计算需付出金额 → 成交 `tradeOrder().receive(...).pay(...).useQuote(token)`，专业细节封装进接口内部。结论：调用方无须懂内部实现，出错面大幅缩小；同一案例贯穿三阶段（功能平铺→设计模式组织参数→回归业务本源）。改造效果以对比展示，未说明量化结果。

**案例二：团队禁用 JDK 1.8 新语法（firsthand，第1章 1.1.2 第二步）**。输入：作者所在团队，Lambda/Stream 等新语法流行期。执行：一段时间内禁止使用。理由：成员看不懂的代码会削弱研发与评审环节发现问题的能力，代码是团队资产。结论：待全员深刻理解后才放开——"独行行快，众行行远"（结果未说明，仅交代规则与理由）。

**案例三：局部"修复"引爆生产故障（reported_case，第1章 1.2 引言）**。输入：一段逻辑不严谨的线上代码。执行：有人对其做了优化。结果：生产环境故障——上游调用端恰好依赖这段"不严谨"行为，两处缺陷原本互相抵消，修掉一处反而引爆另一处。结论：这是"生产代码每一行都有存在意义"黄金法则的现实出处，也是重构必须逻辑等价的证据。

**案例四：重构 ROI 演算（worked_example，第1章 1.3.1）**。输入：月薪 1 万元、月 22 个工作日、约 50 人日的重构项目。计算：人日成本 = 10000 ÷ 22 ≈ 454 元；项目成本 = 454 × 50 ≈ 2.27 万元。结论：发起方必须回答"2.27 万元投入带来什么、多久回本"；先把物质账算清，再评估技术氛围等精神收益（未说明具体项目结果）。

**案例五：isEmpty 改 isBlank 的不等价替换（worked_example，第1章 1.3.2 图1-19）**。输入：Apache StringUtils 的 isBlank 与 isEmpty——对空格串 " "，isBlank 返回 true，isEmpty 返回 false。执行：若为"规范统一"把原 isEmpty 全改 isBlank，输入不变而输出翻转。结论：重构只许改内部逻辑，不许改输入输出映射；验证方式是用线上相同入参重放、比对返回信息。

## A2（情境应用）

**触发场景**：
- 你新写一段业务代码，或接手/评审一段被吐槽"看不懂""不敢改"的代码，要系统性改造而非零敲碎打；
- code review 反复提命名/层次/注释意见，想统一团队的编码底线（default 怎么写、日志怎么打、锁怎么加）；
- 看到一段"不严谨"的祖传代码手痒想重构，但不确定值不值、怎么保证不出生产事故；
- 排查不定期出现的偶发 Bug，怀疑代码依赖了不稳定逻辑（如非单调排序字段）。

**语言信号**：
- 中文：代码可读性差、一眼看到底、编码坏习惯、switch default、防御性编程、祖传代码不敢动、重构怎么保证不出问题、逻辑等价
- 英文：clean code, readability, code smells, defensive programming, fail fast, refactoring legacy code, behavior consistency, logic equivalence

**与相邻能力的区分**（初稿）：
- 与 p9-system-analysis：本能力管代码级构造与重构执行；系分管需求→方案的设计文档层。重构方案本身需跨系统论证时，先走系分再回到本能力执行。
- 与 p9-interface-contract：第七步"协作界面"只管 API 形态友好（如 DSL 封装专业参数）；跨团队权责约束、S/F/U 状态语义与契约测试归接口契约能力。
- 与领域建模能力（第3章）：本能力的"锁模型根/校验集中到领域模型"只取建模思想的编码落地；实体识别、关系梳理、边界划分的完整方法在第3章。
- 与自测用例能力（第4章）：本能力要求"用例时间不少于功能代码"并覆盖边界；用例的体系化设计（用户故事验证、护航关键设计、灰犀牛防治）在第4章。

## E（可执行步骤）

1. **基线判定：做"一眼看到底"测试**。请一个没接触过该代码的人（或自己隔一周）顺序读主流程，记录每个需要跳转定义、回溯上下文、翻注释或问人的位置。完成标准：得到一份卡点清单，每个卡点可归入七步之一（规范/框架共识/结构/注释/细节/用例/协作界面）；无卡点则代码达标，直接进第 3 步坏习惯扫描。

2. **按七步改造**（每步完成标准）：
   - 规范：对照团队规范（无则参考《阿里巴巴 Java 开发手册》）过命名/注释/异常处理——完成标准：无个人风格偏离项；
   - 框架共识：检查是否引入团队未共识的语法/框架或自造轮子——完成标准：所用技术栈全部可指认"团队已共识"，否则先发起共识讨论或退回旧栈，不强推；
   - 模块结构：主方法只回答一个大问题、只留几行编排，子方法各解决一个子问题——完成标准：任意方法能用一句话说出它回答的问题，无数千行单文件；
   - 注释：为"代码行里看不到但影响整体"的信息写注释（要解决的问题/前提假设/约束条件/核心思路/关联关系），状态机用文本图——完成标准：没有"翻译方法名"式注释；
   - 关键细节：识别并发/加锁/顺序敏感点——完成标准：加锁在专门函数中、加锁前对资源排序（防死锁）、锁对象是模型根而非字段；
   - 测试用例：正常功能 + 空串/NULL/边界/并发场景——完成标准：用例设计实现时间不低于功能代码时间，改逻辑时用例能报警；
   - 协作界面：对外 API 让调用方无须懂内部细节——完成标准：调用方按业务语义即可完成调用，专业术语（如买卖方向）被封在接口内。

3. **坏习惯九项扫描**：① switch 的 default 抛异常拒绝而非默认逻辑；② List 取值前断言长度、DB 更新后断言影响条数；③ 悲观锁锁模型根，同模型多处修改不分别加锁；④ 高风险校验集中到领域模型统一检查方法，业务方法只调用；⑤ 排序/分页字段必须单调递增或递减；⑥ 批处理策略配置化 + 正常/失败双队列；⑦ 日志三原则（定位到数据/定位到代码/便于监控）；⑧ 落库存储完整业务语义不用数字；⑨ 同事务多表用单点时间更新 modify 字段。完成标准：九项逐条标注 通过/整改/不适用，"不适用"须写理由。

4. **重构决策：ROI 三问**（判停点在本步末）。① 投入能否承担：估算人日并折算成本（人日成本 = 月薪 ÷ 月工作日，书中示例 10000÷22≈454 元/人日；50 人日 ≈ 2.27 万元），不与业务交付抢资源、不同时铺多个重构；② 产出是否足够：写出可量化收益（效率提升幅度、回本周期），算不平物质账不许拿"技术氛围"抵数；③ 受益方是谁：团队无共识的可读性改造只算个人偏好；过度抽象/造轮子/引入陌生技术计负分。完成标准：三问有书面答案，结论为 重构/缩小范围/不做 三选一。**判停点：ROI 亏损且无法缩小范围 → 记录决策不做**，转入日常小步改善，不"除恶务尽"。

5. **安全执行：先补用例再重构 + 逻辑等价收尾**。① 重构前：把听到的/看到的/想到的（口头经验、线上行为）转成测试用例，在**旧代码**上跑通并留档基线；② 重构中：禁止 isEmpty→isBlank 这类"看似等价"的替换，除非行为差异被用例显式覆盖；③ 重构后：同套用例重跑比对；有线上接口的用相同入参重放比对出参。完成标准：基线与重构后用例结果完全一致，留对照记录。**判停点**：旧代码上用例跑不通（行为本身有 Bug）→ 先修 Bug 或把 Bug 显式固化为用例再继续；重构后用例失败 → 禁止凭自信判"用例问题"，必须对比新旧代码运行结果，差异无法解释即回滚。

**输入契约**：必需 = 目标代码（可读源码与调用关系）+ 重构场景的运行验证手段（可执行测试，或线上接口入参/出参录制；两者皆无 → 先补齐再动手，不静默猜行为）。可选 = 团队编码规范、评审意见清单、性能/并发要求。

**输出契约**：改造后代码 + 卡点清零的"一眼看到底"检查记录（卡点→七步归因→整改项）；重构场景另交付 ROI 三问书面结论、基线用例集、重构前后用例/线上重放对照结果（一致率 100% 或附差异解释清单）。

## B（边界）

**反场景（何时不用）**：
- 一次性脚本、临时代码、已明确下线的系统——不值得投入七步与用例成本；
- 纯算法/性能优化问题（复杂度、缓存命中率）——先解决正确与性能，可读性重排其次；
- 行为需要变更的需求改造——那不是重构（重构 = 行为不变），直接按需求开发并同步更新用例；
- AI 批量生成代码的风格化改写——书中方法以人手写代码为前提（见作者盲点）。

**书中警告的失败模式（含候选反例 id）**：
- 让队友失败类：ce001 暧昧不拒绝（default 默认逻辑/get(0) 不断言/DB 空更新）；ce002 擒贼不擒王（只锁密码不锁用户模型根→改密窗口被盗改密保二次盗号）；ce003 风险管控不集中（校验散落各处，规则变更必改漏）；
- 让团队疲惫类：ce004 非单调排序字段引发不定期偶发 Bug；ce005 照猫画虎（事务消息回查当存在性判断，三态问题二态处理）；ce006 批处理策略写死不给应急留后路（数据积压、服务器过载崩溃）；
- 让团队跌份类：ce007 任性打日志（排障定位不到数据与代码）；ce008 数字替代业务语义落库（省不了空间却转嫁理解成本）；ce009 各表独立取时间破坏统一时间轴；
- 重构类：ce010 修复"不严谨"代码引爆被抵消的缺陷（1.2 引言生产故障）；ce011 重构上瘾/除恶务尽（多线铺开、投入超负荷制造"新一轮垃圾"）；ce012 受益方错位（个人偏好式可读性改造、造轮子，V1/V2/V3 并存是历史痕迹）；ce013 不补用例就重构 + 用例失败时逻辑自信归咎用例；ce014 isEmpty→isBlank 式不等价"规范化"；ce015 英雄主义重构（单人闭环、无评审、无里程碑无度量）。

**作者盲点/时代局限**（阶段 0 批判）：
- 案例与规范（《阿里巴巴 Java 开发手册》、悲观锁+DAO 式资金处理）全部出自蚂蚁支付/交易语境，小团队、非 Java 栈需按组织规模与基建水平降配；
- 成书于 2024 年 10 月，LLM 辅助编码刚兴起，第 1 篇方法以人手写代码为前提，未覆盖 AI 结对编程下"好代码"标准与作者主体的变化；
- "七步/三阶段/三类坏习惯"等数字框架是作者经验归纳，命名整齐但无严格划分依据（事后归纳风险），应作检查清单使用而非教条。
