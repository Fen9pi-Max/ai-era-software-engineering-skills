# 幂等性与错误码排障

## R（原文摘引）

> "幂等性控制逻辑和业务处理逻辑必须同时成功或同时失败。这也是为什么幂等性控制通常使用数据库唯一键来实现，并且被包裹在业务处理逻辑的事务中。"（5.1.1 幂等性的本质·原子性）

> "幂等的传递性是指在具有幂等性的函数链中，如果一个函数是幂等的，那么它所依赖的所有函数也必须是幂等的。"（5.1.1 幂等性的本质·传递性）

> "单一存储点和全局检查构成了幂等性控制不可或缺的两个要素……在使用分库分表时，必须确保相同的幂等性控制字段值落在相同的分库分表中，否则幂等性控制也会失效。"（5.1.2 未受约束的幂等性控制字段存储方案）

> "一锁：根据幂等性约束，获取记录的悲观锁。二判：检查加锁记录的状态是否符合预期。三更新：在加锁和状态检查之后，执行业务逻辑，更新数据。"（5.1.2 暗藏玄机的并发控制）

> "切流开关翻转后，门户因未收到 A 的成功回执，以同一单号重试恰被路由到 B；B 的库中查不到该单号记录，幂等校验失效，再次处理成功——同一单号被 A、B 各处理一次，导致重复提现。"（第5章 图5-7 插图转录）

> "将网络超时等异常视为失败是有问题的。因为无法确定是在请求未到达服务提供方，还是在服务提供方已处理成功但在返回结果时遇到网络超时。"（5.2.2 处理错误码的三种典型技术盲区）

> "做好错误码映射原则：对于非明确表示业务成功或失败的错误码，应一律映射为未知状态。"（5.2.4 错误码的处理·服务调用方）

## I（解释）

这张卡处理分布式系统两类最高发的资损故障：同一笔业务被做了多次（幂等失效），以及我方单据状态与对方系统实际结果不一致（错误码处理失误）。

**幂等有效的两个本质条件**：原子性——幂等控制逻辑（记录请求、更新状态）与业务处理逻辑必须同事务、同时成败，否则"控制成功+业务状态更新失败"会在重试时放行重复请求；传递性——幂等函数依赖的所有下游函数必须全部幂等，否则上层重试把故障修复变成下游重复执行。实现上通常用数据库唯一键包在业务事务里。

**幂等失效排障按三维展开**（大部分故障出在字段维度）：字段——必须在业务分区内永久唯一（防截断"短号"）、不得随时间/环境变化（防日期跨天、时区、时钟不同步）、必须严守契约约定（不得单方面加工拼接）；存储——单一存储点 + 全局唯一检查两要素缺一不可（唯一索引被破坏、分库分表路由键可变都会瓦解全局唯一性）；逻辑——前端防重可被绕过不可依赖、并发更新遵循"一锁二判三更新"（低频也不例外）、缓存只能记录请求路由而业务幂等必须以数据库为准、服务提供方必须保存并返回相同终态并为幂等命中提供专门错误码。

**错误码的本质是异构系统数据一致性**：对方返回码只有"明确业务成功/明确业务失败"两种可映射终态，系统交互失败（Request_Failed）、网络超时、查询"交易不存在"一律映射为未知，再通过拉模式（主动查询，异常/空结果都继续查）或推模式（SPI 通知，结果明确且入 SLA，调用方做幂等与终态锁定）补偿到最终一致。不一致时间窗口是资金安全与用户体验的权衡，必须落地为有法律效力的 SLA：超窗查不到或迟到的通知一律置失败；人工补救先改我方单据状态再操作外部。

## A1（原书案例 / 合成演练）

**原书案例一：提现幂等字段的连环失效（firsthand，5.1.2，图 5-3/5-4）**。输入：用户余额提现场景。执行：第一版取自增 Sequence 后 8 位作幂等字段（requestId 只有 8 位）——请求量增长后短号重复，重复入账；第二版改"8 位日期+Sequence"——网络抖动重试的同一请求号前后相差 1 秒恰好跨天，生成两个不同幂等值，用户提现一次收到两笔钱。结论：字段必须分区内永久唯一，且不得随时间/环境变化。结果：书中交代为实际生产故障（开发者 A 亲历）。

**原书案例二：用户注册的存储失效（worked_example，5.1.2，图 5-5/5-6）**。输入：注册新用户幂等设计（check-then-insert + DuplicatedKeyException 捕获）。执行：唯一索引未设或被数据迁移破坏时，低并发测试与生产都暴露不了，并发上来后同手机号重复注册；若按年龄等可变字段分库分表，同一手机号落入不同分片，各分片各自唯一、全局重复。结论：单一存储点+全局检查是两要素；分片路由必须收敛到稳定键。结果未说明（推演示例）。

**原书案例三：切流期跨系统幂等击穿（worked_example，5.1.2，图 5-7，原书插图转录案例）**。输入：新老提现系统 A/B 双库并行、切流开关切换，用户以单号 X 发起提现。执行（epub v2 插图转录补齐完整步骤链）：开关初始指向 A→门户将单号 X 送提现系统 A 处理成功→A 的成功回执因网络抖动未达门户（图中便签：门户不知道该单号已处理成功）→切流开关翻转到 B→门户复用同一单号 X 重试、请求被路由到 B→B 库查无该单号记录（幂等校验失效）再次处理成功并返回"提现成功"→同一单号被 A、B 各成功处理一次，用户重复提现。结论：单号唯一性只在单系统内成立，切流期幂等必须跨系统全局设计。结果未说明（时序推演；步骤链出自原书插图转录）。

**原书案例四：错误码三盲区重复到账（firsthand，5.2.2/5.2 开篇，图 5-11/5-12）**。输入：对接银行提现接口。执行：三个盲区逐一踩雷——把 Request_Failed（系统交互失败）当业务失败置 FAIL（银行异步处理实际成功，用户重试二次提现两次到账）；把网络超时置 FAIL；超时后查询返回 TRANSACTION_NOT_FOUND（原事务未提交）置 FAIL。结论：非明确成功/失败一律未知，走查询/补偿对齐。结果：书中交代为实际生产资金故障（"银行卡收到了两笔款项"类）。

**原书案例五：提现失败人工打款的订正顺序（worked_example，5.2.3，异常补救）**。输入：提现失败需通过银行网银人工打款补救。执行：错误顺序是先打款后改状态——系统重试可能再打一次；正确顺序是先把我方提现单据置成功、再人工打款，杜绝重试重复处理；且禁止后台直接改单据绕过核心模型校验。结果未说明（操作规程示例）。

## A2（情境应用）

**触发场景**：
- 线上出现重复扣款/重复提现/重复注册类资损故障，要快速定位幂等失效点；
- 设计或评审幂等方案：字段怎么选、唯一键怎么建、要不要加锁、缓存能不能用来防重；
- 对接银行/第三方支付/外部机构接口，处理网络超时、Request_Failed、"交易不存在"该怎么映射单据状态；
- 单据卡在中间态无法推进，或把对方实际已成功的单据错标为失败引发投诉；
- 新老系统切流、数据迁移期间防止同一请求被两套系统各处理一次。

**语言信号**：
- 中文：幂等、防重、重复支付、重复扣款、唯一索引、悲观锁、一锁二判三更新、防重复提交、错误码映射、超时算成功还是失败、未知状态、补偿、对账、卡单
- 英文：idempotency, idempotency key, duplicate payment, dedupe, error code mapping, timeout handling, UNKNOWN state, retry, reconciliation, eventual consistency

**与相邻能力的区分**（初稿）：
- 与 p9-self-test-quality：那卡管怎么用并发用例验证幂等（10 线程断言 1 笔）；本卡管幂等机制本身的设计审查与失效排障——先由本卡定位/修复，再用那卡的用例固化验证。
- 与 p9-dist-tx-cache（ch5.3/5.4）：分布式事务方案选型、事务悬挂、缓存一致性与双刃剑归那卡；本卡只借"缓存只能拦路由"这一点判定幂等，不展开缓存治理。
- 与 p9-async-ha（ch5.5/5.6）：FailOver 切换瞬间幂等、异步任务回查不严谨是同一原理在 HA/异步场景的表现，归那卡；本卡提供其底层的幂等与终态原理。
- 与 p9-emergency-risk：应急响应流程归那卡；本卡的人工补救两原则是数据订正场景的具体操作顺序。
- 与 p9-domain-modeling：那卡 3.2.4 仓储层铁律（逻辑删除/新增幂等/一锁二判三更新）在分层架构中的位置；本卡是其并发与幂等专题的展开。

## E（可执行步骤）

本卡 E 段为**排障路径**：每一步按"症状 → 判断条件 → 操作 → 验证"组织。

1. **定类分流**。症状 A：同一笔业务被执行多次（重复扣款/提现/注册）→ 走步骤 2～4（幂等三维审查）；症状 B：我方单据状态与对方实际结果不一致（成功标失败、卡单、用户收到两笔）→ 走步骤 5～7（错误码与一致性）。两类并发时先 A 后 B（先止血重复处理）。完成标准：症状类别、涉及系统与单据样本（≥2 条）已确认。
2. **[A] 字段维度审查**。判断条件：幂等字段是否经截断/取模/拼接加工（短号）？是否含日期/时间成分（跨天重试、时区、机器时钟不同步）？是否严格按接口契约取值（有无单方面拼装）？操作：改用业务分区内永久唯一、不随时间环境变化、契约明确约定的字段；字段规则变更必须双方协商修订契约，不得调用方单方面改。验证：统计历史数据无同值重复；重放同一历史请求两次，生成的幂等字段值完全相同。
3. **[A] 存储维度审查**。判断条件：唯一索引是否真实存在且未被数据迁移/表变更破坏？分库分表下相同幂等字段是否必然路由到同一分片（分片键是否可变，如年龄）？操作：确保单一存储点 + 全局唯一检查两要素齐备——先查后插的竞态必须由唯一索引兜住（捕获 DuplicatedKeyException 触发幂等返回）；可变分片键换成稳定键。验证：并发重复请求压测（低并发测不出此缺陷）；迁移后复核索引完整性的检查项纳入发布清单。
4. **[A] 逻辑维度审查**。判断条件：幂等控制逻辑与业务逻辑是否同一事务（原子性）？依赖链上的下游函数是否全部幂等（传递性）？是否只做了前端防重？是否用缓存记录判业务幂等？更新路径是否遵循"一锁（按幂等约束取悲观锁）二判（检查加锁记录状态）三更新（再执行业务更新）"？切流/迁移期间是否跨系统全局幂等（失效机理见图 5-7 插图转录：处理成功的回执因网络抖动丢失→切流开关翻转→门户以同一单号重试被路由到新系统→新系统库查无该单号记录、幂等校验失效，再次处理成功即重复提现）？操作：唯一键写入包进业务事务；下游补幂等或去重；后端补幂等校验（前端防重只能算体验优化）；缓存仅用于拦截流量、业务终态以数据库为准；提供方记录每次请求与结果、对同一请求返回相同终态并提供专门幂等错误码（如 REPEAT REQUEST），调用方识别后转主动查询而非更换单号重试。验证：线程池并发提交同一笔请求 N 次，断言成功单据数=1（配合 p9-self-test-quality 的并发自测）；重放历史请求无新增副作用；跨天/跨时区时刻构造重试用例；切流演练——模拟"系统 A 处理成功但回执因网络抖动未达门户"，开关翻转到 B 后以同一单号重试，断言 B 侧幂等拦截、全局成功单据数=1（图 5-7 插图转录步骤链固化为用例）。
5. **[B] 错误码三态映射审查**。判断条件：该返回码是否明确表示业务成功/业务失败？Request_Failed 是否只是系统交互失败（对方可能同步受理、异步处理）？网络超时是否无法区分"未到达"与"已成功但回包丢失"？查询返回 TRANSACTION_NOT_FOUND 是否可能因对方事务未提交？操作：只有明确业务成功/失败才映射对应终态，其余一律置"未知"并进入补偿流程；建立错误码管理体系——定期巡检未知码并更新映射，映射变更走审批并留痕；同码不同义（如"余额不足"有的表示订单流出失败、有的会自动重试）必须逐渠道对焦语义。验证：全量码表过一遍三态映射表，无任何"交互失败/超时/查无"直接置失败的路径；未知态单据均有后续流转出口。
6. **[B] 推/拉补偿对齐**。拉模式三情况：查询异常 → 无明确结果，继续查询；返回空结果（请求在途/对方未写入/事务未提交）→ 继续查询；返回明确结果 → 流转单据状态（结果须明确且提供方承担法律责任，纳入 SLA/合同）。推模式（SPI 异步通知）：通知结果明确 + 法律责任入 SLA；调用方做幂等控制与状态机控制，**终态锁定不可再变更**（对方先通知失败又通知成功属对方故障，记录统计并反馈修复）。验证：终态单据重放通知不再变更状态；按表 5-1 推演各场景窗口内错配——"我方成功/机构失败"方向为红线，严禁出现。
7. **[B] SLA 窗口与人工补救**。时间窗口是资金安全与用户体验的权衡（窗口大损体验、窗口小增资损），从提供方取得的 SLA 承诺须有法律效力并落地两条处置：超窗仍查不到状态 → 置失败；超窗才送达的通知 → 拒绝处理并置失败。人工补救两原则：不绕过核心模型直接改单据（防领域模型风险校验失效）；先改我方单据状态、再执行人工打款等外部操作（防系统重试再次处理）。验证：订正后触发系统重试不产生第二次处理；超窗处置规则在联调环境演练通过。

**输入契约**：排障场景必需 = 故障单据样本（含幂等字段值、请求/重试日志、对方错误码原文）+ 幂等实现方式描述（字段来源、存储结构、控制逻辑位置）；设计评审场景必需 = 待评审的幂等设计（字段/存储/逻辑三层）与外部接口的错误码码表。错误码原文或码表缺失时，先向提供方索取并逐码对焦语义，不得凭猜测映射。
**输出契约**：排障报告（症状类别 → 失效维度 → 根因 → 修复动作 → 验证结果）；设计评审输出三维审查清单逐项结论（通过/缺陷/修复建议）；错误码三态映射表（错误码 → 成功/失败/未知 → 后续动作）；（涉及外部方时）契约修订/SLA 条款建议清单。
**判停点**：步骤 2～4 全部通过仍复现重复处理 → 核查是否跨系统幂等域（切流/FailOver 双写）或依赖链非幂等（传递性），转相应相邻能力场景；步骤 5 对方无法提供语义明确的码表 → 全部按未知处理并将问题升级到契约/商务层（SLA），技术层不得硬造终态；步骤 6 时间窗口无法与对方谈定 → 不得单方面压缩窗口，标记为未决风险并暴露给业务方决策。

## B（边界）

**反场景（何时不用）**：
- 强一致性要求的业务场景不能套"最终一致+补偿"思路（属 5.3 分布式事务的规则，见相邻能力 p9-dist-tx-cache）；
- 内部同构系统调用可简化推拉与 SLA 机制，但"对焦清楚错误码业务语义"这条不可省；
- 单体、无重试、无并发诉求的内部逻辑，不必全套悲观锁序列——但注意原书立场：**即便场景简单且低频，也应遵循一锁二判三更新，不能抱侥幸心理**，所以"低频"不是跳过的理由，只有"真的不存在重复触发路径"才是。

**书中警告的失败模式（幂等失效事故组，ce040–ce051）**：
- ce042 短号：截取 Sequence 后 8 位，量增后必重复，延迟引爆的容量型缺陷；
- ce043 跨天：日期+序号在重试跨天（差 1 秒跨日）、时区、时钟不同步时分裂出新"唯一"值；
- ce044 擅自加工：契约未约定就自行拼接（requestId+文件名日期），对方规则一变即失效且责任说不清；
- ce045 唯一索引失效：索引未建或被迁移破坏，低并发测不出，高并发爆发；"先查后插"存在竞态窗口，唯一索引才是最终防线；
- ce046 分片不单点：可变分库键（年龄）使同一幂等值落入不同分片，分片内各自唯一、全局重复；
- ce047 前端防重替代后端幂等：请求可模拟构造、并发绕过，网络抖动也会击穿；
- ce048 低频侥幸：以"场景低频"为由省略一锁二判三更新，无锁 check-then-act 被重试穿透只是时间问题；
- ce049 切流跨系统：A/B 两套系统各有独立库，单号唯一性只在单系统内成立，切流把重试路由进另一个"幂等域"；
- ce050 缓存判业务幂等：缓存记录只代表"请求曾到达"，机器宕机后重试被拦截，该请求永远无法处理；
- ce051 终态不保存/幂等码不识别：同一单号先失败后成功，用户感知与实际不一致；无专用幂等错误码导致盲目换单号重试、卡单无法恢复。

**书中警告的失败模式（错误码事故组，ce052–ce059）**：
- ce052 交互结果当业务结果：Request_Failed 直接置 FAIL，异步处理的机构最终成功，重复到账；
- ce053 网络超时映射失败：无法区分在途位置就下失败结论，双方状态不一致；
- ce054 查无此交易映射失败：对方事务未提交时查不到，最终却成功；
- ce055 同码不同义：不同机构同一错误码语义相反，未逐渠道对焦；
- ce056 绕过核心模型改单据：后台直改状态使领域模型风险校验失效；
- ce057 先打款后改状态：人工应急后系统重试再打一次；
- ce058 窗口失衡：只压窗口不评估资金方向，或只迁就体验放大资损风险；
- ce059 无巡检无审批：未知码无人巡检、映射随意变更，防线静默失效。

**作者盲点/时代局限**：
- 全部案例与"SLA 具有法律效力、纳入商业合同"的手段来自蚂蚁国际支付语境；对接强势第三方时小团队可能拿不到合同级 SLA，只能退化为内部约定超窗时间并在 B 段显式标注风险；
- 错误码三态映射的维护成本（码表混乱的对手方、巡检人力）未讨论，长尾机构码表失控时"一律未知"会推高未知单量，需要配套运营流程；
- 原书未给出幂等字段的替代生成方案（如全局唯一 ID/雪花算法），只给了"必须唯一稳定"的约束，选型时需另行引入外部知识并标注来源。
