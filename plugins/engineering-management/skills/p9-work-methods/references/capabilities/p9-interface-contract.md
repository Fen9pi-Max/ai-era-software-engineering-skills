# 接口契约设计与落地

## R（原文摘引）

> "从实践经验上，接口契约具有两个重要的价值：研发解耦和质量栅栏。"（第2章 2.3.1）

> "端到端联调测试是非常耗费精力的过程，在大型项目研发中通常需要占据 15%~20% 的精力。然而，有了接口契约的约定……不再需要进行联调测试。"（第2章 2.3.1）

> "接口契约的主要作用是，明确服务提供方和服务调用方之间的权责关系，并就此达成共识。"（第2章 2.3.3 存量接口还原事实）

> "它们没有明确区分成功是指业务处理成功还是系统交互的成功，这是导致严重生产环境故障的根本原因。在同步受理而异步处理的接口中，返回的 S 状态通常仅表示系统交互成功。"（第2章 2.3.3）

> "尽管大家都将从接口契约（公地）中受益，但个人却不愿承担相应的代价。"（第2章 2.3.2 公地悲剧）

> "提供一个统一的空间来存放接口契约文档，建立明确的接口契约发布机制及其纠正和更新机制。"（第2章 2.3.3 统一管理）

## I（解释）

接口契约不是"更详细的接口注释"，而是跨团队之间的行为约束与权责约定：提供方承诺什么、调用方必须遵守什么、出问题谁负责。它解决大系统协作的两个经济问题：一是**研发解耦**——契约定清后双方按各自节奏开发、无须互相等待，配合报文样例可互相 mock，端到端联调（书中口径：占大型项目 15%~20% 精力）可以被契约测试替代；二是**质量栅栏**——针对契约的入参/出参/错误码建立契约测试用例，规定输入必须得到契约规定的结果，让运行多年的旧代码"敢重构"、快速甩掉技术负债。

实施策略是"控制新增 + 治理存量"两线并行：存量接口只**还原事实**——记录提供方当前实际承诺的行为与调用方须遵守的规范，不纠结合理性、不趁机重设计（纠结合理性是推行失败的常见误解）；新增接口按三要点**立好规则**：① 字段说明无二义（业务语义/必填/长度/取值范围/字段间关系）；② 业务处理结果结构体明确——核心是区分"业务处理成功"与"系统交互成功"，如支付 S/F/U 三态各配处理动作；③ 请求/响应报文完整样例支撑双方 mock。最后用统一空间 + 发布机制 + 纠错更新机制持续管理，对抗破窗效应。

推行要跨三道坎（书中三大难点）：认知缺失（习惯联调兜底）、显性投入过高（旧接口审查成本看得见，会议/排障成本隐性）、公地悲剧（个人用扩展参数绕过契约省事，公地逐渐失真）——契约推广必须提供方定义 + 调用方反馈双向共建，任何单方面努力都是徒劳。

## A1（原书案例 / 合成演练）

**案例一：电商购物 8 系统 11 接口的联调成本推演（worked_example，第2章 2.3.1 图2-10）**。输入：从用户注册→登录→商品购买→交易下单→收银台→风控→支付的简化链路。计算：涉及 8 个系统、11 次接口交互，每个接口使用细节确认按 3 人日计，全链路确认成本 = 11 × 3 = 33 人日；且每次端到端联调要 8 个系统同环境稳定、8 组技术人员在线保障数据正确。外推：真实交易链路（交易前后台、多收银台、账务/清算/计费）近 100 个系统、接口成百上千。结论：无契约时对焦会议与联调成本不可承受（成本推演，未说明项目结果）。

**案例二：JDK 文档是接口契约的楷模（worked_example，第2章 2.3.2 图2-11）**。输入：JDK 20 String.format 官方文档。执行：拆解其契约结构——整体效果说明、Parameters（入参逐一说明填写规范）、Returns（出参描述）、Throws（已知异常及调用方处理义务）、Since（版本适用范围）。结论：契约不是新概念，学 Java 查 JDK 文档就是每天在消费契约；难的是把日常每个接口写到这种无二义程度。

**案例三：支付接口契约的 S/F/U 处理表（worked_example，第2章 2.3.3 图2-12~2-16）**。输入：pay 接口契约文档。执行：paymentRequestId 字段标注"最大 128 字符、用于业务幂等，重复提交视为同一请求"；result.resultStatus 处理表——S=支付成功→更新 ACQP 侧状态；F=失败→按 resultCode 分流处理；U+PAYMENT_IN_PROCESS→调 inquiryPayment 查询（60 秒内可查 5~10 次）；U+其他值→未知→用相同 paymentRequestId 重试；另附完整请求/响应报文样例。结论：同步受理异步处理的接口中，S 可能仅表示系统交互成功而非业务成功——契约不写清即成生产故障隐患。

**案例四：AlipayPlus 官网统一管理契约（reported_case，第2章 2.3.3）**。输入：蚂蚁 AlipayPlus 对外服务的契约文档体系。执行：提供统一空间存放契约文档，建立明确的发布机制与纠正更新机制。结果：该机制在 AlipayPlus 持续运作，书中作为正面范例——契约是每代维护者都要接力的持续性工程，不需要建独立系统承载。

## A2（情境应用）

**触发场景**：
- 一个需求要跨多个团队/系统协作开发，接口定义与双方权责还没敲定；
- 存量系统只有代码注释没有契约文档，每次改动都要深读代码、对焦会议和联调排障人日持续走高；
- 上下游对"成功"语义起争议：接口返回 SUCCESS 但业务并没有成功，或调用方把"受理成功"当"业务终态"；
- 端到端联调窗口成为发布瓶颈，想砍掉联调、双方并行开发；
- 想重构旧接口但"没人敢动"，需要先建立行为保护网。

**语言信号**：
- 中文：接口契约、接口文档、接口对接、联调测试、错误码定义、状态码语义、幂等字段、存量接口治理
- 英文：API contract, contract testing, consumer-driven contract, integration testing cost, error code specification, idempotency key, result status handling

**与相邻能力的区分**（初稿）：
- 与 p9-system-analysis：系分评审要"先厘清架构边界（尤其接口契约）"，系分消费契约结论；本能力负责契约的制定、存量治理与契约测试化。
- 与 p9-clean-code 第七步（协作界面/DSL）：后者关注 API 形态对调用方友好（易用性）；本能力关注跨团队权责、结果语义（S/F/U）与测试栅栏，且有跨团队规模门槛。
- 与错误码处理能力（第5章 5.2）：本能力定义契约中错误码/状态语义怎么写、调用方怎么响应；系统内错误码分类与异构数据一致性走第5章。
- 与自测用例能力（第4章）：契约测试是围绕契约入参/出参/错误码的守门用例；研发自测体系（用户故事验证、灰犀牛防治）归第4章。

## E（可执行步骤）

1. **门槛判断：该不该上正式契约**。判据（满足越多越必要）：跨团队/跨系统协作；交互链路复杂且长期演进；系统已传承多代、无对外文档；端到端联调占用大量精力（参照 15%~20% 口径）。完成标准：输出"做/不做"的书面结论。**判停点：单一团队内部、短生命周期、链路简单清晰的接口 → 不做正式契约**，接口注释 + 快速沟通足够（书中 2.3.1 口径）。

2. **存量接口：还原事实**。对每个存量接口，以代码与线上报文为准，记录提供方当前实际承诺的行为（入参约束/返回结构/异常与幂等语义）+ 调用方须遵守的规范，照实写、不评判合理性、不趁机重设计。完成标准：契约描述与实际行为一致（能对着一笔线上报文逐字段核对）；**判停点：梳理会演变成接口重设计争论（ce030 信号）→ 立即拉回"只记事实"**，优化诉求另行立项。

3. **新增/升级接口：三要点立规则**。① 字段说明无二义：每个参数写明业务语义、是否必填、类型与长度/取值范围、字段间逻辑关系（参照 paymentRequestId：最大 128 字符、用于幂等、重复提交视为同一请求）；② 业务处理结果结构体：明确区分"业务处理成功"与"系统交互成功"，输出状态处理表——S（成功→调用方动作）/ F（失败→按错误码分流）/ U（未知→查证或同号重试，写明查询接口、次数与时间窗）；同步受理异步处理的接口必须注明 S 的确切语义；③ 调用样例：完整请求/响应报文示例，双方可据此 mock 解耦。完成标准：三要点齐备；状态处理表每行为"状态→语义→调用方动作"三元组；样例报文可直接复制用于 mock。

4. **契约测试建质量栅栏**。针对契约定义的入参、出参、错误码设计测试用例：规定的输入必须得到契约规定的结果；提供方以此守护行为不变，调用方以此验证用法正确。完成标准：契约测试覆盖全部状态分支（S/F/U 全覆盖，U 的两类处理——查证与同号重试——都要有）；重构前跑通基线、重构后全绿，以此作为"敢重构"的凭据。

5. **统一管理对抗破窗**。统一空间存放契约文档 + 发布机制（接口变更如何通知调用方）+ 纠错更新机制（发现文档与行为不一致如何修）；任何接口改动必须过"是否升级契约→是否更新文档"检查，禁止用扩展参数传递本应是字段的信息来绕过契约。完成标准：每个契约有唯一权威版本入口；变更留有通知记录；"契约文档与实际行为长期不一致"（ce028 信号）列为治理红线，出现即登记修复。

**推行对策（贯穿步骤 2~5，对应书中三难点）**：认知缺失 → 用第 1 步的联调成本账（33 人日推演 + 自家联调人日）向提供方与调用方共讲；显性投入过高 → 从新增接口立规则起步、存量分批治理，把隐性成本（对焦会议/排障/应急人日）与契约投入显性对比；公地悲剧 → 把契约更新纳入接口变更流程（绕过契约的改动不予合入），坚持提供方定义 + 调用方反馈的双向循环。**判停点：调用方拒绝参与反馈循环（只剩单方面推动）→ 暂停推行，先在双方管理层达成共建共识**——书中明示单方面努力徒劳；未达规模效应前不强行"去联调"，保留联调作过渡验证。

**输入契约**：必需 = 接口清单（存量 + 新增）及每个接口的提供方/调用方归属；存量接口需可获取实际行为证据（源码 / 线上报文样例 / 调用日志——三者皆无 → 先做行为还原采集，不凭记忆写契约）。可选 = 既有接口文档、组织错误码规范、mock/契约测试工具链。

**输出契约**：每接口一份契约文档（三要件：无二义字段说明表、S/F/U 状态处理表、请求/响应报文样例）+ 契约测试用例集（状态分支全覆盖）+ 统一管理机制说明（存放空间/发布流程/纠错流程）。完成标准：第三方工程师仅凭契约文档（不看源码）能正确调用接口并正确处理全部返回状态。

## B（边界）

**反场景（何时不用）**：
- 规模较小、链路简单清晰且稳定的系统——接口注释 + 快速沟通足够，强行契约化是过度工程（书中 2.3.1 明示此口径）；
- 单团队内部的模块边界与函数级设计——那是 p9-clean-code 协作界面（DSL/易用性）的问题；
- 未跨过规模效应前追求立即"去联调"——书中承认未达足够规模前契约作用有限，谨慎方仍会联调，应渐进过渡；
- 探索期随时会废弃的接口——先轻量记录，稳定后再立契约。

**书中警告的失败模式（含候选反例 id）**：
- ce026 契约认知缺失：习惯全链路端到端联调兜底、认为接口注释够用，契约文档缺位；系统传承数代后每次改动都要深读代码，难度和风险剧增；
- ce027 显性投入引发抵触：使用旧接口需全面审查历史情况，项目组难以接受看得见的成本，推行半途而废——分析工作并未消失，只是转移到会议、排障甚至生产故障应急中；
- ce028 公地悲剧：小改动用扩展参数、加条件判断就能绕过契约升级，个人省事、契约（公地）逐渐失真，无强制机制时渐进污染，最终回到无契约状态（破窗效应）；
- ce029 S 状态语义混淆：契约不区分"业务处理成功"与"系统交互成功"，调用方把 S 当业务终态直接推进业务，同步受理异步处理场景下成为严重生产故障的根源（书中多处资损事故的共同根因）；
- ce030 存量治理纠结合理性：把"记录事实"做成"接口重设计"，梳理会议变成 redesign 争论，治理成本成倍放大、迟迟无法落笔。

**作者盲点/时代局限**（阶段 0 批判）：
- 收益论证基于蚂蚁近 100 系统的交易链路与 AlipayPlus 对多商户服务的场景，契约的规模收益在小团队、短链路上不成立——方法源自大厂支付语境，移植需按组织规模与基建水平降配；
- 2.3.2 三大难点有诊断无组织级推行 SOP（候选 f022 已登记 missing_condition），第 5 步的管理机制（空间/发布/纠错）需按团队治理结构自行落地，书中未给模板；
- 未讨论契约版本化与兼容性策略细节（字段废弃流程、多版本并存治理），对照 JDK 文档的 Since 机制只点到为止；"去联调测试"结论以配套契约测试与 mock 能力为隐含前提，缺基建的团队不能直接照搬。
