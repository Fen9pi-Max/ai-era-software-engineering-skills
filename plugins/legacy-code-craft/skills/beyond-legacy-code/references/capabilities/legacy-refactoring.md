# 重构遗留代码:安全下手的程序

## R — 原文 (Reading)

> 在软件行业，我们不应该将遗留代码视为定时炸弹，而是地雷。如果代码正常工作，不需要修改或升级，就不要动它。……让每一个改动都分为两步。第一步重构想要扩展的代码，让它可以容纳新功能。这并非添加功能……接下来的一步是增强阶段。先编写失败测试描述要实现的新功能，然后添加功能让测试通过。
>
> —— David Scott Bernstein,《修改软件的艺术》第13章·实践9

## I — 方法论骨架 (Interpretation)

遗留代码(无测试、难修改)的第一原则是**地雷原则:不碰不需要修改的代码**——重构有成本,
只在收益覆盖风险时动手(触发时机:修 bug/加功能/关键代码成累赘/唯一懂的人要离开/有更好设计的信息/重构比重写容易)。
要动时,安全 = **先建防护网再动刀**:①图钉测试(粗粒度锁定端到端行为,每次改动后回验)→
②依赖注入解耦对象与服务(注入模拟→可单独测)→③更细粒度单元测试→④此时才可做复杂重构。
大粒度替换用**系统扼杀**(新接口包老服务→逐块替换→老服务剩外壳)与**抽象分支**
(提取接口+新旧实现并存+功能开关切换,消除版本分支);纠缠过深用天皇法则(Mikado)。
**加新功能 = 开闭原则两步法**:步骤1只重构不加功能(为扩展造空间,测试保护下安全);
步骤2只添加代码(TDD 实现新功能,现码零/最小修改);两步禁合一。
经济学论证话术(对管理层):重构降低四类成本(日后理解/加测试/容纳新功能/日后重构);
技术债=信用卡债,利息复利——只还最低额,1.7万美元要93年/18.4万;做"铁公鸡",
尽快偿清几乎总是对的;例外仅限"确实不是时机/不知如何下手/没时间",且过后要连本带息还。

## A1 — 书中的应用 (Past Application)

### 案例 1: 财务公司的资产观对话(第13章 13.1,作者亲历 firsthand)
- **输入**: 顶级财务公司:顶尖合同工做完一期即撤,初级接手强改,遗留代码一团糟
- **方法执行**: 作者设问:"你们撤走基金经理吗?"——"不会,市场瞬息万变要持续调整"→"那为何这样对待软件资产?"
- **结论**: "软件也是一种关键资产,和其他资产一样需要维护"(奔驰也要保养;倒车档坏了不会一直忍着)
- **结果**: 管理层认知转变(会议结论);后续工程结果未说明

### 案例 2: 1.7 万美元的信用卡债(第13章 13.2,作者亲历转述 firsthand)
- **输入**: 作者自述是"铁公鸡"(账单即全额还款,信用卡公司最讨厌);认识的人欠 1.7 万美元
- **方法执行**: 核算:只还最低还款额→需 93 年、共 18.4 万美元
- **结论**: 技术债同理:开发者每次撞上同一处债都付代价;无视不会让债消失
- **结果**: 类比论证成立;"先付几个月最低额渡难关,再连本带息还清"与"装作相安无事"有本质差别

### 案例 3: 高效团队一半时间在重构(第13章 13.9.1,作者观察)
- **输入**: "重构是负担还是投资"的常见质疑
- **方法执行**: 观察:高效的开发团队可能花费一半时间重构,同时优化设计、提高健壮性
- **结论**: 代码被读的次数是写的十倍以上,清理投入很快回本;重构也是学习现有代码库的最佳方式,
  精通后进入"前构"(一开始就写对)
- **结果**: 经验主张(引用 Ken Pugh《前构》)

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 要给一段没人敢动的老代码加功能/修 bug,不知道怎么安全下手
2. 团队吵"重构还是重写",需要决策依据
3. 想说服管理层批准专门的重构时间(迭代内无新功能)
4. 大模块/老系统要渐进替换,考虑绞杀者模式或分支策略

### 语言信号

- "怎么重构遗留代码 / 没测试的老代码怎么改"
- "不敢动的代码 / 祖传代码怎么办"
- "重构还是重写 / rewrite or refactor"
- "技术债怎么还 / 怎么跟老板要重构时间"
- "strangler pattern / 图钉测试 / pinning test / branch by abstraction"
- "加新功能前要先怎么准备"

### 与相邻能力的区分

- 与 `clean-code-qualities` 的区别: 那里诊断"哪里不好";这里给"在无防护的老代码上安全动手的**程序**"——先建网再动刀
- 与 `design-last` 的区别: 那里是新代码的增量设计;这里是存量代码的抢救,多出图钉测试/扼杀/抽象分支等专门技法
- 与 `test-first-tdd` 的区别: TDD 前提是能测;遗留代码先要"创造可测间隙"(Feathers 技巧),再回到 TDD 节奏

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- 让 agent 批量重构/迁移祖传模块,担心改坏了没人发现——"先建防护网再动刀"的程序直接构成 agent 批量重构的安全门。触发句式: "让 AI 重构这块祖传代码安全吗 / agent 批量迁移老模块前要做什么"
- 无测试的老代码要 agent 修 bug/加功能,改完无法验证行为没变——图钉测试流程先行。触发句式: "没测试的老代码敢让 AI 改吗 / 怎么确认 agent 没改坏老逻辑"

## E — 可执行步骤 (Execution)

**输入契约**: 目标代码的位置与修改动机(修 bug/加功能/改行为/清理),及其当前测试状况(通常:无)。必需:明确的修改需求——无修改需求时输出"不动"(地雷原则),这本身是合法结论。

**步骤**:

1. **决策:动不动**(判停点)
   对照触发条件:修 bug/加功能/关键代码成累赘/唯一维护者将离开/有更好设计信息/重构比重写容易?
   全否→**不动**("东西没坏就别修"),输出风险提示即结束。
   完成标准: 有书面"动/不动"结论及触发条件对应项。
2. **图钉测试**
   从功能层选定可观察行为(输出/接口响应),写粗粒度测试锁定当前行为(哪怕行为本身可疑也先锁,改造后再论)。
   完成标准: 每次修改后可一键回验;记录被锁行为清单。
3. **创造可测间隙(依赖注入)**
   找出对依赖(时钟/DB/服务)的直接调用,提取接口注入;用模拟替代后,目标单元可独立运行。
   完成标准: 至少目标修改区域内依赖可注入;更细单元测试可以开始写。
4. **选定粒度策略**
   改动局部→继续单元级重构;替换整个组件/子系统→**系统扼杀**(新接口包旧实现→新客户端走新接口→逐块实现新逻辑→旧壳只剩转发);主干上大改且不能停摆→**抽象分支**(提取接口+新旧并存+功能开关切换);依赖纠缠到无从下手→**天皇法则**(预演依赖图,自叶节点逆向回滚)。
   完成标准: 策略与改动范围匹配;全程系统可用。
5. **加功能:开闭两步法**
   步骤1(重构期):只为新功能**造空间**(加抽象/接口/工厂),行为零变化,图钉+单元测试保持绿。
   完成标准: 步骤1结束时无任何新功能代码进入。
   步骤2(增强期):TDD 实现新功能——先写失败测试,再**只添加**代码让测试通过;现有代码修改最小化。
   完成标准: 两步分别提交,各自可回滚;最后重构新代码。
6. **还债与管理层沟通**
   需要专门迭代时,用商务话术:重构降低四类成本(理解/测试/新功能/再重构);技术债利息类比;
   提议固定比例(如书中开篇团队 20%)清理时间。
   完成标准: 申请包含"不重构的成本"对照,而非"代码好烂"的情绪表达。

**输出契约**: 动/不动决议+被锁行为清单+间隙改造点+策略选择与理由+两步执行计划(步骤1/步骤2 分列,含各自验证方式)。

**AI 编程适配要点**(AI 适配,非原书):

1. 硬门: agent 大规模重构的前置条件是图钉测试(行为锁定测试)已存在且全绿;无安全网时 agent 会话的第一任务是补图钉测试并跑绿,不是改实现
2. 开闭两步法拆成两个 agent 会话/两串提交: 会话1只重构造空间(行为零变化、图钉测试保持绿),会话2只加功能(TDD);两步混在一个 diff 即打回
3. 动刀前让 agent 先交计划: 动/不动决议+被锁行为清单+依赖注入点+回滚方式,人批准后执行;每轮改动后跑全量图钉+回归,绿才继续
4. 超范围即打回: agent 会话引入新依赖、删除公共接口、触碰任务区域外的代码,均视为越界——即使"顺手改进"也不接受
5. 系统扼杀/抽象分支由 agent 执行时,人核对切换点与功能开关位置,新旧行为等价性靠图钉测试对账,而非逐行人审新实现

## B — 边界 (Boundary)

- **不适用于**: 正常运行且无修改需求的代码——地雷原则优先,重构不是道德义务;预算/工期下的战略性搁置合法,但要记账(技术债清单),不是装作不存在。
- 图钉测试锁的是**当前**行为,包括当前的 bug——锁定≠认可;改造完成后应回访"这些行为本身要不要改"。
- "重构还是重写":书中立场几乎总偏好渐进;但承认极端情况(如 24GB 案例)必须重写——判断依据是验证成本是否已结构性失控,不是情绪。
- 系统扼杀/抽象分支源自 Fowler(2004/2014);与当代渐进交付(灰度/流量切换)叠加使用时注意双写一致性问题(超出本书范围)。
- 作者的"一半时间在重构"是高效团队观察值,不是配额指标;照搬成 KPI 会本末倒置。
- 100%不动 vs 100%重写之间存在连续谱;本能力给的触发条件是判断起点,不是机械规则。
- **AI 场景边界**(AI 适配,非原书): 绝不让 agent 在无测试保护下"顺手大规模重构"——agent 的生成速度会放大破坏面,一个会话重写整个模块等于把小批次/图钉/两步法全部作废;重构还是重写的决策留在人手里(判据是验证成本),agent 只执行既定程序。

## 相关能力

- 依赖(depends-on): `clean-code-qualities`(知道"好"才知重构方向)、`test-first-tdd`(间隙建好后回到 TDD 节奏)
- 组合(composes-with): `continuous-integration`(抽象分支依赖主干+功能开关;重构期靠构建守护)、`design-last`(两步法的步骤1即其重构技法)
- 对比(contrasts-with): `test-first-tdd`(防护网已存在 vs 需要先造防护网)
