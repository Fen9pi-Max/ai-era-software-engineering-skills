# 持续集成:项目的心跳

## R — 原文 (Reading)

> 我把持续集成当作项目的心跳。它在后台运行，而且永不停息。它是自动的……应该自动运行。……在软件开发的所有关键概念中，持续集成最为重要。它为所有其他技术实践提供了框架和条件。有意思的是，它也最容易实现。
>
> —— David Scott Bernstein,《修改软件的艺术》第7章·实践3

## I — 方法论骨架 (Interpretation)

集成痛苦的处理方式只有两种:推迟它(瀑布,痛苦复利)或**切碎它**(持续集成,每次一小点,痛感趋零)。
CI 是基础设施而非仪式,四要素缺一不可:①**版本库管理一切**——不只是源码;构建脚本、配置、数据库模型、
测试代码、第三方库、安装脚本全进版本库,否则测试环境与生产不一致的 bug 只在部署后出现;
②**一键自动构建**——本地秒级、服务器分钟级,上限10分钟,超时按依赖裁剪测试范围;
③**主干+功能开关**——所有人在同一分支,未完成功能用开关隐藏;按团队开发分支、年末合并=仍是瀑布;
④**失败即修**——构建失败灯亮,责任人立即修复或回滚,"不允许失败的构建"。
配套判定:完成三层次——完成(本机能跑)<完整完成(已集成,风险清零)<完美完成(集成+清晰+健壮);
作者说"完成"一律指完美完成。CI≠持续部署:"可以随时发布"是工程状态,是否发布是商业决定。

## A1 — 书中的应用 (Past Application)

### 案例 1: 版本库没管构建脚本的互联网巨头(第7章 7.3,作者亲历 firsthand)
- **输入**: 某互联网巨头团队:手工测试通过,部署到生产后却出现测试中没见过的 bug
- **方法执行**: 作者问"构建脚本、存储过程、DB模型也进版本库了吧?"——学员离场核查:确实没有
- **结论**: 不一致构建的根因是版本库范围不完整
- **结果**: 数月后来信确认根因;测试环境完整复制生产,以 1% 流量渐进导入数据中心部署(替代三周手工周期)

### 案例 2: 消防头盔构建服务器(第7章 7.4,作者亲历 firsthand)
- **输入**: 作者拜访一个 XP 团队,角落里有闪烁红灯的大功率设备+一顶消防头盔
- **方法执行**: 朋友故意让构建失败→灯灭、警报响、红灯闪;"在我们这里不允许有失败的构建"
- **结论**: 可用构建=团队公共资产;失败=全员可见的紧急事件,责任人戴上消防头盔去修
- **结果**: 团队高度成功,文化常态化

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 集成/联调阶段 bug 爆炸,团队发布前加班救火
2. 团队按功能分支开发,合并周痛苦不堪,考虑要不要继续分支
3. 搭建或改造构建流水线,问"该把什么放进版本库、构建多快才算健康"
4. 讨论"做完"的定义:代码写完但没集成算完成吗

### 语言信号

- "集成太痛了 / 合并冲突地狱 / 发布前总要救火两周"
- "要不要用分支 / feature branch 还是主干开发 / 功能开关怎么用"
- "构建要多快 / 十分钟构建 / 构建失败怎么办"
- "done 的定义 / 什么叫真正完成 / definition of done"
- "continuous integration / trunk-based / feature flags / build server"

### 与相邻能力的区分

- 与 `small-batches` 的区别: 那里把任务**拆小**,这里保证小任务**完成即集成**——拆小不集成,风险照旧在累积
- 与 `test-first-tdd` 的区别: TDD 是开发者本地的反馈回路(秒级);CI 是全项目级的反馈回路(分钟级),后者承载前者产出的测试
- 与 DevOps 工具咨询的区别: 本能力是**机制检查单**(什么进版本库/多快/失败怎么办),不绑定 Jenkins/GitHub Actions 等具体工具选型

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- agent 生成的代码要不要直接合入主干、怎么防止带病合入——CI 四要素(版本库/一键构建/主干+功能开关/失败即修)直接构成 agent 产出的准入门禁。触发句式: "AI 生成的代码要不要先跑测试再合 / agent 的提交怎么管"
- agent 声称"改完了",人无法快速核验它真干完了——"完成=完整集成"判级直接适用。触发句式: "agent 说做完了可信吗 / 怎么验证 agent 的活真的完成"

## E — 可执行步骤 (Execution)

**输入契约**: 团队现状描述(版本库范围、构建方式与时长、集成频率、分支策略)。缺失项按"未做"处理并列入缺口清单,不假设。

**步骤**:

1. **盘点版本库范围**
   逐项核对:源码/构建脚本/配置文件/数据库模型与迁移/测试代码与数据/第三方依赖声明/安装部署脚本/相关文档。
   完成标准: "构建所依赖的一切"逐项有"在库/不在库"结论;不在库项列整改清单。
2. **一键构建**
   目标:一条命令(或一次推送)触发 编译→测试→打包;本地构建秒级、服务器构建分钟级、硬上限10分钟。
   完成标准: 无人工步骤;超时即触发"按依赖裁剪测试"或"拆解耦合"行动项。
3. **主干开发+功能开关**(判停点)
   检查:是否存在长生命周期团队分支?是→迁移方案=主干+未完成功能用功能开关隐藏,分支仅留发布需要。
   完成标准: 所有代码每天至少一次进入主干构建。
4. **失败响应约定**
   约定:构建失败→责任人立即修复或回滚;期间他人可继续工作但不得再推。
   完成标准: 有可见的失败信号(通知/灯/徽章);平均修复时间被团队知晓。
5. **完成判级**
   对每个交付项问:本机可跑?已集成?清晰健壮?——三问全过才是"完美完成"。
   完成标准: 团队的 DoD 写明"完整集成+通过自动化测试"为完成底线。

**输出契约**: 版本库范围核对表+构建时长基线与目标+分支策略决议+失败响应约定+DoD 条款。

**AI 编程适配要点**(AI 适配,非原书):

1. agent 会话的 DoD 写死为: 全量构建绿+测试集绿+已合入主干;"agent 说做完了"不构成完成证据,CI 结果才是
2. agent 产出走与人类相同的门禁(同一构建、同一测试集),不给 AI 开旁路;构建被 agent 提交弄红即回滚该提交,禁止 agent 在红条上继续叠改
3. 未审完的 agent 功能用功能开关隐藏后合入主干,审查通过再开开关——避免长存活 agent 分支
4. agent 修改构建脚本/配置/数据库迁移时,改动必须与代码同库同提交——"版本库管理构建所需的一切"对 agent 同样是硬约束

## B — 边界 (Boundary)

- **不适用于**: 无法自动化验证的部分(如 GPS 实地路测)——书中口径:把这类依赖隔离出关键路径再模拟,而非放弃 CI。
- "避免分支"是 XP 主干开发立场(2015);当代发布分支/GitLab flow 等有正当场景,冲突时以"分支存活时长与集成频率"为判据,不教条禁分支。
- 持续集成≠必须持续部署;发布节奏由商业决定。
- 构建时长10分钟上限引 Shore & Warden《敏捷开发的艺术》,是经验阈值而非定律。
- 工具选型(Jenkins/GitLab/GitHub Actions)与容器化等当代实践超出本书范围,本能力只给机制检查单。
- **AI 场景边界**(AI 适配,非原书): CI 绿 ≠ 可免人审——构建与测试通过只对应"完整完成";agent 代码的行为正确性与设计质量仍须人审(完美完成=集成+清晰+健壮)。也不得以"agent 改动小/置信度高"为由豁免门禁,小改动聚合起来就是大批次。

## 相关能力

- 组合(composes-with): `test-first-tdd`(CI 承载其测试产物)、`small-batches`(完成即集成是拆小的闭环)、`user-story-first`(自动化验收标准挂入构建)
- 依赖(depends-on): 无(作者定位:最易实现,应最先建立;也是其他实践的基础设施)
- 对比(contrasts-with): `legacy-refactoring` 中的抽象分支——用接口+功能开关在主干上做大改动,是本能力"避免分支"在遗留场景的延伸
