# 测试先行:红绿重构循环

## R — 原文 (Reading)

> 测试驱动开发有三个独立的阶段。我们称之为红条、绿条、重构……最开始编写测试的时候还没有可以测试的代码。……接下来需要做的是为产品代码做"存根"，好让测试通过编译。……这时对红条的观察就是对测试的测试。测试是允许失败的，这点非常重要，因为测试不可失败比没有测试还要糟糕。
>
> —— David Scott Bernstein,《修改软件的艺术》第10/11章·实践6

## I — 方法论骨架 (Interpretation)

TDD 的正确打开方式是**用测试定义行为,而不是验证代码**。先写的"测试"其实是**假设**(对需求理解的假设),
实现通过后它才变成持续增值的回归测试(像引擎灯一样的传感器)。循环五拍:
①为下一个意图写一个测试(此刻无物可测,甚至不能编译);②生成存根(空类/空方法返回假值)让测试可编译;
③运行,**必须看到红条**——这是"对测试的测试",永绿的测试是假安全;④写**刚好**让测试通过的最简实现→绿条;
⑤重构实现与测试(测试也是代码,须保持 CLEAN),回到①。
两条地基定义:**单元=行为单元**(独立的、可验证的行为;不是方法/类——设计整理而行为不变时,测试不增不改),
以及**只写让失败测试通过的代码**(覆盖率因此天然100%,杜绝"万一将来用到"的投机代码)。
反馈时机经济学:巴甫洛夫——响应必须紧随刺激;三个月后发现的错误无法在大脑中对接因果,立即发现则修复成本最低。
边界:TDD 不取代质量保证(测试针对行为定义,不针对穷举异常);误用(过度测试/针对实现/不隔离依赖)会产生
"测试引入的损伤",让测试比代码更难改。

## A1 — 书中的应用 (Past Application)

### 案例 1: Person 类全程演例(第11章 11.2–11.4,原书例题 worked_example)
- **输入**: 构建"有姓名和年龄的 Person 类"(Java/JUnit/Eclipse)
- **方法执行**: 快乐路径测试 testCreatePersonWithNameAndAge→IDE 生成类/构造器/getter 存根→红条
  (getName 返回 null)→写字段+构造器赋值→绿条;再以 testConstants 定义 MINIMUM_AGE=1/MAXIMUM_AGE=200;
  再加两个反向测试:age=0 抛 AgeBelowMinimumException、age=201 抛 AgeAboveMaximumException(各先红后绿)
- **结论**: 最终 4 个测试;age 断言恰 3 个(0/1/201)且各唯一;明确**不写**第4断言(201 与 0 镜像同因)
- **结果**: 全绿;"演例完成"——书中可下载完整 Eclipse 工程

### 案例 2: "我们这里不用TDD"经理(第10章 10.6,作者亲历 firsthand)
- **输入**: 互联网巨头资深经理开课前质问:"我们不用TDD,你为什么教我的人?"
- **方法执行**: 作者回应:"我不关心是否测试先行,我关心他们写出**可测试的代码**,TDD 只是最有效的方式"
- **结论**: 目标是可测试性,实践是路径——理解原理后实践可按语境替换
- **结果**: 经理接受该表述

### 案例 3: TDD 失败客户(第10章 10.7,作者亲历 firsthand,反面)
- **输入**: 客户"花一天清代码、一周清测试",测试连真实 Oracle 数据库,执行数小时→放弃 TDD
- **方法执行**: 诊断三违反——测试针对实现而非接口、测试冗余、未隔离依赖(测了 Oracle 的代码)
- **结论**: "测试引入的损伤"是误用所致,不能归咎 TDD 本身;依赖应注入模拟
- **结果**: 客户放弃 TDD(书中作反例剖析)

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 想学/教 TDD,需要具体到"先敲哪行代码"的操作程序
2. 写代码前犹豫"从哪下手",或写完不敢重构(没有防护网)
3. 团队 TDD 试行失败过,测试越写越沉重,想知道哪里做错了
4. 修 bug 想避免同类 bug 再犯

### 语言信号

- "怎么开始 TDD / 红绿重构怎么走 / test-driven development 入门"
- "先写测试还是先写代码 / 为什么测试先行"
- "测试写得比代码还多,很痛苦 / 测试拖慢了重构"
- "覆盖率怎么保证 / 单元测试写多少"
- "red green refactor / write the failing test first"

### 与相邻能力的区分

- 与 `behavior-specification-tests` 的区别: 本能力给**循环本身**(假设→存根→红→绿→重构);那里解决**每个行为写几个测试、测试如何唯一**——本书刻意分为实践6/7
- 与 `clean-code-qualities` 的区别: 那里定义质量;这里是以测试为载体的日常生产流程
- 与测试框架教程的区别: 不教 JUnit/pytest 语法;给跨语言的循环纪律与判停

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- agent 拿到任务直接生成实现再补测试,测试只验证"代码能跑"而非定义行为——要求 agent 按红绿重构顺序执行,红条证据成为人的核验点。触发句式: "让 AI 先写测试还是先写代码 / agent 生成的代码要先补测试再合入吗"
- agent 修完的 bug 同类问题反复复发——先写重现测试的修 bug 变体直接适用。触发句式: "怎么让 agent 修 bug 不复发"

## E — 可执行步骤 (Execution)

**输入契约**: 一个待构建的行为描述(可来自用户故事的验收标准)。必需:行为可命名、有可观察结果。不可命名→先回 `user-story-first` 澄清,不硬测。

**步骤**:

1. **写失败测试(假设)**
   从调用者角度杜撰方法签名(名/参/返),用仪表法(maxUsers 而非 20)写断言;此刻不能编译是正常的。
   完成标准: 测试名描述行为(testTotalIs90When...)而非实现(testCalc)。
2. **存根**
   用工具/手写生成空实现(返回 0/null/空),让测试可编译可运行。
   完成标准: 无业务逻辑混入存根。
3. **确认红条**(判停点)
   运行测试,**必须失败**。测试不可失败比没有测试更糟糕——若直接绿,测试有问题,回步骤1。
   完成标准: 记录该测试确实红过(此红条即"对测试的测试")。
4. **最简实现→绿条**
   写**刚好**让测试通过的代码;禁止顺手实现"将来会用"的分支。
   完成标准: 绿条;且实现中无未被该测试要求的逻辑。
5. **重构**
   清理实现与测试(消除冗余、改善命名),保持绿条。
   完成标准: 绿条不变;若重构波及测试,说明测试绑定了实现(警报),按行为重写测试。
6. **循环**
   回到步骤1取下一个意图。快乐路径先行,异常路径随后的顺序可按情况调换。
   完成标准: 每个新行为都经历过完整红绿循环。

**修 bug 变体**: 先写重现 bug 的失败测试(见 `behavior-specification-tests` 的 bug 流程)。
**输出契约**: 新行为+定义它的测试(曾红后绿)+可一键执行的绿条套件。判停:全套测试秒级可跑;连真实外部依赖即违规(应改用模拟)。

**AI 编程适配要点**(AI 适配,非原书):

1. agent 任务指令从失败测试开始,固定模板: 先写测试→运行并**贴出红条输出**→写最简实现→再跑绿;无红条证据的会话产出直接打回
2. 红条核验是人的判停点: 核对 agent 贴的失败确实因断言失败(而非编译错误/环境错误/被 skip),防止流程被伪造
3. 用"只写让失败测试通过的代码"约束 agent 投机: 审查时对照测试集找出未被任何测试要求的逻辑分支(投机的"将来会用"代码),发现即打回删除
4. 行为步与重构步分提交: agent 变绿后单独一轮"只重构不改行为、测试集零修改",通过才可合入——防止一个 diff 混入行为变化与结构变化
5. 修 bug 会话的关闭条件三件套: 重现测试(红)→修复(绿)→该测试常驻回归套件;缺任一件不予合入

## B — 边界 (Boundary)

- **不适用于/不取代**: 质量保证(异常穷举、性能/安全/端到端)——书中明言 TDD 定义行为,QA 思维另有时段("两件事不能同时占用一个大脑");GUI/数据库/多线程代码测试难度高,需架构调整而非蛮力。
- "TDD已死"批评(书中引述)针对的是误用形态(过度测试/绑定实现),照本能力的三条防误用纪律可规避,但学习曲线真实存在(书中见团队挣扎12个月)。
- 不要在发布前夕给团队强加 TDD 学习曲线(书中失败案例的教训);从低风险模块起步。
- 引证的缺陷率下降数据(IBM 40%/微软 60–90%)为 2008–2013 工业研究,样本有限,引用须注明。
- 覆盖率100%是"测试先行"的自然结果,不是事后追打的 KPI——把它当指标会诱发挑软柿子测试。
- **AI 场景边界**(AI 适配,非原书): 警惕 agent 的"测试剧场"——为应付流程补写从未红过的测试、或针对实现细节写脆弱测试,两者都是书中"测试引入的损伤"的 agent 加速版;判据仍是红条证据与"测试名描述行为",不接受"agent 已充分测试"的口头保证。
