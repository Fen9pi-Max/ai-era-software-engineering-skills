# 最后实现设计:演化式设计与意图导向编程

## R — 原文 (Reading)

> 迭代开发自然产生演化式设计，我们先由单一的可测试的行为开始，然后持续改善，直到演化出我们的设计。……将所有公用的应用程序接口中的代码都委托到不同的方法中，就可以消除这些重复工作。这样代码读起来就像一段脚本或一个菜单，因为它保持同样抽象层次。我们将这个技巧称作意图导向编程。
>
> —— David Scott Bernstein,《修改软件的艺术》第12章·实践8

## I — 方法论骨架 (Interpretation)

"最后实现设计"不是不做设计,而是**把健壮性设计推迟到有运行代码+测试保护之后**——此时对问题的理解最深,
设计模式的机会最可见。三条落地技法:
①**意图导向编程**:公共方法体内零实现细节,只含同层委托(load()→format()→write()),读如菜单;
实现下沉为可命名的私有方法。收益:视角内聚(同一抽象层次)、单点定位 bug、消除"概念/实现"层间来回切换的心智开销。
②**创建与使用分离**:实例化集中在工厂,使用方经接口/多态消费;类型选择知识被封进创建端,
使用端零分支——加新变体=加新类+工厂登记,客户端不改(开闭原则的实现路径)。
③**圈复杂度控制**:复杂度=路径数;独立条件相乘(6个if=64),一个方法最少测试数=其圈复杂度;
手段=把条件逻辑移到创建阶段(工厂+多态),使用阶段无分支。
配合"**第二次做好**":第1个用例按 TDD 具体实现,第2–3个用例到齐后再泛化抽象(三角定位式),
比一个用例就猜通用结构更稳。日常节奏:编码与清理**分开为两种任务**(小范围=每次绿条后;大范围=每几个月还一次技术债)。

## A1 — 书中的应用 (Past Application)

### 案例 1: 解压缩的多态设计(第12章 12.7,书中设例 worked_example)
- **输入**: "我想将一个文件用压缩它的软件来解压缩:zip→unzip,pack→unpack,我不关心差异"
- **方法执行**: 客户端只说"解压吧";判断用哪个解压器的对象承担类型知识(创建端),经多态分派
- **结论**: 出现新的压缩格式→现有代码自动适用,因为"选择压缩软件并不是它的职责"
- **结果**: 演示性质;机制=创建/使用分离+多态("如同魔法一般……但并非魔法")

### 案例 2: 连续6个条件的客户代码(第12章 12.6,作者亲历 firsthand)
- **输入**: 客户代码中一个方法连续 6 个条件判断
- **方法执行**: 核算圈复杂度 2^6=64——"我的大脑远远处理不了"
- **结论**: 最少需要 64 个测试覆盖;复杂度高的方法出 bug 概率随之升高
- **结果**: 用作"条件逻辑代价高昂"的量化证据(未说明后续改造)

### 案例 3: 到银行还车贷的待办清单(第12章 12.5,生活类比)
- **输入**: 待办列表写什么?
- **方法执行**: 写"到银行还车贷"(做什么),不写"拿钥匙、穿鞋、发动引擎…"(怎么做);后者是下一层
- **结论**: 抽象层次感是人的自然思考方式;代码同构——每层委托到下一层直至逻辑门
- **结果**: 类比论证,支撑"意图导向=按人的方式组织代码"

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 新功能动工前纠结"要不要先把设计想完善"(预先设计 vs 边写边演化)
2. 方法里 if/switch 嵌套层层,或公共方法一半委托一半实现,读起来费劲
3. 加一种新变体(新支付方式/新导出格式)要改一串调用方代码
4. 评审时争论"这个抽象是不是过度设计/该不该现在就抽"

### 语言信号

- "要不要预先设计 / 大设计前置还是演化设计 / emergent design"
- "怎么降低圈复杂度 / 圈复杂度多少合适"
- "意图导向编程 / programming by intention / 单一抽象层次"
- "工厂模式什么时候用 / 创建和使用分离"
- "过度设计 vs 欠设计 / 什么时候抽象 / rule of three"

### 与相邻能力的区分

- 与 `clean-code-qualities` 的区别: 那里给质量的**判据**(好不好);这里给设计的**时机与技法**(何时抽象、怎么摆方法、工厂放哪)
- 与 `test-first-tdd` 的区别: 测试先行生产行为,"最后设计"生产结构——两者刻意反直觉地配对(先测后设计)
- 与 `legacy-refactoring` 的区别: 本能力用于**新代码的增量设计**;遗留代码的抢救走图钉测试等专门路径

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- agent 首轮交付就带工厂/配置点/"将来扩展"分支的大而全抽象——按"第2–3个真实用例到齐再泛化"打回。触发句式: "AI 生成的代码过度设计了 / agent 上来就建一堆抽象要不要留"
- 要不要让 agent 顺手把设计改"好"——编码与清理分时、行为提交与结构提交分离给出裁决。触发句式: "要不要让 agent 顺手重构一下"

## E — 可执行步骤 (Execution)

**输入契约**: 一个待实现的功能行为(最好已有/可先写测试)或一段待整理的方法/模块。必需:行为可测试(否则先走 `test-first-tdd`)。

**步骤**:

1. **第1个用例:具体实现(TDD)**
   用测试驱动写出最直接的具体实现,**不建抽象**。
   完成标准: 绿条;无投机性参数/配置点("为将来"的分支=违例)。
2. **骨架:意图导向**
   公共方法改写为纯委托序列:每步=一个意图命名的方法调用;实现细节全部下沉。
   完成标准: 公共方法体内零业务实现;每行一个动作,读如菜单/脚本(同层抽象)。
3. **核算圈复杂度**
   数分支:复杂度=1+决策点数(独立条件相乘)。方法>10 或嵌套>2 层→拆方法/移条件。
   完成标准: 每方法复杂度有数字;超标项有拆分方案。
4. **分离创建与使用**(判停点)
   检查:使用方是否自己 new 具体类型并据类型分支?是→提取接口;类型选择移入工厂(静态工厂/DI);
   使用端只依赖接口。测试时注入模拟。
   完成标准: "加一个新变体"演练:只新增类+工厂登记,使用端零修改(开闭达成)。
5. **第2–3个用例到齐后再泛化("第二次做好")**
   重复行为出现第2次:仍容忍;第3次出现或模式清晰:提炼抽象,对比各用例异同定接口。
   完成标准: 抽象有≥2个真实用例支撑;删得掉任何"只有一个实现且无第二用例在路上"的抽象层。
6. **编码与清理分时**
   小清理=每次绿条后的重构步;大清理=每几个月一次的集中还债(列出技术债清单再批量处理)。
   完成标准: 两种时段在日历/迭代上有各自位置;不边写新行为边大改结构。

**输出契约**: 意图骨架(方法树)+复杂度核算表+工厂/接口分离方案(或"暂不需要,理由")。
**判停**: 演化式设计不适合新手(书中原话)——团队未掌握 CLEAN/TDD/重构前,先补地基再上此实践。

**AI 编程适配要点**(AI 适配,非原书):

1. agent 首轮任务在 spec 中写明"具体实现、零抽象": 审查发现投机配置点/只有一个实现的接口即打回(与 TDD"只写让测试通过的代码"同源)
2. 泛化时机由人裁决: 第 3 个真实用例出现时才开独立的"提炼抽象"会话;agent 提炼的抽象必须列出支撑它的≥2个真实用例,人核对后再合入
3. 意图导向作为 agent 产出的可读性门禁: 公共方法只含同层委托、实现下沉私有方法,人按"能否顺序读出意图"快速判 diff——读不出即打回重排
4. 圈复杂度当对账工具: 要求 agent 报告每个方法的复杂度,测试数少于复杂度的方法列为覆盖缺口(书中规则: 一个方法最少测试数=圈复杂度)
5. 行为与结构分提交: agent 会话输出"行为提交"与"结构提交"两串、各自可独立回滚;一个 diff 混新行为+大改结构即打回

## B — 边界 (Boundary)

- **不适用于**: 新手团队(书中明言"它并不是一个新手就能掌握的技术");安全关键等需事前完备设计的领域。
- "最后实现设计"≠永不设计:领域模型/系统边界仍需先想;推迟的是**健壮性/通用性**层面的精化。
- 强行轮换抽象会制造错误抽象——第2–3用例未到时的抽象多是猜的(与 YAGNI 同向);但等到第4+个用例才抽象也在累积冗余。
- 圈复杂度阈值(方法≤10 等)是行业通例而非本书硬数字;书中唯一硬规则是"最少测试数=圈复杂度"。
- 意图导向/工厂/多态均属 OO 工具箱;函数式语境以高阶函数/模式匹配对应转译,勿生搬类工厂。
- 每几个月一次大重构的前提是有测试防护网,否则退回 `legacy-refactoring` 的图钉测试路径。
- **AI 场景边界**(AI 适配,非原书): agent 没有真实用户的"重复之痛"作演化信号,无人把关时要么一步到位生成大抽象、要么永远不敢抽象——泛化时机必须由人按真实用例数裁决;也勿让 agent 把"演化式设计"当成不写测试的借口(本能力的前提是有测试保护)。

## 相关能力

- 依赖(depends-on): `test-first-tdd`(行为先于结构;重构步在其循环内)、`clean-code-qualities`(诊断输入)
- 组合(composes-with): `legacy-refactoring`(其开闭两步法的步骤1就是本能力的重构技法)
