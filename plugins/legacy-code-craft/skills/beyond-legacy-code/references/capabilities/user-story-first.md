# 在问如何做之前先问做什么、为什么做、给谁做

## R — 原文 (Reading)

> 故事是包含如下内容的一句话：某个东西是什么；为什么会有某个东西；这个东西是给谁做的。
> 假设我们要创建一个线上电影售票系统。故事应该是：作为一名电影观众，我希望能在在线购买电影票而不用在电影院排队。
>
> —— David Scott Bernstein,《修改软件的艺术》第5章·实践1

## I — 方法论骨架 (Interpretation)

把"需求收集"重构为"持续对话"：一个功能只用一句话表达——**作为〈谁〉,我希望〈什么〉,以便〈为什么〉**。
这句话的职责不是记录需求,而是**引发产品负责人与开发者的对话**;由对话(而非文档)承载理解。
三条纪律支撑它运转：①故事里禁止出现"如何做"(实现是开发者的领地,客户指挥实现会得到僵化的代码);
②每个故事在动工前要有**验收标准**——功能做什么/什么时候算工作/何时可以前进,且尽量自动化(给定输入→期望输出);
③边界情况(非快乐路径、错误路径)在故事阶段就要列出并进验收测试,否则交付时就是"死之蓝屏"。
这套机制的经济账:传统项目把 1/3–1/2 时间花在需求文档上,而 41% 的开发资源被低质量需求文档浪费——
故事+对话能省下约三分之一的开发时间,并消灭"近半数功能从未被使用"的镀金。

## A1 — 书中的应用 (Past Application)

### 案例 1: 线上电影售票系统的故事(原书示例,worked_example)
- **输入**: 要建一个线上电影售票系统
- **方法执行**: 一句话故事——"作为一名电影观众,我希望能在在线购买电影票而不用在电影院排队"
- **拆解**: 给谁=电影观众;做什么=在线购票;为什么=免于排队。书中明言这"仅仅是开端",不足以开始编码,但足够开启对话
- **结论**: 故事是占位符;3×5 卡片+粗笔是为了**让写细节变困难**

### 案例 2: 500 人在线拍卖实训的启示(第5章 5.2,作者教学观察 firsthand)
- **输入**: 约 500 名学员各自实现同一个在线拍卖系统
- **方法执行**: 实体命名趋同(拍卖/拍卖者/竞价),实现千差万别
- **结论**: 书中推论——实现不该标准化,**该标准化的是行为定义与测试**;故事恰好把对话锚定在行为上
- **结果**: 未说明(教学观察)

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 接到功能需求,正在写"需求说明"或往需求文档里堆细节
2. 团队争论"这个功能到底要做到什么程度才算完"
3. 开发者抱怨需求老变/客户说"这不是我要的"
4. 评审一个故事卡,发现里面写了表结构、接口或算法

### 语言信号

- "帮我写个用户故事 / user story"
- "这个需求的验收标准怎么定 / 怎么知道做完没"
- "客户又改需求了,怎么管需求"
- "故事卡上应该写什么 / 要不要写实现方案"
- "how to write user stories / acceptance criteria"

### 与相邻能力的区分

- 与 `small-batches` 的区别: 本能力管"一句话怎么写、验收怎么定";small-batches 管"写好的故事怎么拆小、多快交付一个"
- 与 `behavior-specification-tests` 的区别: 本能力产出的是**人读的**验收标准(可含自动化);后者是**把验收标准落成可执行的测试判定**(测试数量、唯一性)
- 与纯敏捷流程咨询的区别: 不讲冲刺/站会流程,只管需求表达层的机制

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- 给 agent/Claude Code 类工具写任务 spec: 把实现方案(表结构/框架/算法)直接堆进 prompt, agent 照做后产出僵化代码——本能力的故事句+二值验收标准正是 agent 任务的 spec 层。触发句式: "帮我给 AI 写个任务描述 / 这个需求怎么描述给 agent 才不跑偏"
- agent 交付的功能不对路要返工: 人审发现 agent 理解偏了、做出没人要的镀金功能——缺的是动工前的三要素对话与边界情况约定。触发句式: "AI 做出来的不是我要的 / 怎么让 agent 不自作主张加功能"

## E — 可执行步骤 (Execution)

**输入契约**: 一条功能诉求(可为一句话或一段描述)。必需:功能的受益者可推断。缺失时先问"这是给谁用的、他们拿它干什么",不猜。

**步骤**:

1. **转写故事**
   把诉求压成"作为〈角色〉,我希望〈可观察的行为〉,以便〈收益〉"。给角色加一句背景故事(人格化)帮助开发者理解使用方式。
   完成标准: 句中**零实现词**(无表结构/技术组件/算法);三要素(谁/什么/为什么)齐全,缺项向产品负责人要,不编造。
2. **列边界情况**
   问"这个故事里哪些部分会出错?":非法输入、依赖不可用、无数据、权限不足。
   完成标准: 每条快乐路径之外至少识别 1–2 条次要/错误路径,记在卡片背面。
3. **定义验收标准**
   每条标准写成"给定〈前置〉,当〈动作〉,则〈可观察结果〉"(Gherkin 三段式);尽量用自动化框架(Cucumber/SpecFlow/FIT)落地。
   完成标准: 每条标准**二值可判**(通过/不通过);全部通过即故事完成——这是防镀金的停止线。
4. **移交给对话**(判停点)
   故事不取代沟通:若产品负责人无法及时回答开发者问题,流程瓶颈在此暴露——升级给产品负责人,而不是让开发者猜。
   完成标准: 开发期间的问题有明确应答渠道。

**输出契约**: 1 张故事卡(故事句+边界清单+验收标准组),或等价的 backlog 条目。禁止输出:技术方案、数据模型、实现顺序。

**AI 编程适配要点**(AI 适配,非原书):

1. agent 任务模板 = 故事句(作为/希望/以便)+ 验收标准组;行为定义与实现约束(框架/库/表结构)在 spec 中分层书写,行为层零实现词
2. 验收标准即 agent 会话的完成判据: 交付前逐条执行"给定-当-则"并记录二值结果,全过才算完成,不接受 agent 的"基本完成"表述
3. 边界情况清单随 spec 一起交付给 agent 并要求逐条对照;人审时按清单核对未覆盖的边界,缺项打回同一会话补齐
4. agent 对需求有缺口时必须提问上报,由人按产品负责人角色应答——spec 没写的,不允许 agent 自行猜测补齐

## B — 边界 (Boundary)

- **不适用于**: 已明确的技术任务分解(那是 `small-batches`)、非软件产品的需求、纯 bug 修复单。
- 故事不能承载复杂规则的全部细节——它是"沟通的保障"(Cockburn),细节在对话中现场确认;指望故事=完整规格说明即回到需求文档老路。
- 若组织无产品负责人角色,先补角色(委员会设计行不通),否则本能力只能治标。
- 作者立场(2015/企业级咨询背景):"节省三分之一开发时间"是其经验推算,非受控实验结论。
- 时代注记:书中 3×5 卡片实践在当代多被 issue tracker 承载,"限制细节"的纪律不变。
- **AI 场景边界**(AI 适配,非原书): 给 agent 的 spec 写得过细(规定到函数名/字段/算法)反而剥夺 agent 的实现判断、把人的偏见固化进代码——故事纪律"零实现词"在 agent 场景更关键: spec 只定行为与验收,实现选择交给 agent+人审把关。

## 相关能力

- 依赖(depends-on): 无前置;但配合 `behavior-specification-tests` 才能把验收标准变成可执行判定
- 组合(composes-with): `small-batches`(故事写好后拆小交付)、`continuous-integration`(验收自动化后挂入构建)
- 对比(contrasts-with): `small-batches` 管"多快",本能力管"写什么"
