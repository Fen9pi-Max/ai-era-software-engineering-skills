# 用测试描述行为:判定测试数量与唯一性

## R — 原文 (Reading)

> 单元是指一个行为的单元：一个独立的、可验证的行为。……这需要三个断言：一个是 MINIMUM_AGE - 1（0），应该返回异常……；一个是区间内第一个有效值 MINIMUM_AGE（1）……；一个是另一个非法值 MAXIMUM_AGE + 1（201）……注意三个断言（0、1、201）都是唯一的。
>
> —— David Scott Bernstein,《修改软件的艺术》第11章·实践7

## I — 方法论骨架 (Interpretation)

把测试集当**标准文档**看,"该写多少测试"就有客观答案:**测试数量由行为的结构决定,不由安全感决定**。
判定规则:①每个测试必须**唯一**——"系统中唯一可以由此原因导致失败的测试";多个测试因同一原因失败=冗余,
反馈噪音化,重构时被迫改一堆测试(测试引入的损伤主因)。②边界枚举法:线性区间[min,max]恰好 3 断言
(min-1 异常/首合法 min/上界+1 异常);对称端点的镜像断言与已有断言同因失败,不写(书中 Person 例明确不做第4断言)。
③**测试即活的标准**:点一下按钮即知文档是否过期(需求文档做不到);常量也测(有人把 MINIMUM_AGE 改成 18,
断言即红)。④仪表法:意图变量(personAge)替代硬编码(21),配见名知意 helper,让测试读如规格。
⑤**bug=缺失的测试**:修 bug 先写重现它的失败测试,修复后该 bug 永久设防;并追问"流程哪里漏了它"。
⑥模拟对象:验证"与依赖如何交互"(被正确调用?参数对?)须用 mock,断言管不了工作流。
编写次序纪律:先用行为思维建行为,QA 思维(穷举破坏)放到行为工作之后——两件事不能同时占用一个大脑。

## A1 — 书中的应用 (Past Application)

### 案例 1: Person/age 的 3 断言演算(第11章 11.4–11.5,原书例题 worked_example)
- **输入**: age 合法区间 [1,200](常量 MINIMUM_AGE/MAXIMUM_AGE,本身有测试锁定)
- **方法执行**: 枚举 0(下界外,异常)/1(首合法,无异常)/201(上界外,异常)
- **结论**: 3 断言各唯一;"你也许奇怪为什么不做第四个断言测 age=200——那与=1 的情况重复,决定两个测试是否通过的因素是一样的"
- **结果**: 全绿;"只要你编写测试我就为你喝彩"——作者不因第4断言之争阻止写测试

### 案例 2: 测试集当需求文档用(第11章 11.5,方法论主张)
- **输入**: "很难判断需求文档是否已经过时"这一行业痛点
- **方法执行**: 用测试集承载行为定义(含常量、边界),随时一键执行
- **结论**: "单元测试是活的文档"——绿条即文档与代码同步的证明
- **结果**: 方法论主张,配套仪表法/helper 法使其可读

### 案例 3: 二手车复合故障(第11章开篇,作者亲历 firsthand,动机案例)
- **输入**: 便宜二手车电路故障,3 个修理工换件无效
- **方法执行**: 第4个修理工找到**两个共存**短路(复合问题)
- **结论**: 复合型问题"如果出现在软件里,几乎不可能顺利排查"——单元测试把行为隔离验证,复合bug在编写时即现形
- **结果**: 修复完成;用作测试即时反馈价值的类比

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 提交前自问"这几个测试够了吗/是不是写多了"
2. 改一处行为挂一片测试,怀疑测试冗余或绑定了实现
3. 接手一段无文档代码,想用测试重建行为规格
4. 修完 bug 担心复发,想建立防复发机制

### 语言信号

- "该写多少单元测试 / 测试要写到什么程度"
- "测试重复了怎么办 / 哪些测试是多余的"
- "边界值怎么选测试点 / 边界测试"
- "怎么修 bug 才不复发 / 回归测试怎么加"
- "how many tests / test uniqueness / boundary testing / regression"

### 与相邻能力的区分

- 与 `test-first-tdd` 的区别: 那里给**循环流程**(红绿重构的时序);这里给**测试集的设计判据**(数量/唯一性/仪表法)——一个管"怎么走",一个管"每步放什么"
- 与 `user-story-first` 的区别: 那里的验收标准是人/PO 层的(给定-当-则);这里把它们落成开发者层的行为断言并判定数量
- 与测试覆盖率工具的区别: 覆盖率数字回答"跑过没有";本判据回答"哪些行为点必须各有断言"

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- 让 agent"补全测试"后测试数量膨胀、一改实现挂一片——用"数量由行为结构决定+失败原因唯一"来验收 agent 的测试集。触发句式: "AI 补的测试是不是写多了 / agent 的测试怎么验收"
- 给 agent 生成的代码设计验收测试点与边界值——3断言法与唯一性判据直接作为测试设计规格交给 agent。触发句式: "让 AI 给这段逻辑设计测试用例 / agent 代码的边界测试怎么定"

## E — 可执行步骤 (Execution)

**输入契约**: 一个行为的规格描述(合法域/非法域/边界)或一个待修 bug(复现条件)。必需:可判定"什么算合法输入"。缺失时先与产品负责人确认边界,不猜合法域。

**步骤**:

1. **画行为的输入域**
   标出:合法区间的下界/上界、离散合法值集合、显式非法值集合、无上(下)界时注明"无界"。
   完成标准: 每个维度有"连续区间/离散集合/无界"标注。
2. **枚举断言点**
   连续区间: 下界-1(异常)/下界(首合法)/上界+1(异常)——共3;若某端无界,该端只留内侧重界1个;
   离散集合: 每个语义不同的取值1个;布尔/开关: 2个。
   完成标准: 每个断言点写出"输入→期望",且与其它断言点的**失败原因不同**。
3. **唯一性审查**(判停点)
   对每对断言问:"它们会因同一处代码错误而同时失败吗?"会→删其一(或合并);镜像端点(如同时测 0 和 201 之外再测 -1)通常冗余。
   完成标准: 任选一处行为改动,失败的测试不超过1个(理想)且各断言失败原因可解释。
4. **仪表化**
   硬编码值换成意图变量(maxUsers/anyInt);初始化逻辑提为见名知意 helper。
   完成标准: 测试体读如一行规格说明;无魔数。
5. **bug 变体流程**
   ①复现:写失败测试重现 bug(红)→②修复至绿→③防复发确认:该测试此后常驻回归套件→④追问流程:"这个 bug 是怎么漏出来的?"(缺失的评审/边界对话/依赖故障)并补流程。
   完成标准: 红→绿有记录;回归套件新增该测试;流程改进项有归档。
6. **工作流用 mock**
   需验证"调用顺序/参数/次数"时,用模拟对象替代真实依赖,断言交互而非返回值。
   完成标准: 交互断言与行为断言分属不同测试。

**输出契约**: 断言清单(输入/期望/失败原因各一列)+唯一性说明+回归新增项。计算类输出可复算(阶段4已对折扣规则执行,见 runs/stage4-output-eval.md)。

**AI 编程适配要点**(AI 适配,非原书):

1. 用机械判据验收 agent 测试集: 每个测试失败原因唯一;线性区间核对是否恰 3 断言(下界-1/首合法/上界+1);镜像冗余断言要求 agent 删除并说明理由
2. 让 agent 先报输入域(连续区间/离散集合/无界)再报断言点: 人只核域划分对不对——域错则断言全错,这是审查的最小充分点
3. 防覆盖率游戏: 对 agent 的考核口径是"断言点覆盖行为结构",不是覆盖率百分比;发现凑覆盖的空断言/同因重复断言即打回
4. 仪表法写进 agent 编码规范: 测试禁魔数、用意图变量与见名知意 helper——让人能直接把 agent 的测试当规格读,降低审查成本
5. bug 防复发流程固化: agent 修 bug 的会话必须以"重现测试进入回归套件"收尾,缺该测试的修复不予合入

## B — 边界 (Boundary)

- **不适用于**: 质量保证型测试(穷举异常、性能、安全、端到端)的数量决策——那是 QA 思维,须放在行为建完之后(书中明确分时段);"测试越多越好"在此被明确否定。
- 3断言法针对**线性区间**的单一维度;多维度组合(如 age×国家×币种)按维度分别枚举,组合爆炸时应先怀疑设计(拆行为)而不是硬测。
- 作者对"要不要写第4断言"持开放态度("只要你编写测试我就为你喝彩")——唯一性是纪律,不是教条到阻止写测试。
- mock 只管交互验证;滥用 mock 测实现细节会绑定实现(与唯一性纪律冲突时,以测行为优先)。
- 100% 覆盖率主张是作者立场(以测试为规范的自然结果);现实中外部依赖遮蔽处允许例外,但须显式列出。
- **AI 场景边界**(AI 适配,非原书): 不要用"让 agent 多生成些测试"回应质量焦虑——数量由行为结构决定,与安全感无关;唯一性判据恰是拒绝 agent 测试膨胀(生成便宜、维护昂贵)的依据。
