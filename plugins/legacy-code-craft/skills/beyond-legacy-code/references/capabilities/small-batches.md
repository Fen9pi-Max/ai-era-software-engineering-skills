# 小批次构建:拆分故事、限制半成品、控制范围

## R — 原文 (Reading)

> 相对于用独立的分析、设计、编码、测试、部署阶段来构建软件，逐个功能地构建系统，即每几周往一个正常工作的系统中添加功能要简单得多，而且风险小得多。……理想的任务是需要大约四小时完成的工作。
> 周期时间 = 任务数量 / 吞吐率（利特尔法则）
>
> —— David Scott Bernstein,《修改软件的艺术》第6章·实践2

## I — 方法论骨架 (Interpretation)

交付节奏决定流程形态:**发布周期越长,越被迫回到瀑布**(前期写需求文档、后期集中测试集成)。
小批次的本质不是"快",而是**用验证取代假设**:任务越小,越易理解、易预估、易实现、易测试,反馈回路越短,
问题在萌芽期就被发现。三条操作机制:①**拆分决策树**——故事过大先判型:复合型(内含子故事)按组件拆;
复杂型(含未知)先分离已知/未知,对未知用穿刺(spike)时间盒子迭代缩小,或封装在接口后面。
②**WIP 控制**——利特尔法则(周期时间=任务数/吞吐率):减少在制任务数就能缩短周期;
99% 完成的任务风险未知、价值为零,唯一消除风险的方式是完成即集成。
③**范围控制**——铁三角在软件里只有范围是自由变量(质量不可牺牲,人力加倍的沟通成本反使更慢);
用 MMF(最小可市场化功能集)锚定"生死功能",排待办**顺序**而非优先级;时间盒子是训练轮,
终点是范围盒子(拿起一个完整工作单元→做完→下一个)。

## A1 — 书中的应用 (Past Application)

### 案例 1: 发布节奏效率表(第6章 6.3,转述 Poppendieck,reported_case)
- **输入**: 假设任务均≈1周,需求随机到达
- **方法执行**: 平均等待≈发布周期×1.5;效率=基准任务时长/平均等待
- **演算**: 2周周期→平均等待3周→效率50%;2个月→3个月→≈12%;6个月→9个月→仅约2.6%
- **结论**: 6个月周期中,开发者一半以上时间不在写代码;长周期必然催生需求文档与集中测试
- **结果**: 表格演算结果(**注**:书中表格隐含≈1.5周基准任务,正文6个月算例用1周任务,两处基准不一致——定性结论可靠,精确公式见 needs-review nr-01)

### 案例 2: 24GB 内存的发布周期(第6章 6.7,作者亲历 firsthand)
- **输入**: 年营收十亿美元客户,改一个单词拼写也要全系统重建,三周手工测试验证每次发布
- **方法执行**: 想改双周迭代→按其验证成本"算一下就知道根本行不通"
- **结论**: 大批次验证成本会反过来固化长周期,最终"他们必须重写一切"
- **结果**: 客户被迫整体重写系统

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 故事/任务大到一个迭代做不完,或做完没法验证
2. 排期讨论:为什么进度总估不准、为什么总有"快完了"的任务挂着
3. 团队同时做很多事,切换频繁、交付拖沓,想引入 WIP 限制/看板
4. 要向管理层论证"缩短发布周期"的价值

### 语言信号

- "这个故事太大怎么拆 / 怎么拆分用户故事"
- "为什么我们估时总不准 / 任务总是 90% 完成挂着"
- "要不要限制在制品 / WIP / 看板怎么用"
- "发布周期多长合适 / 缩短发布周期有什么用"
- "story splitting / reduce WIP / batch size / lead time"

### 与相邻能力的区分

- 与 `user-story-first` 的区别: 那里管"故事怎么写",这里管"写好的故事怎么拆小、以什么节奏交付"
- 与 `continuous-integration` 的区别: 本能力把任务切小;CI 保证切小的任务能**完成即集成**(拆小了却不集成,风险照旧)
- 与 `measure-development-value` 的区别: 本能力是机制;度量能力提供"周期时间/价值时间"等配套口径

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- 让 agent 一口气做完一个大功能,产出上千行 diff 人没法审、错了没法回滚——需要按"一个会话一个可回滚小批次"切分人机结对节奏。触发句式: "AI 生成了一大坨代码怎么审 / agent 的任务怎么切小"
- 多个 agent 会话并行写码,半成品分支越堆越多、集成遥遥无期——WIP 控制直接适用(未审合的 agent 产出=在制任务)。触发句式: "能开几个 agent 并行写码 / agent 分支堆积、挂着一堆 90% 完成的怎么办"

## E — 可执行步骤 (Execution)

**输入契约**: 一条(或一组)用户故事/任务,含其验收标准的粗略描述。缺失验收标准时先回 `user-story-first` 补,不在此处编。

**步骤**:

1. **判型拆分**
   问:"它内含几个可独立验收的子行为?"——复合型→按组件拆成独立故事(各自有验收标准);
   "它含我不知道怎么做/要什么的部分吗?"——复杂型→标记已知/未知,未知单独成探查任务。
   完成标准: 每个子故事单一目的、可测试、有可观察结果。
2. **核粒度**
   用"≈4 理想工作小时"(一个工作日的一半产出力)校准任务;城市出行类比:再小的外出也要半天。
   完成标准: 任务要么≤4小时,要么已再拆;同时按验收标准分解,完成即有证据。
3. **限制 WIP**(判停点)
   利特尔法则:周期时间=任务数/吞吐率。规则:完成一个再领下一个;看板每列设上限,满了先清"进行中"。
   完成标准: "进行中"任务数有显式上限且被遵守;无 99% 挂起任务(要么完成集成,要么退回待办)。
4. **控制范围**
   识别 MMF(产品可用且有价值的最小功能集);待办排**顺序**(下一个最重要的),迭代内不换向、新想法进下迭代;
   交付压力来时砍范围,不砍质量、不加人。
   完成标准: 每个迭代结束时系统处于可发布状态(与 `continuous-integration` 联动)。

**输出契约**: 子故事/任务清单(各含验收标准与预估粒度)+ WIP 上限约定 + 待办顺序表。
**效率演算口径**(引用书中表时必须注明): 平均等待≈周期×1.5;效率=基准任务(书中表≈1.5周,正文算例1周,基准不一致)/平均等待;仅作定性比较用。

**AI 编程适配要点**(AI 适配,非原书):

1. 一个 agent 会话 = 一个小批次: 会话目标控制在"人能一次整段审完的 diff"量级;会话产出以独立可回滚的提交/PR 收口,不跨会话攒大摊子
2. WIP 上限按人的审查吞吐设定,不按 agent 生成速度设定: 未审合的 agent 产出计入在制;审查积压时先清"进行中",不开新会话
3. 复合型需求先拆成故事级子任务再分发 agent;含未知的部分单独开时间盒子 spike 会话(只探查出方案、不改实现),与已知部分分离
4. 每个会话开始前验收标准必须已写进任务;结束时逐条核对,不达标退回同一会话修完——不用"再开一个会话叠功能"来消化欠账

## B — 边界 (Boundary)

- **不适用于**: 已是原子级的任务(为拆而拆再拼回大功能,书中明言"这样并不管用");硬件耦合型工作(波音没法只造一只机翼就测试)。
- 时间盒子是脚手架不是目的——永久依赖"双周冲刺"如同一辈子贴尼古丁贴片(作者原喻);终点是流式小任务。
- 效率表的精确百分比不可作为承诺数字(书内基准不一致,见 needs-review nr-01;且假设任务均≈1周、需求随机到达)。
- "加人提速"在此被明确否定( Brooks 法则):沟通路径超线性增长——但书中也承认这是软件开发特有,勿外推到其他协作场景。
- 度量拆分效果时禁止回退到速度/代码行(见 `measure-development-value` 的反指标清单)。
- **AI 场景边界**(AI 适配,非原书): 不因"agent 生成很快"而放大批次——人审读能力才是瓶颈,超大 diff 会诱使审查形式化;反向同理,已是单一行为单元的任务不为切而切硬拆成多个 agent 会话(原书"拆了再拼回大功能并不管用"在 agent 场景同样成立)。

## 相关能力

- 依赖(depends-on): `user-story-first`(拆分的对象是合格的故事)
- 组合(composes-with): `continuous-integration`(拆小的任务必须完成即集成,风险才清零)、`measure-development-value`(周期时间/价值时间口径)
- 对比(contrasts-with): `design-last`("第二次做好"容忍第一版具体实现,与"小步交付"互补不冲突)
