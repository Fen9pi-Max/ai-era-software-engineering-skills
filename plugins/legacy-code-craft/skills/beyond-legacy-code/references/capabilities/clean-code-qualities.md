# CLEAN 五特质:评估并改善代码质量

## R — 原文 (Reading)

> 我们这么称呼这些特质：Cohesive 内聚 / Loosely Coupled 松散耦合 / Encapsulated 封装 / Assertive 自主 / Nonredundant 没有冗余。首字母拼在一起就是 CLEAN（整洁）。优秀的代码就是 CLEAN 的代码。
>
> —— David Scott Bernstein,《修改软件的艺术》第9章·实践5

## I — 方法论骨架 (Interpretation)

代码质量不是感觉,是五个可判定的结构特质。**内聚**:每个实体只关注一件事;"难以命名"=职责尚未定义好;
OO 程序像洋葱,层层抽象包裹,微型类胜过万能类。**松散耦合**:用"有意耦合/意外耦合"取代松紧二分——
退出按钮与退出动作就该耦合,要消除的是混入的意外耦合;经抽象/接口间接调用,保留可注入的接缝。
**封装**:让"做什么"隐藏"如何做";默认全部 private,必要时再暴露(暴露易、收回难);由外而内设计。
**自主**:对象管理自身状态,行为放在它依赖的数据处;打印文档的格式化逻辑属于 Document 而非 Printer
(Printer 只执行);"多管闲事"的对象破坏封装又拖慢性能。**无冗余**:冗余=对**意图**的重复
("不一样的代码可能是冗余的,一样的代码可能没有冗余");复制粘贴前先问能否封装一处两处调用。
三定理:①五特质互相促进——专注一两种即可带动整体;②可测试性是综合标尺(测试太多=内聚不足;
依赖一堆=耦合过度;测试依赖实现=封装问题;结果出现在别处=不自主;重复测试=冗余);
③今天的内部质量决定明天的速度——最快的开发者恰是代码最整洁的人(因果不可倒置)。

## A1 — 书中的应用 (Past Application)

### 案例 1: 打印职责归谁(第9章 9.4,书中设例 worked_example)
- **输入**: 问题:控制打印文档的代码应放"文档类"还是"打印机类"?多数开发者脱口而出"打印机类"
- **方法执行**: 谁拥有行为所依赖的状态?只有 Document 了解文档细节→格式化归 Document,打印执行委托 Printer
- **结论**: "文档类进行控制,打印任务托管给打印机类"——自主特质给出行为放置的判据
- **结果**: 演示性质,无后续交付("未说明")

### 案例 2: NASA 的有意冗余(第9章 9.5,作者亲历 firsthand)
- **输入**: 作者授课说"冗余一定是坏事",台下两位 NASA 开发者起立反对
- **方法执行**: 航天飞机5台计算机独立计算再互核答案——这是**有意为之**的冗余
- **结论**: 判据是意图:关键任务系统的有意冗余可救命;非刻意冗余总是维护负担
- **结果**: 概念修正,"冗余=意图的重复"且须排除有意冗余

### 案例 3: 最快的程序员最整洁(第4章 4.1,作者亲历 firsthand)
- **输入**: 作者观察"我认识的最优秀的开发者也是最整洁的程序员"
- **方法执行**: 按字母序排列实例变量、频繁重命名、立即删除无用代码
- **结论**: 不是"不顾质量求快",而是**因为**保持高质量才能持续快
- **结果**: 虚拟世界中质量投入短期也省钱(与现实世界相反)

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 代码评审:想给"这代码好不好"一套非个人喜好的判据
2. 重构前诊断:不知道该往哪个方向改
3. 团队争论代码质量定义(快?没bug?好读?)需要统一语言
4. 写完代码自检:测试很难写,想知道是设计问题的哪个信号

### 语言信号

- "这段代码质量怎么样 / 怎么评估代码质量"
- "什么是好代码 / 代码评审看什么"
- "内聚 / 耦合 / 封装 怎么判断"
- "为什么我的代码难测试 / 难改"
- "clean code / code quality / cohesion / coupling / encapsulation / DRY"

### 与相邻能力的区分

- 与 `test-first-tdd` 的区别: 本能力是**质量的定义与诊断**;TDD 是达到它的**日常生产手段**(可测试性是本能力的标尺之一)
- 与 `design-last` 的区别: 这里给"什么是好"的判据;那里给"何时做设计决策、用什么技法(意图导向/工厂/多态)"的时机与操作
- 与代码风格/lint 工具的区别: 不检查格式与命名风格(集体所有权条款另说),只判结构特质

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- 人审 agent 生成的代码没有统一判据,只凭个人喜好或只盯风格——CLEAN 五特质可直接作为 AI 代码审查的结构化清单。触发句式: "AI 写的代码质量怎么评 / 审 agent 的代码该看什么"
- agent 生成的代码测试写不动、一改一片——用"可测试性反推设计缺陷"的标尺诊断 agent 产出。触发句式: "AI 生成的代码好难测 / agent 代码怎么越改越乱"

## E — 可执行步骤 (Execution)

**输入契约**: 一段代码(类/模块/函数)及其使用上下文(调用方、测试如有)。纯算法片段也能评内聚/冗余,但耦合/封装需调用上下文——缺失时明确标注"该维度证据不足",不猜。

**步骤**:

1. **内聚检查**
   每个类/方法:能否用一句话命名它做的事?命名困难→职责未定义;一个方法里做多件不相关事→拆。
   完成标准: 每个受检实体有一句话职责描述;说不出的列入拆分清单。
2. **耦合检查**
   列出依赖:哪些是"需要所以耦合"(有意,如退出按钮→退出),哪些是"图方便/直接掏别人状态"(意外)?
   完成标准: 每条依赖有 有意/意外 判定;意外耦合项给出经接口/抽象的替代路径。
3. **封装检查**
   问:调用方需要知道"如何做"才能用吗?内部状态是否被直接暴露/读取?
   完成标准: 列出"可隐藏而未隐藏"清单(默认 private→必要时暴露;由外而内:从调用者需要出发重排接口)。
4. **自主检查**(判停点)
   对每个方法问:它依赖谁的数据?若主要依赖别的对象的状态→方法应搬到那个对象(依恋情节)。
   完成标准: 每个行为有"数据归属"结论;错位行为列入迁移清单。
5. **冗余检查**
   找"在不同地方做同一件事"(意图重复,不限字面);复制粘贴冲动点即候选;消除后能否暴露出更简的统一方案?
   完成标准: 每处冗余有"合并为一处+两处调用"或"保留理由(有意冗余)"的结论。
6. **可测试性标尺复核**
   综合信号:测试难写落在哪个维度(测试太多→内聚;依赖爆炸→耦合;测试绑实现→封装;结果在别处→自主;重复测试→冗余)。
   完成标准: 输出五维结论表+按"专注一两个特质带动整体"选择的改进次序。

**输出契约**: 五维评估表(判定+证据行号/位置+改进方向)+改进优先级清单。计算/断言类结论需可回溯到具体代码位置。

**AI 编程适配要点**(AI 适配,非原书):

1. 把五维检查固化为 agent 产出的审查清单: 每个 PR/会话产出五维结论表(判定+代码位置证据),人按表抽查;不合格维度打回对应会话整改
2. 可测试性信号直接判 agent 设计: agent 报告"这段没法写单元测试"→按标尺定位维度(依赖爆炸=意外耦合;测试绑实现=封装问题),先修结构再补测试,不允许绕过
3. 内聚检查的快捷用法: 让 agent 自报每个类/方法的一句话职责,人核对自报与实际行为是否一致——对不上即职责不清,列入拆分清单
4. 冗余判定防误伤: agent 提"消除重复"时要求说明合并的是**意图**而非字面;人审时警惕 agent 为消冗余顺手建出的过早抽象(与 `design-last` 的 rule of three 联动)

## B — 边界 (Boundary)

- **不适用于**: 关键任务型系统的**有意冗余**(5机互核)——冗余维度须先排除该场景;性能等真实约束允许局部妥协(但须是真约束而非假设)。
- 本框架出自 OO 范式(Java/C# 语境);函数式/过程式代码的"自主/封装"维度需转译(以模块边界代替对象),作者自认"很多场景下面向对象不适用"。
- "内部质量决定速度"是作者经验+行业引证,非受控实验;引用时标注。
- 评估≠重写:输出是诊断与方向,动手改造走 `legacy-refactoring`/`design-last` 的路径,且遵循"没坏别修"。
- 书中"理想状态是看不出代码出自谁"针对团队一致性,不应压制合理的个人风格创新。
- **AI 场景边界**(AI 适配,非原书): 五特质判定权留在人手里——agent 自评自己的代码存在系统性宽松,正确分工是 agent 出证据表、人下判定;也不以"风格统一"为由让 agent 批量重格式化全库,超出诊断范围的批量改动只会制造 review 噪音与风险。

## 相关能力

- 依赖(depends-on): 无前置;是 `test-first-tdd`/`design-last` 的公共判据来源
- 组合(composes-with): `test-first-tdd`(可测试性标尺的双向应用)、`design-last`(诊断后的改造技法)、`collaboration-pairing`(结对的公共语言)
- 对比(contrasts-with): `legacy-refactoring`(诊断 vs 安全动手的程序)
