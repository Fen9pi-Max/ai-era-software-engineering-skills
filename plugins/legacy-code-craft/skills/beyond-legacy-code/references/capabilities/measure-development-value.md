# 度量软件开发:价值导向的7个策略

## R — 原文 (Reading)

> 我们应该用对客户的价值来衡量自己。这是我赞同的为数不多的几个度量方法之一，因为它不鼓励局部优化。几乎所有其他的度量方法（代码行数、速度等）都是局部优化。
>
> —— David Scott Bernstein,《修改软件的艺术》第6章·6.13.1

## I — 方法论骨架 (Interpretation)

多数开发度量在奖励局部优化:代码行数奖励啰嗦、速度奖励乐观承诺、覆盖率数字奖励挑软柿子。
本能力用 7 个价值导向度量替代:①**产生价值的时间**(从开始构建到用户获得价值——着眼大局的端到端口径);
②**编码时间占比**(好流程让开发者大部分时间在写代码;反例:有开发者<10%时间在开发,其余耗在会议/报告);
③**缺陷密度**(千行 bug 数——少数可跨团队对比的口径之一;频繁出现=流程缺陷的症状,修根因不修表象);
④**发现缺陷的时间**(修复成本随缺陷产生后的时间**指数**增长;秒级发现成本近零);
⑤**功能的客户价值**(近半功能从未使用→待办按价值排序,不确定就问客户);
⑥**未交付功能的损失**(问利益相关者"这功能不交会损失多少"——答案常令人吃惊,是构建的最强理由);
⑦**反馈回路的效率**(回路越短效率越高;流程本身常是最大杠杆)。
配套经济学(引用需注明出处与口径):交付后修 bug 成本≈需求阶段100倍(Boehm);
~80% 开发成本花在排查修复(NIST 2002);60% 所有者成本在优化/17% 在错误修正(Glass 2001)。
反指标黑名单:速度(传递错误信号,诱使牺牲质量)、代码行数(客户毫不关心)。

## A1 — 书中的应用 (Past Application)

### 案例 1: 咖啡壶的 4 万美元(第6章 6.8,作者亲历 firsthand)
- **输入**: 团队在三楼,咖啡壶在四楼,人人喝咖啡
- **方法执行**: 团队负责人核算跨楼层取咖啡的时间成本≈每年 4 万美元
- **结论**: "最重要的提议:买个咖啡壶"——小改进的量化论证;配合"每两周2%改进→一年50%"的复利
- **结果**: 20 美元购壶获批

### 案例 2: TDD 实证数据汇总(第14章 14.1,作者转述 reported_case)
- **输入**: "TDD 是不是降低缺陷但拖慢速度"的争议
- **方法执行**: 汇总工业研究:IBM 缺陷率-40%、微软-60%~90%(Nagappan 等);微软 Windows/MSN 案例质量超 2 倍(Bhat&Nagappan);NC State 实验:通过率+18%、耗时+16%、覆盖 92–98%(George&Williams);XP 案例:效率+50%、发布前质量+65%(Layman 等);QSM:福莱特周期缩短5个月、缺陷减半、省 130 万×6 次
- **结论**: "提高效率并不意味牺牲质量;它们通常共同进退";TDD 的成本被"时间都在调试/开会而非打字"的事实抵消
- **结果**: 转述研究,均含出处;作者注明"这些数据并未被广泛认知"

### 案例 3: 开发者的直觉估计(第2章 2.4,作者亲历 firsthand)
- **输入**: 数千名课程学员被问"软件项目成功率多少"
- **方法执行**: 匿名直觉估计 5%–30%
- **结论**: 与混乱报告量级吻合——从业者体感即数据交叉验证;勿用速度等伪精确度量替代
- **结果**: 用作"先直面试问题再谈度量"的依据

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 管理层要求"度量团队产出/效率",团队担心被错误指标绑架
2. 敏捷导入后想用"速度"做跨团队比较/考核,需要判断是否合适
3. 想论证质量投入(测试/重构/结对)的回报,需要数据框架
4. 建立团队仪表盘,选首批指标

### 语言信号

- "怎么度量开发效率 / 开发团队 KPI 怎么定"
- "用速度考核团队行不行 / velocity 能比较吗"
- "缺陷密度怎么算 / 千行代码 bug 数"
- "证明 TDD/重构/结对的收益 / 质量投入的 ROI"
- "developer productivity metrics / DORA / velocity vs value"

### 与相邻能力的区分

- 与 `small-batches` 的区别: 那里是交付机制;这里提供"周期时间/价值时间"等衡量该机制效果的口径
- 与 `collaboration-pairing` 的区别: 结对推行时"跟踪进度/用数字说话"的策略由本能力承接(缺陷、返工、代码量的前后对比)
- 与 DORA/SPACE 等现代度量体系的区别: 本书口径(2015 前)不含部署频率/变更失败率等;可兼容使用,但须标注来源差异

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- 管理层要求用生成代码行数/PR 数/提交数度量"AI 产出",团队担心被错误指标绑架——反指标黑名单原则直接适用。触发句式: "怎么度量 AI 编程的效率 / agent 的产出怎么算 KPI"
- 引入 agent 后写码变快、但人在审查与返工上的时间激增,要向管理层解释时间去哪了——价值时间与回路效率口径给出量化框架。触发句式: "AI 省下的写码时间去哪了 / 人机团队的瓶颈怎么量化"

## E — 可执行步骤 (Execution)

**输入契约**: 度量目的(考核?改进?论证?)、团队现状(现有指标、数据可得性)。必需:明确目的——为考核而度量的诉求应先提示 gaming 风险并记录决策,不静默配合。

**步骤**:

1. **审计现有指标**
   对每个在用指标问:它奖励什么行为?能否被局部优化(gaming)?在"速度/代码行/覆盖率数字"黑名单内→列入替换清单。
   完成标准: 每个指标有"保留/替换/废弃"结论与理由。
2. **选 3–5 个价值导向指标起步**
   推荐最小集:产生价值的时间(端到端 P85 口径:进入待办→用户可用)、缺陷密度(千行 bug 数)、反馈回路时延(提交→CI 结果)。
   按目的增选:论证质量投入→缺陷发现时间分布;排期决策→未交付功能损失(访谈利益相关者)。
   完成标准: 每个指标写明 定义/数据源/计算口径/反 gaming 说明。
3. **建立基线并设定改进假设**
   先测现状两周,不急着定目标;"每两周 2%→一年 50%"的复利框架设定节奏。
   完成标准: 有基线数值与记录渠道;目标表述为改进率而非绝对值。
4. **解读纪律**(判停点)
   缺陷密度升高→问"流程哪里漏了"(症状观,5个为什么),不追责个人;
   指标变差但客户价值提升→以价值口径为准(局部服从全局)。
   完成标准: 每次指标回顾有"流程改进项"产出。
5. **论证质量投入时引用实证**
   用第14章研究(标注出处与年代)+自身基线前后对比;主张"质量与效率共同进退"。
   完成标准: 论证文档区分"书中转述数据"与"本团队实测数据"。

**输出契约**: 指标审计表+选定指标的定义卡(口径/数据源/反 gaming)+基线记录+回顾节奏约定。
**成本口径引用规范**: Boehm 100倍/ NIST 80%/ Glass 60%+17% 各注明出处与统计口径,不得混同为同一口径的统一公式。

**AI 编程适配要点**(AI 适配,非原书):

1. 反指标黑名单扩展到 AI 指标: 生成代码行数、token 消耗量、agent 会话数、PR 合入速度均逐一审"它奖励什么行为、能否被局部优化"
2. 价值时间口径适配人机流: 进入待办→用户可用,链路计入 agent 生成+人审+返工全段;用分段时延定位瓶颈在 spec 质量还是人审吞吐
3. 缺陷密度按来源归因: agent 产出的缺陷在 CI/人审/生产各环节的发现分布,用"发现缺陷的时间"口径度量流程漏斗——修流程,不追责人(也不追责 agent)
4. 审查吞吐(人均审 diff 行数/打回率)只作过程改进信号: 用于发现批次过大或 spec 缺陷,明确不进个人或 agent 的考核
5. 论证"测试先行约束 agent"的收益时,自家基线前后对比与书中转述研究(注明出处与年代)分栏呈现,不混同两类证据

## B — 边界 (Boundary)

- **不适用于**: 把这些指标直接变成个人绩效考核——缺陷密度等口径只在团队/流程层有效,个人层必然 gaming(书中暗线:度量用于发现流程缺陷)。
- "生产率也许根本不可能(度量)"是书中原话——本能力交付的是**改进与论证口径**,不是精确生产率测量。
- 引证的行业数据(NIST 2002/Galorath 2012/Standish)年代久远且方法受质疑(书中第2章自证 Standish 缺陷);引用时标注量级参考属性。
- 现代体系(DORA 四指标、SPACE)可作补充,但属书外知识,混用须分栏标注。
- "编码时间占比"的分子分母(何为编码/何为会议)须团队先定义,书中未给操作定义。
- **AI 场景边界**(AI 适配,非原书): 不因 agent 生成代码"边际成本近零"就把返工当零成本——返工消耗的是人审时间这一最稀缺资源;也不可用"生成很快"论证跳过测试与审查,度量口径必须包含缺陷与回路时延,否则又落回局部优化。

## 相关能力

- 组合(composes-with): `small-batches`(周期/价值时间是其效果口径)、`collaboration-pairing`(推行的数据论证)、`continuous-integration`(反馈回路时延的载体)
- 对比(contrasts-with): `small-batches`(机制 vs 测量)
- 依赖(depends-on): 无硬前置;与回顾会议(`collaboration-pairing` E 步骤4)共用"责怪流程不责怪人"纪律
