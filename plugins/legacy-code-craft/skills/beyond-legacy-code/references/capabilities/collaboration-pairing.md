# 协作:结对编程与回顾会议

## R — 原文 (Reading)

> 驾驶员是键盘前的那个人，领航员坐在他旁边能够清楚地看到整个显示器。但是领航员并不是干坐在那里看着驾驶员编码。领航员和驾驶员彼此交流。……驾驶员和领航员应该尽可能频繁地交换角色——多于五分钟但是不能多过三十分钟。
>
> —— David Scott Bernstein,《修改软件的艺术》第8章·实践4

## I — 方法论骨架 (Interpretation)

"我们拥有的最宝贵的资源是彼此"——协作不是氛围问题,是有角色契约的技术。
**结对编程**:两人一机,驾驶员写、领航员实时审查并追问"为什么这么做而不是那样做";5–30分钟轮换键盘
(作者习惯20分钟;发现对方无聊就交出键盘);变体乒乓结对(一人写测试,另一人让它通过再写下一个)、
强式结对(想法必须经他人的手入机器)。配对策略:性格互补(主动×被动,防好友互绑随声附和)、
资深×新手(新成员见习1–2周)、随机轮换(promiscuous——和意想不到的人搭档效率可能是"最佳搭档"的3倍)。
降级方案**伙伴编程**:全天独编+每天最后一小时与伙伴互审。扩展谱系:穿刺(小组时间盒子研究未知)、
群战(小组同时攻坚)、围攻(全团队+双投影仪+轮流驾驶,像蚁群分解食物)。
**回顾会议**:责怪流程不责怪人;5个为什么追根因(约第4次发问见效);找 2% 级小改进(每两周2%→一年50%);
倾听每个人;给改进以支持;度量进度。经济账:结对只多花15%总时间,换来缺陷更少、知识全网传播、
新成员两周上手——是作者所知最快的知识传播手段。

## A1 — 书中的应用 (Past Application)

### 案例 1: IBM"牛棚"合同工(第8章开篇,作者亲历 firsthand)
- **输入**: 作者在 IBM 做合同工,被安排进所有桌子拼在一起的"牛棚",而正式雇员有私人办公室
- **方法执行**: 面对面坐下→抬头即可提问/讨论/互相纠偏(平行的"儿童游戏"终会变成真协作)
- **结论**: 合同工产出反超高薪正式雇员,归因于可协作的物理与社会结构
- **结果**: "他们无法理解为什么我们可以更有产出"

### 案例 2: 克莱斯勒综合薪酬系统(第8章 8.1,转述 reported_case)
- **输入**: 庞大昂贵的克莱斯勒薪酬系统濒临失败,Kent Beck 受邀顾问
- **方法执行**: 关键改变之一是办公布局:隔断→公共办公桌,消除"私人"空间
- **结论**: 空间改变是"转折点"之一;团队成员把任务置于办公室空间之上
- **结果**: 一年后团队境遇完全不同;XP 方法论在此诞生(与 Cunningham/Jeffries 共事)

### 案例 3: 结对轮换的意外发现(第8章 8.3.3,作者亲历 firsthand)
- **输入**: 作者自认的"最佳搭档"vs 角落里少言寡语的伙计
- **方法执行**: 随机轮换配对,一天/一小时/一星期为周期
- **结论**: "我和那个角落里的少言寡语的伙计一起工作的效率是和最佳搭档时的三倍"
- **结果**: 结论——和所有人都搭档过之前无法预知谁是最优选

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个能力?

1. 团队想引入/试行结对编程,不知道怎么配对、怎么轮换
2. 管理层质疑"两个人一台电脑=浪费一半人力",需要论证与试点方案
3. 新成员入职,需要快速上手方案
4. 迭代结束想开回顾会,但总是开成吐槽大会或没有产出

### 语言信号

- "怎么推行结对编程 / 结对有用吗 / pair programming 怎么做"
- "驾驶员领航员 / 轮换 / 乒乓结对 / driver navigator"
- "新人怎么带 / onboarding 方案"
- "回顾会议怎么开 / retrospective 没产出 / 5个为什么"
- "mob programming / 围攻 / 群战 / spike 调研"

### 与相邻能力的区分

- 与 `test-first-tdd` 的区别: 结对是**人的协作机制**(谁和谁、怎么换);乒乓结对虽以测试为媒介,但本能力关注配对与轮换本身
- 与团队建设/沟通培训的区别: 不做信任游戏、个性测评;只给可执行的角色契约与轮换规则
- 与 `measure-development-value` 的区别: 那里回答"怎么证明结对值得"(跟踪缺陷/质量);这里给机制本身

### AI 编程适配(AI 适配,非原书)

agent 写码、人审码的现状下新增触发情境:

- 人机结对的角色分配: agent 当驾驶员产出代码、人当领航员实时审查追问——本能力的角色契约与轮换纪律可直接转译到人机配对。触发句式: "怎么和 AI 结对写代码 / 人审 agent 代码算不算新型结对"
- 引入 agent 后团队返工/误用变多,想在人机协作方式上做系统性改进——回顾会+5个为什么追流程根因。触发句式: "agent 写码返工多, 回顾会上怎么改进人机流程"

## E — 可执行步骤 (Execution)

**输入契约**: 团队构成(人数、资历分布、是否有新人)、当前协作方式、试行意愿。注意:书中明言结对不能由管理层强制——输入中无团队自愿意愿时,输出应从"伙伴编程"等低阻力方案起步。

**步骤**:

1. **选定协作模式**
   全员抵触→伙伴编程(每日最后1小时互审);局部愿意→核心任务结对;研究型未知→穿刺(小组+时间盒子+问题清单);全员开放→可试围攻。
   完成标准: 模式与任务类型匹配(设计/编码/重构/调试适合结对;纯机械任务可独做)。
2. **结对契约**
   明确:驾驶员操作键盘;领航员实时参与(认可成就与指出笔误同样重要;追问"为什么这么做");5–30分钟换位;卡住回退到定时轮换。
   完成标准: 双方都处于活跃状态——"两个婴儿换玩具"式各自为政即失败信号。
3. **配对与轮换**
   新人×资深见习2周;其余随机轮换(按天/任务/小时);避免固定搭档与同性格互绑。
   完成标准: 一个周期后配对矩阵覆盖团队全员两两组合的大半。
4. **回顾会议**(判停点)
   流程:每人发言(哪些正常/哪些有问题)→对问题连问5个为什么→定位流程缺陷(不责怪人)→选1–2个2%级小改进→指定负责人与度量方式。
   完成标准: 有可度量的小改进项进入下迭代;1小时以内结束。
5. **向管理层汇报口径**
   用数字而非感受:跟踪缺陷数、返工时间、代码量(结对用更少代码完成同样功能)、知识传播案例。
   完成标准: 至少1项前后对比数据。

**输出契约**: 协作模式决议+结对契约条款+配对轮换表+回顾会议纪要模板(含5个为什么记录位)。

**AI 编程适配要点**(AI 适配,非原书):

1. 人机结对契约: agent 驾驶员按小批次产出可整段审读的 diff;人领航员对不满意的实现追问"为什么这么做/为什么选这个库",打回让 agent 重做而非自己接手改——角色不混
2. 审查重点轮换: 每轮会话人只盯 1–2 个维度(行为正确性/CLEAN 特质/测试质量/安全),逐轮换维——以轮换防审查疲劳漏检
3. 乒乓结对变体: 人写失败测试→agent 写最简实现跑绿→人重构与审查→循环;测试是人向 agent 表达意图的媒介
4. 回顾会加"人机协作"议题: 对返工连问 5 个为什么,定位 spec 没写清/批次太大/审查清单缺项等流程缺陷,责怪流程不责怪人(也不责怪 agent),产出 2% 级改进项
5. 新人/新代码库上手: 让 agent 先产出代码库行为地图与测试现状报告,人按"见习"节奏逐模块验收——知识传播手段的对偶用法

## B — 边界 (Boundary)

- **不适用于**: 不是所有人都适合结对、不是所有任务都适合(书中自认);需要深度独处思考的任务、涉密单人场景不强制。
- 管理层强制推行必失败——成功团队都是自发决定("经理,我们要这么做");推行策略必须是自下而上+示范。
- 15%时间节省引 Cockburn & Williams(2000)研究,样本与年代有限;当代远程/异步协作需适配(书中场景全部基于同地)。
- 结对一天极耗精力("精疲力竭但满足")——不可要求全天全周结对。
- 围攻"看上去十分低效",书中也只主张特定项目类型有效;勿当默认工作方式。
- **AI 场景边界**(AI 适配,非原书): 人审 agent 代码不能退化成橡皮图章——只看测试绿条与表面风格等于领航员缺席,结对收益归零;同时不可全托管: 人长期脱离编码细节会丧失审查判断力,应保留亲手写关键模块/测试的时段。

## 相关能力

- 组合(composes-with): `test-first-tdd`(乒乓结对是两者的交叉技法)、`continuous-integration`(结对即写代码时的实时审查)
- 依赖(depends-on): 无硬前置;`clean-code-qualities` 提供结对的公共质量语言
- 对比(contrasts-with): `measure-development-value`(论证手段 vs 机制本身)
