# 变异测试：评估测试集质量

## R（原文摘引）
> 通过在软件中植入人为的漏洞（变异），并检测测试集能否发现它们……这一测试集就需要进行完善。（第18章）

> 当我们把注意力侧重于影响较大的变异之后，等价变异所占的比例下降到了很低的比例（＜3%）。

## I（解释）
**动机**：覆盖率三大缺陷——缺陷分布不均（帕累托）、风险分布不均、覆盖率只反映执行不反映**断言有无**（100% 覆盖也可能不检查输出）。
**流程**：
1. 生成变异（核心算子小子集即够）：改数字常量（X→X+1、X−1、0；指针 0=null）、跳转条件取反、改数字操作符（+↔−、*↔/、<<↔>>）、省略方法调用（返回 0 或删除）；
2. 跑测试集：未被发现的变异=测试集盲区；
3. 逐个补测试用例直到变异可检出（示例：文件写测试必须"写后重开断言内容"，否则 write() 前加 return 的变异不可见）。
**三优化**（使可行）：直接操作二进制（免重编译）、变异模板（运行时条件生成不同变异版）、只变异测试覆盖到的代码且只跑涉及该代码的测试。
**等价变异处理**（对程序无影响的变异，Jaxen 实验占未检出 40%，手工判定昂贵）：**影响排序法**——①覆盖率影响=加入变异后代码覆盖发生变化的方法数；②先决/后置条件影响=记录方法参数与返回值，变异后重跑统计状态改变数；侧重高影响变异后等价占比降到 <3%；**高影响变异未被检出即应改进测试集**。
工具：Javalanche（自动批量+影响排序）、μJava（交互式）。实测量级：10 万行 AspectJ 4.7 万变异、8 核 <2 小时；单元测试集仅杀 53%。

## A1（原书案例）
AspectJ 测试集评估：发现 `staticAndInstanceConflict` 等真缺陷漏报错——53% 杀灭率直接量化了测试集弱点。

## A2（情境应用）
评估/改进既有测试集：
1. 选核心模块（帕累托 20%）做变异；
2. 按影响排序取 top 变异跑测试；
3. 未杀灭的高影响变异逐个写针对性测试（先检查断言是否缺失）；
4. 输出杀灭率报告+新增用例清单。

## E（评测）
- 输入：一段含 2 个断言缺失的测试代码与被测函数。
- 输出：变异清单（标注预期可杀/不可杀）+缺失断言定位。
- 通过标准：正确定位"写后未重开断言"类盲区；能解释等价变异为何需要影响排序。

## B（边界）
须高度自动化才可行；等价变异无法完全自动判定；与覆盖率互补（变异贵而深刻、覆盖便宜而浅）；运行成本高→聚焦核心模块。
