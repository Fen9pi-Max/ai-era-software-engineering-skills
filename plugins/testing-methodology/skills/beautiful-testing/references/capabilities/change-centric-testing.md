# 以变化为中心的测试

## R（原文摘引）
> 实际变化之外的三级分离是基本安全的，因为f3的改动所造成的任何后果，可以在测试被改变方法及其所有二度分离以内的方法时被检测出来。（第11章）

## I（解释）
**新项目**：PRD 线框图为功能区标顺序号（F-008→F-008001），测试用例命名含功能区标识；**代码签入信息写入功能标识**（含缺陷修复签入）；QA 按标识查询签入→运行关联测试（单元/冒烟/夜间/BAT）。
**遗留代码建基**：
1. 全量跑测试+Valgrind/Callgrind 生成调用关系图（callgrind_annotate 三列输出；KCachegrind 可视化导出 dot 入库）；
2. 建测试↔源文件/函数多对多映射入库；
3. gcov 累积覆盖率→识别覆盖差距→针对性补测计划；
4. 每日定时 diff 源树列改动文件与行。
**影响分析**：函数三分类——源函数（被多人调用，改动传播广）、同步函数（不被调用，无传播）、管道函数（双向）；经验规则：**三度分离以外基本安全**——跑被改方法的测试+调用者测试+递归二度。
**执行策略**：动态变化测试清单与固定功能测试集并行；全量系统测试以较长间隔定期执行（非每夜）。

## A1（原书案例）
大型遗留代码库：被遗漏错误清单变短、夜间全量套件数量大幅减少；"知道要测试什么是一种美，知道正在测试什么是一种美"。

## A2（情境应用）
大代码库回归时间失控时：
1. 生成调用图与测试映射；
2. 每日 diff 出改动集；
3. 按三度分离规则生成动态测试清单（源函数改动扩到二度调用者）；
4. 覆盖差距区标记风险并排补测计划。

## E（评测）
输入：一张调用图（标注一处改动）+测试映射；输出：应跑测试集。通过标准：改动在源函数时扩展到调用者二度；同步函数改动只跑自身测试。

## B（边界）
需要工具链（Callgrind/gcov）与映射维护成本；无映射时先用功能区标识从新代码做起；UI 级变化影响仍需探索性验证。
