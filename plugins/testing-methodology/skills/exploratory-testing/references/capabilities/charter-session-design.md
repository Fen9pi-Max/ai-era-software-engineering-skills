# 探测章程设计与限时探测会话

## R（原文摘引）
> 目标：你要探索何处？…资源：有什么资源是你需要带着用的？…信息：你希望找到哪种信息？（第2章2.2）

> 一个优质探测章程即是一个提示信号：它指出了灵感之源，又避免了对行动或结果做出事无巨细的规定。（第2章2.3）

## I（解释）
章程 = 探索的使命说明，源自杰斐逊给刘易斯与克拉克的信。三段模板：
1. **目标**：探索何处——一个特性/需求/模块，不含整个系统。
2. **资源**：带着用的东西——工具、数据集、技术、配置、相互依赖的特性。
3. **信息**：想找哪类信息——安全性/性能/可靠性/容量/设计一致性…或"找出让客户无法完成有效购买的方法"。
质量判据：过细=伪装的测试用例（浪费文档时间）；过宽="探索整个系统"永远完不成。执行用 SBTM 限时探测会话：会话前定章程、会话中原生态记录（思路/问题/风险/惊喜/bug）、会话后向干系人汇报能力与局限。章程是流动过程，贯穿开发周期持续产生，不要预先全部排定；发现脱离章程的诱惑就记下一条新章程。

## A1（原书案例）
- 杰斐逊 1803 年信：探索何处（密苏里河及支流）/可用资源（船只、勘测工具、礼物）/所寻信息（可商用的跨大陆水路），三年后刘易斯与克拉克带回 7000 英里地图。
- 反例章程："探索整个系统寻找安全问题"——既大又不明确，可能数周仍不知是否完成。
- 章程灵感五来源：需求讨论（Alex 听到"改用户名"就记章程）、隐性期待（横切质量标准）、干系人问题（"黑客能否挟持通知系统发垃圾邮件？"）、现有工件（代码注释"我也不知道为什么行得通，别碰它"、bug 库、支持日志）、探测中的新发现。

## A2（情境应用）
1. 收到"探索一下 X 功能"时，先补三段：目标=X 的哪个子区域；资源=用什么账号/数据/工具/相邻特性；信息=要回答的风险类别。
2. 校准价值：问干系人"如果我发现 X 与 Y 的交互问题，你想知道吗？"再开工。
3. 开 45–90 分钟时间盒会话，边探边记；结束后写三行汇报：覆盖了什么/发现了什么/还剩什么。
4. 会话中被诱惑偏题时，记新章程入池，本次不追。
5. 章程池每周重排，不一次排死。

## E（评测）
- 输入：任一特性描述（如"用户可修改用户名"）。
- 输出：≥3 条章程（各含目标/资源/信息三段、信息类型不同）+1 个会话执行计划（时长/记录方式/汇报对象）。
- 通过标准：每条章程可独立判断"做完了吗"；无一条是单测用例级细节，也无"整个系统"级宽泛。

## B（边界）
不覆盖会话内的具体测试设计（用 test-heuristics-cheatsheet）；不判断行为对错（用 oracle-strategies）；汇报细节见 stakeholder-reporting-stop-criteria。数据来自第2章、第1章1.3。
