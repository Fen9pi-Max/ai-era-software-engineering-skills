# 观察细节与可测试性

## R（原文摘引）
> 可测试性是可视性和控制。一个可测的系统既能提供其内部工作情况的可视性，又能提供足够的控制点可实施操纵。（第3章3.3 引 Kaner/Bach/Pettichord）

> 人们越是关注他们视野范围内的一切事物，就越有可能会忽视了那些意料之外的事物。（第3章3.1 引 Simons）

## I（解释）
观察四招：
1. **防无意视盲**：越专注一个维度越漏其他——刻意轮换关注维度、屏幕不同区域、带期待找惊喜。
2. **深挖问题**：把粗浅问题升级——"安装向导不出错吗？"→"刚装好的软件能用吗？"。测试报表不止看生成，看不同场景下数据是否准确。
3. **明察秋毫**：全感官捕捉微线索——UI 闪烁、意外噪音、发热、内存爬升；易出小毛病的系统可录屏回放。
4. **可测试性布置**（可视性+控制）：系统监视器（CPU/内存/依赖库）、文件系统活动监控、网络流量观察、浏览器开发者工具、数据库触发器；有能力就直接加钩子（详细日志模式、隐藏字段、诊断工具，发布前清理）。
控制台与日志：`tail -f production.log`、`tail -f ... | grep ERROR`；日志能把 UI 操作与底层调用关联——作者靠日志发现 Rails 搜索页每次都触发 Paperclip 保存附件（UI 完全不可见的性能地雷）。

## A1（原书案例）
- 月球漫步熊视频：全场注意力在数传球，穿熊皮的人滑过无人看见——无意视盲实证。
- 安装程序：测试员只看向导无报错，漏掉"装完不能用"（关键文件缺失）；补救=装后行动清单（文件落位/注册表/启动执行基本操作）。
- 深夜硬盘"嗡嗡"声：死寂房间里注意到周期性硬盘加速→软件为阻止休眠周期性唤醒→违背核心需求，推迟一天发布。
- Paperclip：一次用户搜索日志中出现两次 "Saving attachments"。

## A2（情境应用）
1. 接手任一被测系统先布防：找到所有日志文件与控制台，开两个终端 `tail -f` + grep；记录可用的系统监视器。
2. 每次探索前列"深挖问题清单"：当前验证的问题是什么？更深一层的问题是什么？
3. 观察时轮换焦点：这一轮只看日志，下一轮只看网络/内存/屏幕角落。
4. 对可疑会话录屏，事后快进找差异帧。
5. 发现系统难观察时，向开发要可测试性钩子（详细日志、测试模式、诊断页），并确认发布前可摘除。

## E（评测）
- 输入：任一 Web 应用/服务的描述。
- 输出：监控布置清单（日志/控制台/系统监视/网络/DB 各至少一项具体落点）+ 粗浅→深度问题升级示例 ≥3 组。
- 通过标准：每项监控写明"能看见什么原本看不见的行为"；问题升级能落到可执行的验证动作。

## B（边界）
观察不负责判断对错（oracle-strategies）；日志证据的排障用法见 intermittent-bug-hunting；不覆盖具体 APM 产品用法。依据第3章。
