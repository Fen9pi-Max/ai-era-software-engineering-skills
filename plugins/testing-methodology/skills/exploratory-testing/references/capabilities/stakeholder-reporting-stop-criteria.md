# 向干系人汇报与探索停止标准

## R（原文摘引）
> 不能把探测章程或探测会话的数量用作成功/失败的指标，因为对于探测章程和探测会话来说根本就没有成功或失败的概念。（第13章13.6）

> 时间没了就停下来，这应该算是最常用的标准了。不幸的是，这往往也意味着…最差的标准。（第13章13.5）

## I（解释）
**停止标准**（判断某区域探索是否充分，替代"时间没了"）：①未决问题都答完了；②学不到新东西（功能/局限/风险已评估）；③更多信息不会带来改变（干系人明确不需要）；④其他信息的价值更大。若据此该停而计划表没做完→是估时太短，不是探索太慢。
**站会汇报**：别答"昨天探索今天继续探索"；答——昨天发现什么有趣的东西（"导入空文件导致进程死掉，批次剩余文件全不处理，已报 bug"）/今天探索哪些风险/需要什么（信息/可测性改进/环境/反馈："再多找几个这样的 bug 值不值？"）。
**向决策者简报**三问模板：①探索了什么（区域+深度："大部分时间在 Web 界面，API 很少"）②发现了什么（含运转正常部分："会话超时两个严重问题已修复"）③还剩什么未知（"API 覆盖差，Web 有超时问题则 API 大概率也有"）。原则：只陈述外部可验证的事实；"它还没好"是结论，"发现如下阻碍型缺陷"才是证据——让决策者自己下结论；留心听反馈校准干系人重视的信息；但若认为不找某类风险是失职，要说清后果。探索估算并入整体估算（T 恤尺寸/斐波那契），不单列；探索发现大量惊喜=检查之网有大洞，修流程。

## A1（原书案例）
- 站会范例：畸形数据探索→空文件杀进程→今日继续探畸形数据→先问"再找出几个这样的 bug 值不值？"
- 简报范例：三段式回答覆盖深度、已修复问题、API 覆盖缺口及推断。
- "我们没有瞎搞事"：程序员视角的每个非法 HTML bug=新需求——期望值与范围要在汇报中说清（与第12章呼应）。

## A2（情境应用）
1. 每个探测会话结束当天，用三问模板写 ≤150 字简报存档。
2. 站会前三问自己：有趣发现？今日风险？需要什么？——照此回答。
3. 对每个进行中的探索区域跑一遍 4 条停止标准，记录判定。
4. 汇报中把每个判断改写成"观察到 X"的事实句；对重视度存疑的信息附一句"这类信息你想继续要吗？"
5. 把学到的探索技巧（怎么进数据库、哪里拉数据）上团队维基——智慧结晶别埋没。

## E（评测）
- 输入：一段探索工作记录（区域/发现/剩余疑问）。
- 输出：三问简报一份 + 对该区域的停止标准判定（逐条）。
- 通过标准：简报含覆盖深度、正常项与未知项三要素；无会话数/通过率类指标；无未支撑的结论句；每条事实可被第三方验证。

## B（边界）
不覆盖探索与检查的流程整合（overview 保留）与估算细节（并入整体估算即可）；章程价值校准见 charter-session-design。依据第13章13.5-13.6。
