# 建模工作流：从单功能到测试条件（TCon）

## R（原文摘引）
> 这 15 条枝干就像遍历树的基路径一样，我把它们称为"测试条件（Test Condition）"。

> 画 Model 的过程总是能帮助我们识别出很多问题……拿着这个 Model 和需求人员或者开发人员交流时，它非常直观。

## I（解释）
选定 PPDCS 特征后的建模与产出流程（收银机 14 步浓缩为通用 8 步）：
1. **定单功能边界**：分析输入（分类）与输出（列出）；不影响业务逻辑的参数暂不单列；与实现相关的细节不关注。
2. **单功能拆分**：复杂输出/逻辑 → 拆（如输入数据处理 M1 / 业务规则处理 M2）；复杂交互场景移 F 做探索性测试。
3. **按风险排优先级**：核心、风险高的先建模（"万一后面没时间了呢？"）。
4. **建模**（按选定特征）：
   - 判定表：参数纵列、每行一条规则；从最简单规则开始逐条填；不影响规则的参数删掉（归 M1）；规则冲突用不关心项"-"；存疑处标红问号。
   - 等价类：为每个 Data 列有效 VEC / 无效 IVEC，编号 A-V-1 / B-IV-4 式。
   - 流程图/状态图：识别 MF/AF 或状态与转换事件。
5. **查完整性**：判定表转判定树找悬空节点（有实际意义的补成规则）；流程图查未覆盖分支。
6. **得出 TCon**：判定表每行规则 = 1 个 TCon；可计算覆盖率但不盲目求 100%（剩余 TCon 与其他未测内容比优先级）。
7. **等价类覆盖方式四选一**（按风险）：Weak Normal（各 Data 有效类）/ Strong Normal（有效全组合）/ Weak Robust（有效+无效，每条只含 1 个无效类）/ Strong Robust（全组合）。
8. **Given-When-Then 描述**：Given=预置状态（隐含输入）；When=操作/传参；Then=反应+系统状态变化（系统级须检查全局影响如库存/营业数据）。
建模中每个疑问记入问题列表——未运行一个测试即产出大量问题/风险。

## A1（原书案例）
收银机打印小票：M2 判定表 15 条规则（6 条存疑待澄清），M1 等价类含"特殊字符/中间空行/数字非5位"等 IVEC；最终 2 个单功能、39 个 TCon、16 个需求疑问点。

## A2（情境应用）
对任一单功能（优惠规则计算、表单校验、状态机、流程审批）：
1. 按第 1-3 步定边界拆分排优先级；
2. 建判定表/等价类表（表格输出）；
3. 自查完整性（转树/查悬空）；
4. 产出 TCon 编号表（TCon-001…）+ GWT 描述 + 疑问清单。

## E（评测）
- 输入：一个"满减+折扣冲突取其一"式的优惠规则描述（植入规则遗漏与模糊点）。
- 输出：判定表 + TCon 表 + GWT + 疑问清单。
- 通过标准：判定出可检出植入的模糊点（进疑问清单）；TCon 与规则行一一对应；无冗余参数列。

## B（边界）
选哪个特征建模先过 ppdcs-model-selection；TCon 是粗粒度条件，具体取值见 test-design-4steps；写不写 GWT 由上下文定（外包/审计/执行者未参与分析时必要）。
