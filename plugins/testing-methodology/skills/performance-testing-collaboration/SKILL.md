# 性能测试协作方法

## R（原文摘引）
> 从承诺达到一定水平的性能，转变为承诺报告在什么样的条件下性能目标将无法实现。（第4章）

> 我再也没有在和Sam确认我的怀疑之前，就宣布性能问题的原因。（第4章）

## I（解释）
**需求转换**：拒绝不可验证承诺（"100%情况下5秒内显示"）；改承诺"报告何种条件下目标无法实现"；设定**报告触发阈值**（如 >5% 请求超 5 秒、>1% 超 8 秒须报开发组长；最高负荷 1 小时 95% 达标为验收线）。
**性能测试检查点**（替代"用例"）：按用户负荷分级（1 用户基准→10→100~3000 逐级→1000 用户 9 小时压力），每级验证使用模型中每个任务；多角色评审（PM 按合同/测试经理按交付/技术负责人按决策价值/开发按信息价值）；直接映射客户最终报告项。
**使用模型共建**：客户+开发+测试白板画高峰期最流行条目+高风险功能区流程图；开发指出底层可互换的冗余活动；共识"对此建立信心前，测其他部分是浪费"。
**异常排查协作**：
1. 重跑测试+**同步手动使用**确认现象真实；
2. 数据（表格/图表）带入会议；第三方佐证；
3. 与开发确认怀疑前不宣布原因；开发不以"工具问题"驳回——建立"一起看奇怪结果"机制；
4. 警惕环境根因（疑似内存泄漏实为许可证 3 并发限制）。
**延迟排查排除法**：识别模式特征（0.25/4.25/8.25s 递增 4 秒）→系统排除可控部分→跨部门正式备忘录→现场复现定位（物理损坏路由器）。
**"用户说慢"诊断**：看原始反馈表而非汇总→找到具体评论者新旧系统现场模拟计时（新 2.5 分钟不熟练 vs 旧 47 秒熟练）→判定为 UI 设计影响效率而非响应时间。
**非技术解法**：架构扛不住峰值时，UI 重设计使高消耗操作只在流程末端出现，营销期后恢复。

## A1（原书案例）
Scott Barber 财富 50 强 eVersity 四个关键事件（100% 需求失败/假内存泄漏/改 UI 降负载/网络 4 秒延迟），每次化解都靠协作而非测量技术。

## A2（情境应用）
启动性能测试：
1. 与干系人把性能承诺改写为触发阈值+报告义务；
2. 白板共建使用模型并排序功能区；
3. 检查点表（负荷级×任务）；
4. 排查规则上墙：先自证现象→数据进会议→不先宣布原因。

## E（评测）
- 输入：一份含"100% 保证"式性能需求+一段疑似泄漏的现象描述。
- 输出：改写后的阈值式需求+检查点骨架+排查步骤。
- 通过标准：无不可验证承诺；检查点含负荷分级；排查含"重跑+手动佐证+不宣布原因"三规则。

## B（边界）
非技术解法需多角色工作组（含财务）；深度调优与压测脚本工程不在本卡范围。
