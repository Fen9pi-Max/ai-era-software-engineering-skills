# 测试结果验证与僵尸测试防御

## R（原文摘引）
> 工具不会告诉你一个测试通过还是失败；它仅仅能告诉你测试结果和你期望的结果是否匹配。（第0章 0.2.4）

> 在你的自动化测试套件中谨防"无用"测试用例。（第15章）

## I（解释）
1. **期望结果负责制**：期望错了工具照报全绿——期望结果必须有人审查并对齐需求（P9）。
2. **验证手段优先级**：屏幕文本/控件属性/API/数据库校验 > 截图比对；尽量避免坐标/位图锚定的验证（脆弱且维护贵）。
3. **僵尸测试防御**：
   - 静态分析（如第15章 Checkman for eCATT）：自动发现从未使用的模块、不覆盖任何代码的脚本；
   - 测试生命周期管理（第2章状态机）：开发→评审→候选（连续失败退回）→有效→挂起→度量后退出删除；
   - 定期审阅代表性测试方案。
4. **部分 oracle 也有价值**：探索性/猴子/可靠性测试可只检查"系统存活"，能自动跑海量测试本身就是收益。
5. **报告面向受众**：过滤并解释原始结果，让人读得懂；绿条不代表没问题。

## A1（原书案例）
- 第15章 SAP：代码被注释后遗忘的脚本永远显示绿色——"僵尸测试"由此得名；Checkman 静态分析抓出从不覆盖代码的脚本。
- 第19章：监测工具发现"验收测试其实吞掉了数据"——通过的测试通常无人检查，可能掩盖严重问题。
- 第2章：测试生命周期状态机周期性清理低价值测试，防止套件腐化。

## A2（情境应用）
接手或审查一套既有自动化套件时：
1. 抽 10 个"长期绿色"的测试，人工核对期望结果与当前需求——找僵尸。
2. 若无静态分析，写一个简单脚本扫描：断言被注释的、空验证函数、从不失败(历史100%通过且从不改动)的用例。
3. 给套件引入生命周期标签（active/candidate/suspended/retire），连续 N 天失败退回开发，一周无失效转有效。
4. 检查验证手段：列出仍用截图/坐标比对的用例，排期改为属性/文本校验。

## E（评测）
- 输入：一套含 3–5 个"僵尸模式"（注释掉的断言、空检查、过时期望）的样例测试代码/描述。
- 输出：逐个测试的判定（可信/疑似僵尸+证据）+ 修复建议。
- 通过标准：能识别全部植入的僵尸模式；建议含生命周期与静态分析两项治理措施。

## B（边界）
"从不失败"只是嫌疑不是罪证——冒烟测试可以长期通过；判定需结合覆盖分析；部分 oracle 场景（猴子测试）不适用"期望结果负责制"的全量要求。
