# 自动化试点项目方法论

## R（原文摘引）
> 对于那些打算应用自动化测试的公司，最重要的建议是要从小范围开始应用。试点项目是个好主意，在将自动化测试扩展到更广的范围之前先在小范围内尝试不同的方法，来判断哪种方法最好。（第0章 0.1.8）

> 从一个有限的、但是自动化之后会提供实际值的测试集合开始是比较重要的。（第25章）

## I（解释）
试点是廉价发现"该不该继续/该不该停手"的机制：
1. **目标先行**：试点必须有书面目标与时间盒（典型3个月）；无目标的"试点"会直接变成失控的实际项目（第6章项目1之死）。
2. **选代表性用例**：挑稳定、重复执行、有实际价值的手动用例（配合 automation-decision-checklist）。
3. **量化基线**：以历史手动工时为基线，记录自动化同等测试的工时，形成 ROI 数据（喂给 roi-evaluation）。
4. **顺带建公共库**：启动/关机、时间同步、恢复初始状态、环境初始化等公共脚本在试点期一并建立。
5. **quick wins 优先**：安装软件、关机任务等外围自动化先出成果，证明价值换取持续支持。
6. **同步立标准**：命名约定、脚本头、存储位置在试点中定义（见 testware-standards），之后构建到工具里强制执行。

## A1（原书案例）
- 第6章：项目1（无管理层支持、无目标、对未上线系统自动化）半年被取消；项目2（3个月有明确目标试点+公共元素+标准）成功并持续扩展。
- 第17章 Google：试点的价值恰恰是廉价地发现工具不合适、及时止损迁移 WebDriver。
- 第25章 NATS：3个月试点产出 12 个测试规程的回归包，手动 20 分钟的测试缩短一半时间。

## A2（情境应用）
启动自动化倡议时：
1. 写一页试点章程：目标（具体可评）、范围（哪些用例）、时间盒（如8–12周）、成功标准（如：X 用例自动化、执行时间降 Y%）、资源（1名专职工程师+工具预算）。
2. 每周向管理层发一屏进展（量化数据+发现的 bug）。
3. 试点结束输出三选一决策：扩大 / 调整方法再试一轮 / 止损停止，并附 ROI 数据。

## E（评测）
- 输入：一个团队的现状描述（产品、手动测试规模、管理层态度）。
- 输出：试点章程（含目标/范围/时间盒/成功标准/quick win 清单）。
- 通过标准：目标可量化可评判；范围 ≤ 数十条用例且全部通过决策清单筛选；含止损条件。

## B（边界）
试点不能替代管理层支持的争取（0.1.2：自下而上不可持续）；若组织已确定大规模投入可缩短试点但不可跳过标准建立；敏捷团队可按第1章以"工程冲刺"节奏替代传统试点。
