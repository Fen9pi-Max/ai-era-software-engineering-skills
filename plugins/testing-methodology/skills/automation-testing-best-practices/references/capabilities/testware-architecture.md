# 测试件架构：抽象层次设计

## R（原文摘引）
> 对于成功的自动化测试执行来说，（至少）有两个主要的抽象层次：将工具和工具特定细节与结构化的测试件分离开来；将测试（即测试人员所从事的工作）与结构化的测试件分离开来。（第0章 0.2.1）

> 公司放弃一个测试执行工具是因为测试脚本维护费用很高！（第0章）

## I（解释）
测试件（脚本、数据、文档、工具）是长期资产，其架构决定自动化成败：
1. **工具隔离层**：只有最底层脚本使用工具语言；高层结构化测试件与工具无关。换工具/应用迁移时只改底层。
2. **领域测试层（DSTL/关键字驱动）**：测试人员用领域相关的关键字写测试，不懂编程也能编写和运行用例。
3. **实现手段**：框架、对象映射（object map）、UI 包装器（wrapper）、setter 链默认值模式（跳过的参数取默认值）。
4. **抽象层"正确厚度"**：太薄→一处业务变更要改数百用例；太厚→自造 DSL 维护贵、架构师成瓶颈。用编码标准+优秀示例+架构师持续跟进来治理。

## A1（原书案例）
- 第18章市场交易系统十年三框架：正确厚度的抽象层支撑 1.5 万–5 万用例回归；框架C因 XML 自造语言太厚，用例长期停滞在约1000个。
- 第10章英国保险：测试与工具解耦的抽象设计让自动化活过工具更替，17年后每月运行 500 万次测试。
- 反例（第16章）：登录流程加一个 Captcha，录制/回放的 100 个脚本每行都要改；功能调用抽象则只改一处。

## A2（情境应用）
当你要搭建或重构自动化测试框架时：
1. 画三层图：用例层（领域关键字）→ 功能模块层（每编辑器/对话框一个模块）→ 工具适配层（唯一允许出现工具 API 的地方）。
2. 为 GUI 对象建集中 object map，禁止用例直接写控件坐标/位图。
3. 评估厚度：如果一个常见业务变更（如登录方式改变）需要改 >5 个用例，抽象太薄；如果测试人员看不懂用例且所有新关键字都要等架构师，抽象太厚。
4. 区分角色：架构师定结构与编码标准，自动化人员实现模块，测试人员只用关键字写用例。

## E（评测）
- 输入：任一真实项目的自动化现状描述（或一套脆脚脚本）。
- 输出：分层架构方案 + "变更影响面"分析（模拟登录方式变更/换工具，列出各需改几处）。
- 通过标准：换工具场景只需重写工具适配层；模拟业务变更影响 ≤5 个模块；非程序员能读懂用例层。

## B（边界）
不适用于一次性/丢弃型脚本（第19章：disposable script 有意省略抽象）；不解决管理层支持问题（见 pilot-project-methodology）；抽象层本身也是软件，需按 testware-standards 维护。
