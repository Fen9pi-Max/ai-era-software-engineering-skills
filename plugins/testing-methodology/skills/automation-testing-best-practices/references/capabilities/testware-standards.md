# 测试件标准、复用与文档

## R（原文摘引）
> 标准的命名约定，存储测试件条目的统一的地方，创建测试的标准方式……每个脚本的标准文件头——需要达成一致并且普遍使用的事情远比你能想到的还要多。（第0章 0.2.2/0.2.3）

> 去找寻那些可以复用的模块，而不是一切都从头编写。（第0章）

## I（解释）
1. **标准项**：命名约定（沿用被测系统的模块/对话框命名，避免基线漂移）、统一存储、脚本标准头（作者/状态/构建目标/依赖/平台/时长/修正历史/等价手动脚本引用）、归档方式。
2. **落地方式**：在试点中定义 → 写进编码规约 → 尽量构建进工具强制（模板、下拉列表）→ 允许经验证的例外 → 随成熟度更新。
3. **复用**：DRY；区分项目特定函数与通用复用函数（第16章目录结构）；每编辑器/对话框一个模块（第27章）。
4. **文档与灵活性**：脚本头写目的/输入输出/前后置条件/错误条件，可搜索；灵活脚本允许跳过空字段取默认值；测试打标签+测试选择器快速选子集；脚本拥有者制+配置管理检入检出。
5. **自动化代码也是软件**：审阅代表性方案+静态分析（见 results-verification-defense）。

## A1（原书案例）
第6章项目1：同一组件因命名不同被重复创建；第15章 SAP：编码指南+代码审查+Checkman 支撑 300 万行自动化代码跨国复用；第27章：模块名映射产品模块名+编辑器下拉提示关键字。

## A2（情境应用）
套件超过 ~50 个脚本或超过 2 人维护时：起草一页编码规约（命名/目录/脚本头模板/复用规则）；建模板让 IDE 自动套头；每季审一次例外清单。

## E（评测）
输入：一套无标准的散乱脚本描述；输出：规约文档+重构后的目录/命名方案+脚本头模板。通过标准：任一脚本能从名称定位到被测模块；模拟"对象改名"只需改一处。

## B（边界）
一次性脚本可豁免（第19章）；标准不宜僵化——须有更新与例外机制；过重的文档要求会压制脚本产出，够用即可。
