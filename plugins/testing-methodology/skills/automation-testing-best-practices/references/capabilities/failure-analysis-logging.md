# 失败分析与日志设计

## R（原文摘引）
> 当自动化测试失败时，你可能仅仅知道测试的 ID，而并不清楚这个测试到底是做什么……在写 bug 的报告前需要重建 bug 的上下文信息，这需要一些时间。（第0章 0.2.8）

## I（解释）
自动化失败分析比手动更贵，因为上下文丢失。设计规则：
1. 脚本记录充分日志：步骤、输入数据、被测版本、硬件/软件环境（纳入配置控制）。
2. 校验失效瞬间自动输出报告+截图（第27章：Word 文档含脚本+检查结果+现场截屏，使错误定位成本最小）。
3. 故障签名/模式库（第2章）：失败与错误信息、测试名关联，自动分类；正确率达标（60–80%）后才启用自动识别，新故障人工补充标记。
4. 猴子测试日志要求：蓝屏后仍保留、可回放重现、崩溃时截图+资源使用。

## A1（原书案例）
第27章 RightNow：失效瞬间自动生成 Word 报告；第2章 JET：故障签名自动分析 + 邮件/XML/网站报告 + EMMA 覆盖率；第24章：猴子日志蓝屏保留可回放。

## A2（情境应用）
设计框架的失败处理：失败时自动 dump（用例元数据+最近N步日志+截图+环境信息）；建立故障分类表，重复失败按签名聚类；每周review 未归类故障补签名。

## E（评测）
输入：3条失败记录（仅测试ID+裸日志）；输出：补齐上下文所需日志清单+故障签名方案。通过标准：单凭自动报告即可定位到模块级，无需回放。

## B（边界）
日志本身有成本（体积、敏感数据脱敏）；不解决"失败是环境还是真缺陷"的判定（见 automation-pitfalls 的环境同步治理）。
