# 评估结果：绝不和始终、替代资源与近似神谕

## R（原文摘引）
> 任何时候，如果所做探索导致系统违背了某条"绝不"或"始终"规则，它就是一个重大问题。（第5章5.1）

> 你可以从结果的特征入手进行评价，而不是它的精确值。（第5章5.3）

## I（解释）
三层神谕，按顺序取用：
1. **绝不和始终**：从三处提炼不可侵犯规则——核心功能（"如果其他功能全军覆没，什么必须仍能运转？"电梯游说三问）、质量因子（准确性/可靠性/可用性/安全性…翻译成绝不/始终句）、干系人风险（噩梦头条）。违背即重大问题，无需预期值。
2. **替代资源**：①内在一致性——同一操作在两个相似页面行为应一致、相似 API 调用参数约定应一致、日志格式应一致；②标准——HIPAA/萨班斯、平台 UI 指南、W3C、OWASP（先确认干系人认账该标准）；③对比——公司其他产品、同类软件的惯例（找回密码=邮件加密链接，明文发密码会被嘲笑）。
3. **近似**（对付复杂/非确定性系统）：①参照范围（燕子 12.8 m/s vs 维基 11–20）；②特征评估（随机数生成器跑千次看分布与模式）；③结果反转（平方根再平方；翻译再反译；A→B 与 B→A 路径长度应相近）；④选择环境（排队模拟全设最大/最小值放大参数效果）。

## A1（原书案例）
- 会计软件：账目必须**始终**平衡；软件**绝不**创造或摧毁金钱。
- 支付系统：**始终**能对购买收费，**绝不**重复收费——同一风险的两种表述。
- 燕子空速：扯淡输入（0 克）得 -5 m/s 明显错；正常输入得 12.8 m/s，与维基范围比对通过合理性测试。
- 随机数生成器：20 次内连续两次产出相同 0–9 序列→不够随机。

## A2（情境应用）
1. 探索前先和干系人列绝不/始终清单（每条写明来源：核心功能/质量因子/风险）。
2. 观察到可疑行为时按序套：违背绝不/始终？→与系统自身别处一致？→与标准/同类惯例一致？
3. 都不适用时上近似：找结果合理范围、看统计特征、做反向运算、造极值环境。
4. 报告时写"观察到 X 违背了'始终 Y'规则"，不写"这是个 bug"的结论。

## E（评测）
- 输入：任一系统描述（如"购物车+支付"）。
- 输出：绝不/始终清单 ≥6 条（标注来源类别）+ 每类至少一个替代资源/近似神谕的具体用法。
- 通过标准：清单中无同义重复；近似手段针对的是"无法精确算预期值"的场景；每条规则可被第三方独立检验违背与否。

## B（边界）
标准类神谕需干系人确认适用，避免拿未承诺的标准报 bug；需求期的"如果的话"预防见 requirements-exploration。依据第5章。
