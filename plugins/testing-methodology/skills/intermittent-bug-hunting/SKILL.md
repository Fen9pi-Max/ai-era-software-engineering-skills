# 不可重现缺陷调查

## R（原文摘引）
> 搞定这些神秘的间歇性缺陷的关键在于，要意识到，只要能发现并控制影响其行为的所有变量，任何缺陷都是绝对 100% 可重现的。（第11章11.6）

> 真正的间歇性缺陷往往会涉及多重诱因，它从来都不是寻找单个变量那么简单。（第11章11.6）

## I（解释）
四步流程：
1. **收集证据**：从历史蛛丝马迹搜证——日志、截图、输入数据、控制台错误；找模式：特定时段/星期？特定机器/配置/用户？与操作时机或活动水平相关？
2. **绞尽脑汁想嫌疑变量**：列全可能影响行为的变量（重温微妙变量：配置、顺序、时机、活动水平、计数）。预设多因——真实案例就是两个变量相乘。
3. **状态模型理解时机**：多数间歇缺陷与时机有关；用状态图捕捉只存在极短时间且无法直接控制的中间态（锁、超时、竞态窗口）。
4. **协作**：拉齐互补技能（资深测试懂系统全局+资深程序员懂数据存储与线程）；单人单干常失败，技能齐了才看得见全貌。
结局两种：能按需触发（最好），或至少**让问题更频繁发生**——找出变量后即使无法完全控制，通常也足以加大发生频率，为定位赢得入口。

## A1（原书案例）
PC 后台监控程序间歇崩溃：团队先放弃、发布后几乎每位客户都遇到；四名队员（两名资深测试+两名懂数据存储与线程的资深程序员）闭关一周逐行查源码，根因=两个变量相乘：客户端活动水平 × 服务器可下载更新数量，触发排它锁冲突。发现变量后仍无法按需触发，但足以让它更频繁发生。

## A2（情境应用）
拿到"无法重现"的 bug 报告时：
1. 先收集而非复现：所有相关日志、报告人环境、发生时间点，做成时间线。
2. 列嫌疑变量矩阵（变量 × 可观察 × 可控制 三列），标注哪些只能间接影响。
3. 对时机敏感的假设画状态图，标出怀疑的中间态及其窗口。
4. 组队：至少一名懂该模块实现的人+一名懂系统行为的人。
5. 设计"放大试验"：把可控嫌疑变量推向极值使问题高发，再二分收缩。

## E（评测）
- 输入：一份含糊的间歇性 bug 报告（症状+大致频率+环境）。
- 输出：证据时间线 + 嫌疑变量矩阵（≥8 个变量，标可观察/可控制）+ ≥3 条放大试验设计。
- 通过标准：矩阵含至少一个计数/时机类微妙变量；放大试验写明每条 manipulated 变量与预期效果；流程体现协作角色分工。

## B（边界）
