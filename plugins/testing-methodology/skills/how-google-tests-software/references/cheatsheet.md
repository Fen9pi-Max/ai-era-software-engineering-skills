# 决策规则速查 — Google软件测试之道（How Google Tests Software）

| 能力 | 一句话规则 |
|---|---|
| ACC 特质-组件-能力测试计划法 | 用形容词(特质)×名词(组件)×动词(能力)三步矩阵替代散文测试计划，30分钟出80%完整性 |
| 风险分析：失败频率×影响热图 | 每个能力按频率4档×影响4档定性打分，交点平均出红黄绿热图，先测风险最大的 |
| 小/中/大型测试规模模型 | 测试按范畴规模分小/中/大三档并施加环境与依赖约束，比例参考70/20/10，用分层覆盖率诊断失衡 |
| 八种漫游测试（结构化探索式测试） | 用游客漫游隐喻（购物/学生/地标/通宵/危险地带等8种）给探索式测试主题与结构，配合ACC行列分工防重叠 |
| SET 早期介入：设计评审与可测试性 | 立项后即介入：六维度评审设计文档、第一个实现接口协议的mock/fake、轻量自动化框架配合提交队列 |
| 自动化范围取舍与维护模式瘦身 | 只自动化覆盖80%场景的20%用例；维护模式按淘汰方针数量级精简，撤离前建冒烟集+how-to文档 |
| 爬走跑四级发布版本链 | 金丝雀(每日排雷)→开发版(须支撑真实工作)→测试版(月度最佳可dogfood)→beta/发布，用版本放量换逐级真实反馈 |
| SWE/SET/TE 三角色职责模型 | SWE写功能并测自己代码、SET建可测试性与框架让别人能测、TE当用户代言人做风险与端到端；测试少而精 |
| 测试认证分级（团队测试健康度阶梯） | 团队代码库按0-5级认证测试健康度，逐级有量化门槛，游戏化推行让开发承担测试 |
| 测试组织四大缺陷诊断与转型 | 诊断测试成拐杖/角色凌驾产品/崇拜测试产物/谁测不重要四缺陷，处方是SET并入开发+TE转测试设计师 |
| bug 生命周期与双维定级 | 严重性×优先级双轴独立定级，品味→演示→全证据记录→修复→回归免疫的处理节奏，到达超修复即停新功能 |
| 基于风险的大型项目测试计划模板 | Chrome OS式完整测试计划模板：风险分析+构建级/日级LKG/发布级三级节奏+分工+基础设施栏目 |
| 众包/内部试用/外部供应商测试组织 | 用按风险排序的能力点+一般性用户故事+漫游指令组织众包/dogfood/供应商，保密功能只给可信测试者 |

> 速查只给结论；需要原文依据、案例或反例时读对应能力卡。
