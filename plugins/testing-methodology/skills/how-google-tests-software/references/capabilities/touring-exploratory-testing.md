# 八种漫游测试

## R（原文摘引）

> "每个城市都有一些危险地带，观光者都会谨慎地避开。软件中也存在危险地带——那些集中产生bug的代码。"（附录B B.7 危险地带漫游）

> "行或列也是探索式测试的极好目标，每个探索式测试人员负责不同的行和列，就可以有效避免重叠，并达到更高的覆盖度。"（第3章 3.2.1）

> "'money tour'得到很大关注，对于各个发布都很重要。'landmark tour'和'bad neighborhood tour'在发现最严重的bug方面最为有效。"（第3章 3.4 Apple Chow 访谈）

## I（解释）

漫游（tour）用"游客行程"隐喻给探索式测试提供主题化结构：每种漫游是一种测试视角，防止漫无目的与互相重叠。每种漫游两层结构：旅行隐喻描述 + 该产品上的具体测试要点清单（附录B Chrome 版全清单）：

1. **购物漫游**：像逛街消费一样走完各种商业流程——Chrome 检验主流零售站点（eBay、Amazon、Sears、Staples、OfficeMax、Macy's、NewEgg、BestBuy）上购买体验是否流畅有效。
2. **学生漫游**：像留学生利用当地资源做研究——收集与组织信息：各类数据经剪贴板复制粘贴、离线内容（Web 页面/图像/文字）上云、多窗口多文档的容量、标签页与窗口间（含隐身窗口）传输数据。
3. **国际长途漫游**：像从异地给家里打电话——跨配置用相同功能：Windows/Mac/Linux × 高/低可信度权限 × 复杂语言与从右到左（RTL）语言 × 代理/无线/有线局域网/防火墙。
4. **地标漫游**：像用罗盘找地标穿越森林——依次到达所有主要界面地标：浏览器主窗口、隐身窗口、紧凑工具条、下载管理器、书签管理器、开发者工具、设置、主题页。
5. **通宵漫游**：像挑战耐力的通宵观光——长时间连续使用且不关闭任何东西：大量标签页 + 大量扩展 + 持续浏览，夜间保持打开次日继续，暴露只有长时间使用才会出现的问题。
6. **公务漫游**：像出差者考察工作条件——检验开发工具：开发者工具（页面元素/资源/脚本/资源跟踪）、JavaScript 控制台、查看源码、任务管理器（进程与资源占用）。
7. **危险地带漫游**：直奔 bug 重灾区——Chrome 聚焦富内容：在线视频（Hulu/YouTube/全屏/高分辨率）、Flash（游戏/广告/演讲稿）、富内容扩展、Java applet、O3D、多实例。
8. **个性化漫游**：像定制私人行程——各种定制方式：主题、扩展程序、设置、快捷键、用户概要隔离（一个概要的偏好不影响其他账号）。

**与 ACC 行/列分工配合**：能力矩阵的行（一个特质跨所有组件）或列（一个组件跨所有特质）是天然功能切片——每个探索者负责不同行/列即可避免重叠、提高覆盖度；整行/整列也可做深度 bug 大扫除。

**每日构建差异分析定重点**（f50，Android 实践）：不盲目钻研整个产品，先观察每日构建的变化面——变化内容、新增/修改代码行数、新改功能、提交者、变化分布广度——据此抓当日重点，配合每日沟通会消除重复。

**YouTube 实战筛选**（c22）：money tour（金钱相关特性，YouTube 即广告/合作伙伴特性）对各发布都很重要；landmark tour（重要系统功能）与 bad neighborhood tour（先前重灾区/最近 bug 集中领域）在发现最严重 bug 上最有效——漫游模式要经本产品实战筛选，不全部照跑。

**漫游名即任务语言**：给众包下指令"对这些能力点做一下 FedEx 漫游测试"比扔一个应用过去有效得多；产品导览（tours）= 把漫游写成清单发给大众测试员，直接引导到应用特定部分。

## A1（原书案例 / 合成演练）

**原书案例一：Chrome 的八种漫游清单（worked_example，附录B 全文）**。输入：Chrome 浏览器。执行：为每种漫游先写旅行隐喻（如危险地带漫游引"每个城市都有一些危险地带"），再落到 Chrome 的具体测试要点（购物漫游列八大零售站；国际长途漫游列平台×权限×语言×网络四维配置；通宵漫游要求"即使不再使用也不关闭任何标签页，夜间保持打开，次日继续"）。特别地，危险地带漫游锚定真实历史：Chrome 初次发布时"YouTube 上的视频都不能正确播放"，富内容由此成为重灾区。结论：该清单即第3章"为大众测试员编写产品导览"的实物，用于指导众包探索式测试；隐喻可迁移，清单必须为本产品重写。

**原书案例二：YouTube 的漫游实战（reported_case，第3章 3.4 Apple Chow 访谈）**。输入：YouTube 产品（Vevo 发布、新 Watch 页、ActionScript2→3 播放器重写等）。执行：测试团队从 Whittaker《探索式软件测试》一书学习漫游模式并实战筛选——"一些漫游方式起作用了，也有一些并没有效果，我们很快就搞清楚了哪些模式适用于我们的产品"：money tour 得到最大关注、每次发布都跑；landmark tour 与 bad neighborhood tour 在发现最严重 bug 上最有效；团队还发明玩笑式漫游（antisocial tour 输入最不可能的输入、obsessive compulsive tour 重复同一动作、couch potato tour 只接受默认值）。成果佐证：IE7 下鼠标移出播放器区域后播放器失去响应的隐蔽 bug（未释放的事件指针反复计算）被发现并修复；Vevo 发布当天 14000+ 视频上线、三个月访问量 1400 万。结论：漫游不是照单全跑，而是按产品特性（视觉体验型、广告变现型）筛选出最有效的组合。

## A2（情境应用）

**触发场景**：
- TE 新接手产品或不熟悉的应用，需要不怎么需要计划的快速摸底（"从中间开始"时先做探索式测试）；
- 发布冲刺期，集中火力找最严重的 bug；
- 组织众包/外包测试，需要一种外行也能执行的任务语言与导览；
- 探索式测试各自为战、互相重复，需要结构化分工。

**语言信号**：
- 中文：探索式测试、漫游、自由测试、头脑风暴式测试、上手指令、测试导览
- 英文：exploratory testing、tour、test tour、free-form testing、product tour

**与相邻能力的区分**（初稿）：
- 与 acc-test-planning：ACC 在计划层产出矩阵，漫游在执行层消费矩阵——行/列切片给漫游提供路线与分工；无 ACC 也可漫游，但重叠风险高。
- 与无结构 ad-hoc/随机测试：漫游有主题、有隐喻、有可勾选的检查点清单；monkey 式乱点不是漫游（"漫游≠随机乱点"）。
- 与 bug-lifecycle（U10）：漫游负责发现，发现后的品味-演示-记录-修复-回归免疫走 U10 流程。
- 与自动化测试：漫游是手工/探索的形态，期望之外的行为才是其目标；回归验证不靠漫游。

## E（可执行步骤）

1. **选漫游组合**：按产品类型与目标选 2-4 种漫游——交易/变现类产品加购物漫游与 money tour；发布冲刺加危险地带漫游 + 地标漫游；有每日构建 diff 先做变化面分析，把漫游聚焦到变更区域。完成标准：每种选定漫游有一句话目标与入选理由。
2. **写漫游卡**：每张漫游卡 = 隐喻一句话 + 本产品的具体清单（地标漫游列全部主要界面；危险地带漫游从 bug 库定位重灾区；国际长途漫游列平台×权限×语言×网络矩阵）。完成标准：检查点可直接勾选，目标区域指认到具体功能或历史 bug 集。
3. **执行与分工**：每个探索者认领不同漫游，或按 ACC 矩阵认领不同行/列；发现的 bug 按生命周期流程处理。完成标准：参与人之间漫游/行列无重叠；每张漫游卡有执行记录（发现 bug 列表或明确的"未发现"结论）。

**输入契约**：必需 = 被测应用（可访问、可操作）。可选 = ACC 能力矩阵（用于行/列分工）、每日构建 diff（用于聚焦变更）、bug 库（用于定位危险地带）。ACC 缺失时不猜产品特质，直接从八种漫游全列让用户按目标挑选。

**输出契约**：选定漫游组合表（漫游名 / 目标 / 入选依据）+ 每漫游的检查点清单（地标列表、重灾区列表或配置矩阵）+ 执行记录（bug 列表或未发现结论，附漫游名与执行人）。

**判停点**：产品无历史 bug 数据且执行者不熟悉产品 → 危险地带漫游降级为通宵漫游/地标漫游，先积累一周使用经验；漫游卡写不出任何具体地标/场景 → 停，先花 30 分钟做产品导览再回来；用户想八种全跑 → 停，出示 ce32（无重点全量漫游是反模式），按目标裁剪到 2-4 种。

## B（边界）

**反场景（何时不用）**：
- 回归验证与精确断言——漫游找的是期望之外的行为，既定行为的反复验证属于自动化测试与测试用例；
- 每次都全量漫游：坐下来"自顾自地钻研整个产品"不是明智之举——精力均匀撒在不变区域，变化区域反而覆盖不足；
- 需求/架构尚未稳定的原型期做系统性漫游——早期探索式测试可少量做，成建制的漫游投入应等聚焦对象（构建、bug 历史）出现。

**书中警告的失败模式**：
- ce32 无重点全量漫游："我们需要仔细观察要进行测试的每日构建版本，分析里面有些什么……这些问题都能帮助我们抓住重点，而不是自顾自地探索整个产品"——漫游必须锚定变化面与重灾区；
- ce14 无导览把众包投入产品：大众测试员需要时间学习被测应用，"考虑到数量，这意味着惊人的浪费"——漫游清单即导览解药，且可分发不同分组避免重复；
- 漫游退化为随机乱点：漫游的价值在主题与检查点；丢了清单的"漫游"只是漫无目的的点击，既无覆盖主张也无复盘结构。

**作者盲点/时代局限**：
- 附录B 清单是 Chrome 特化的（O3D、Java applet 等技术已过时，八大零售站名单随时间失效）——隐喻与两层结构可迁移，具体清单必须为本产品重写；
- "money/landmark/bad neighborhood 最有效"的结论来自 YouTube 单一产品的实践（c22，reported_case），其他产品应自行实战筛选而非照搬结论；
- 书中漫游主要面向 UI 型、面向用户的产品；纯后端、协议层或数据管道产品的漫游需要重新发明隐喻（如把"地标"换成关键数据转换节点），原书未覆盖此场景。
