# 众包、内部试用与外部供应商测试组织

## R（原文摘引）

> "ACC的真正威力在于它能用来确定一系列的能力点，按风险排序，然后分配给所有的质量伙伴。……这样，就能在保证重要区域覆盖度的同时又减少重复测试，比简单地把应用扔出去一哄而上更有效率。"（第3章 3.2.2）

> "很细致的测试用例反而会导致外包人员在一遍又一遍的重复执行时产生厌倦感，而用户故事则为确定具体行为留出了更大的余地。……'对这些能力点做一下Fed Ex漫游测试'常常要比简单地扔给他们一个应用然后乐见其成的效果要好得多。"（第3章 3.2.2）

> "我们预先认识到Wi-Fi和3G连接是最大的风险。……因此，我们绝不能把这些功能的测试交给好心好意但却不够专业的人。"（第3章 3.2.12）

## I（解释）

方法骨架：把"是谁在做测试并不重要，关键是进行了测试"（第5章缺陷四的论断）落成可操作的组织流程。三类外部测试力量，三种组织法。

**众包适用判断**：适用面——大众拥有海量硬件/环境组合与多元视角（"以前是一个测试人员想象1000个用户的使用场景，现在是1000个真实用户在做测试"），且 7×24 可用；约束面——大众测试员需要时间学习被测应用并跟上更新（学习成本×人数=惊人的浪费）、敏感保密的内网项目只能交给可信测试人员。开源项目适合大众测试，保密项目走可信测试者。

**任务下达方式**：给一般性用户故事而非过细的测试用例（防厌倦、为具体行为留变化空间，反而提高覆盖）；用漫游命名指令（"对这些能力点做一下 FedEx 漫游测试"）——指令本身即包含期望测试的特性与展开方式，比"扔一个应用出去乐见其成"有效得多。

**按风险排序的能力点分配**：用 ACC 产出能力点清单 → 按风险排序 → 分配给所有质量伙伴：参与项目的 TE、dogfood 用户、20% 贡献者、外包测试人员、众包测试人员、SWE、SET 各负责一个能力子集——保证重要区域覆盖度同时减少重复。配套机制：测得快者自动多得任务、超时任务自动转推（BITE 式分发，机制可迁移）。

**产品导览编写**：为大众测试员编写 tours（附录 B 的 Chrome 八种漫游即实物），引导探索式测试与用户场景到应用的特定部分；编写多个导览分发给不同分组，实现分工与去重。

**dogfood（内部试用）**：内部试用者就是真实用户（TE 只能想象自己是用户）；让 TE 做的测试越少、支持其他人做的测试越多，效果越好。经营内部试用者群体是测试设计师的核心职责。

**外部专业供应商协作**（自身缺乏专业能力时）：预先识别自己无法覆盖的最高风险领域（Chrome OS 的 Wi-Fi/3G 连接——物理设备在不同制造商间变化大，无网络连接的云设备没有价值）→ 认识到"好心好意但不够专业"不能替代专业（当时 Google 无人有物理测试设备）→ 找专业供应商（较低层级工程师也可直接联络，快速行动快速交付；供应商数周内发现内部无法发现的问题：多路由器覆盖的公寓场景切换与吞吐率下降）→ 请供应商评审自家硬件合格性测试列表（既发现遗漏，又把格式对齐行业惯例，使交付给 PC 制造商的第一批测试可读且完整）→ 渐进自建设施但持续借助专家。"以谦虚的态度寻求外部专家的帮助，这会带来回报。"

## A1（原书案例 / 合成演练）

**c16：Chrome bug 悬赏与 18 秒/URL 众包评审。** Chrome 设 bug 换奖金活动激励最佳 bug 发现者；uTest 等商业众包公司参与 Google 产品测试。对照实验（Quality Bot 侧）：现场外包工程师花 3 天检查 150 个 URL，bot 只标记其中 6 个转给众包——有 bot 数据和差异可视化辅助，一个众包测试人员确认一个网站有无问题的平均时间是 **18 秒**，判断效果与 3 天人工评审一致而成本低得多。证明众包在"结构化+有上下文"的任务上可以匹敌专业评审。

**c17：Google Feedback（用户侧输入通道）。** point-and-click 提交+隐私过滤（用户可先删敏感区域）+服务端聚类去重+按报告量排序的 dashboard——新应用上线数万条问题精简到约 10 个主要共性问题。没有这层过滤，众包/用户的原始报告会拖垮 triage。

**c29：Google+ 最好的 bug 来自内部试用者。** 许多 Google+ 最好的 bug 由团队以外的 Googler 试用者发现——内部试用不是补充手段，而是最有效的测试力量之一；测试设计师的职责是经营他们。

**外部供应商实例（3.2.12）**：Chrome OS Wi-Fi/3G——机架上放 20 台商用路由器由供应商驱动测试，几周内发现公寓多路由器场景的切换问题与严重吞吐率下降，开发在内部使用阶段就完成修复；Allion Test Labs 还评审了 Google 的硬件合格性测试列表，补遗漏并重排格式。

## A2（情境应用）

**触发场景**：
- 测试资源不足，考虑把测试众包/外包，但不知道怎么组织
- 产品配置组合爆炸（机型×浏览器×网络×语言），内部覆盖不过来
- 已有众包/外包投入，但反馈集中在表面 UI 问题、同一 bug 大量重复
- 计划发内部 beta/dogfood，想知道怎么组织内部试用者才有产出
- 产品涉足自身无专业能力的领域（射频/认证/音频实验室/安全渗透）
- 保密产品/特性需要外部测试力量但担心泄密

**语言信号**（中英双语）：
- 中文：众包测试 / 外包测试 / 内部试用 / dogfood / 可信测试者 / 早期用户 / beta 用户 / 测试任务包 / 产品导览 / 找外部供应商
- English: crowdsourced testing / crowdsource QA / outsourced testing / vendor testing / dogfooding / trusted testers / early access users / beta program / test tour / writing a product tour for testers

**与相邻能力的区分**（初稿）：
- 与 `touring-exploratory-testing`（漫游测试）：那张卡是漫游的语义库（八种漫游=测试视角）；本卡是组织层——把漫游指令作为任务语言分发给众包/外包。导览=漫游清单的产品化包装。
- 与 `acc-test-planning`（ACC 计划法）：本卡直接消费 ACC 产出（按风险排序的能力点是任务分配的输入）；没有能力清单就"把应用扔出去一哄而上"，正是本卡反对的形态。
- 与 `test-org-pathologies`（缺陷四）：那张卡论证"谁测不重要"；本卡给出组织流程（任务包/导览/保密边界/供应商）。诊断在前，组织法在后。
- 与 `crawl-walk-run-release`（爬走跑）：dogfood/可信测试者/早期用户是发布版本链上的用户群体来源；本卡决定给他们什么任务、怎么收反馈。
- 与 `bug-lifecycle`：众包/用户报告的信息质量与去重（c17 聚类、BITE 自动采集）由那张卡的证据机制承接。

## E（可执行步骤）

1. **能力点准备与分配**：用 ACC 产出能力点清单 → 按风险排序 → 分配给各类质量伙伴（TE/dogfood 用户/20% 贡献者/外包/众包/SWE/SET 各领一个子集）；高风险能力点优先给可信度高的力量（内部试用者、外包合同方），低风险能力点可交给众包。完成标准：每个能力点有唯一责任群体；高风险点无一落入"无主"状态；保密边界有明确清单（哪些能力点只能给可信测试者）。
2. **制作任务包**：每个分配出去的能力点配——一般性用户故事（"尝试用两种语言打同一句话"）或漫游命名指令（"对该能力点做个性化漫游"），绝不写细粒度用例；附产品导览（引导到应用的特定部分，可多份导览分发不同分组）；预留反馈与去重通道（一键报告+聚类）。完成标准：抽查任务包——拿到任务的人不看细用例也知道测什么、怎么展开；导览覆盖被分配区域。
3. **专业领域找供应商**：识别自身无专业能力的高风险领域 → 选该领域专业供应商（授权一线工程师直接联络，快速行动）→ 供应商执行专业测试并出具报告，数据回流开发 → 请供应商评审自家测试列表（采纳遗漏与格式建议）→ 渐进自建能力但保持专家关系。完成标准：高风险专业领域有供应商覆盖；自家合格性测试列表经专家评审；有数据回流路径。

**输入契约**：ACC 能力点清单 + 风险排序（可来自 `risk-heat-map` 卡）+ 保密边界（哪些产品区域不可对外）。
**输出契约**：任务包清单（能力点 + 用户故事/漫游指令 + 导览链接）+ 供应商选择与协作清单（领域、候选、评审安排、数据回流方式）。
**判停点**：①无导览资产时判停众包投放（ce14：学习成本×人数=惊人浪费）——先写导览再放人；②反馈大量重复或集中于表面 UI → 判停加人，先修任务粒度与导览指向；③涉密能力点不可进入众包/外部包范围，只能给可信测试者，宁缺勿泄；④专业领域（射频/认证/安全）判停"好心好意但不专业"的内部人员顶替——找专家；⑤众包确认类任务的反馈与自动检查结果长期一致 → 该任务可自动化，从众包清单移除（人留给机器做不了的部分）。

## B（边界）

**反场景**：强保密产品（未发布核心功能、内网系统）不适用开放众包——只能用可信测试者与保密协议外包；专业资质门槛领域（认证、渗透测试）不能用众包替代授权实验室；需要深度产品知识的测试（复杂工作流、领域逻辑）众包产出低——学习成本吃掉收益，这类留给内部或长期外包。
**书中失败模式**：ce14 无导览投入众包——每个测试员自行摸索产品与更新，浪费惊人，反馈集中表面、重复提交同一 bug；"把应用扔出去一哄而上"式的众包——无能力点分配，重要区域覆盖靠运气；把高风险专业领域交给"好心好意但不够专业"的人（3.2.12 的核心警告）。
**作者盲点/局限**：①众包质量管控成本原书着墨很少——误报过滤仅 Quality Bot 转发众包快速评审一例（18 秒/URL 有对照实验支撑），报酬机制、验收标准、作弊防护未展开，采用时需自行补充；②BITE 式任务分发（快者多得、超时转推）绑定已停维护的 Google 内部工具——机制可迁移（现代众包平台多有等价物），工具名不可迁移；③uTest 等商业众包形态已演变（如今 Applause 等），组织原理不变但平台选型需更新；④供应商案例默认"供应商专业且配合"——现实中的供应商选择与验收标准书中未给，需自行定义（可参考：能否发现内部发现不了的问题、是否愿意评审你的测试列表、报告数据能否回流开发）；⑤dogfood 依赖内部用户规模与使用意愿，小公司内部试用者基数不足时，此路收窄——退而求其次做可信外部测试者（早期用户）计划。
