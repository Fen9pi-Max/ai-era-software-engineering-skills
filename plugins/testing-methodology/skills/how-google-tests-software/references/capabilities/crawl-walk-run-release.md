# 爬走跑四级发布版本链

## R（原文摘引）

> "Google 经常在最初的版本里只包含最基本的可用功能，然后在后继的快速迭代的过程中得到内部和外部用户的反馈，而且在每次迭代的过程中都非常注重质量。一个产品在发布给用户使用之前，一般都要经历金丝雀版本、开发版本、测试版本、beta或正式发布版本。"（1.4）

> "金丝雀版本：这是每日都要构建的版本，用来排除过滤一些明显不适宜的版本。就像煤矿井里的金丝雀……如果构建失败了的话，意味着我们的流程可能在哪里出了严重问题，需要去复查一遍我们的工作。"（1.4）

> "对于初期版本的用户，并不是因为这个产品还处于早期版本就不为之提供足够的功能，早期版本并不意味着是一个不可用的烂版本。"（1.4）

## I（解释）

方法的骨架是用"版本放量"替代"一次大爆炸发布"，把真实用户反馈切成四级逐级引入：

1. **金丝雀版本**（每日构建）：排雷用。构建失败=流程出了严重问题，需复查工作；仅产品工程师与管理层使用，需极强容忍度，基本功能都可能不可用。
2. **开发版本**（约每周）：产品线全体工程师被要求安装并在日常工作中真实使用——自用即持续测试；若不能支撑日常真实工作，打回为金丝雀版本，工程团队重新评估。
3. **测试版本**（约月度最佳）：日常最稳定、最受信任的版本；可被选为内部尝鲜（dogfood）版本；持续优良即成 beta 候选；内部足够稳定时外部合作伙伴也可使用。
4. **beta/发布版本**：由非常稳定的测试版本演变而来，经内部使用并通过所有质量考核，才对外发布。

两条配套原则：

- **早期版本≠烂版本**：核心功能必须可用，每次迭代都注重质量；beta 标签只用于管理用户预期（Gmail 戴了四年，99.99% 可用性才摘），不是降低质量要求的借口。
- **bug 寿命缩短逻辑**：每级版本换一批更真实的用户（工程师→全产品线工程师→内部尝鲜者/合作伙伴→外部用户），bug 在到达下一级用户前就被当前级消化；配合快速迭代与增量上线回滚机制，"bug 的寿命从几个月变成了几分钟"（5.3）。

晋级/打回标准在原书中均为定性描述（"不能满足日常真实工作即打回"），无量化门槛——如实沿用，自行校准，不要伪造数值。

## A1（原书案例 / 合成演练）

- **c01 Gmail beta 四年**（firsthand，1.3/1.4）：核心功能可用即上线，beta 标签警示用户"仍在改良"，用四年真实用户反馈驱动迭代，达到 99.99% 可用性才摘标签；Android G1 与 Nexus 复用同一策略。
- **c02 Chrome 四层版本链**（firsthand，1.4）：作者亲历两年的项目，按"对产品的信心+用户反馈"组织四级版本：金丝雀每日构建过滤坏构建→开发版每周发布供工程师日常使用→测试版为当月最佳并作 dogfood/beta 候选→beta/发布版对外。
- **c03 Android 每日构建装进主力手机**（reported_case，1.4 注意框）：金丝雀的极端化——核心开发团队成员的手机就运行每日构建，装了坏代码连给家人打电话都不行；用最痛的自用体验倒逼不提交问题代码。

## A2（情境应用）

**触发场景**

- 团队纠结"什么时候让真实用户进来"，或发布节奏只有"内部开发版+正式上线"两级
- 大爆炸式发布前集中测试压力过大、想改灰度/分批放量
- 线上 bug 频出但用户反馈链条太长，修复循环以周计
- 内部版本无人使用，中间版本质量信号缺失

**语言信号**

- 中文：发布节奏 / 发布通道 / 灰度 / 内测 / 公测 / 金丝雀 / dogfood
- 英文：release channel / canary / staged rollout / incremental rollout / beta program / dogfooding

**与相邻能力的区分（初稿）**

- 与 test-size-model：那是测试分级（小/中/大，按范畴规模），这是版本分级（放量节奏）；版本链的每一级内部都可以有三种规模的测试，两个维度正交。
- 与 risk-based-test-plan-template：附录A 的"每次构建/每日 LKG/发布候选"三级是**测试执行频率**，本卡是**版本对用户放量**——前者在 risk-based-test-plan-template 卡，勿混。
- 与 crowd-and-dogfood-testing：测试版如何组织 dogfood 与众包在 U13 展开；本卡只定义"测试版可被选为 dogfood"这一衔接点。

## E（可执行步骤）

1. 盘点用户群体分级：产品工程师→产品线全体工程师→内部尝鲜者/外部合作伙伴→外部用户，确认每级有明确使用者和反馈回收通道。
2. 填版本链设计表（五栏：级别 / 频率 / 使用者 / 晋级条件 / 打回条件），从金丝雀逐级向下定义；原书无量化门槛，晋级条件按产品风险自定（如"支撑某团队一周日常真实工作零阻断"）。
3. 试运行一个完整晋级周期：金丝雀每日跑起来→演练至少一次打回→开发版被真实日常工作使用→选出月度最佳→核对质量考核清单通过后才外发。

**完成标准**：表中每级的使用者、晋级条件、打回条件三栏非空；开发版有"无法支撑日常工作即打回"的明确判定人；外发前有质量考核清单（可用风险热图的红黄绿门槛）。

**输入契约**：产品形态（能否在线更新）、可日构建的 CI、分级可触达的用户群体清单。

**输出契约**：版本链设计表（级别/频率/使用者/晋级条件/打回条件）+ 每级反馈回收方式说明。

**判停点**：连每日构建都做不到（无 CI）→ 先建构建基础设施，本卡暂不适用；用户群体无法分级（如合同交付单一下家）→ 版本链退化为"内部测试版+交付版"两级，不硬凑四级；产品无法在线更新 → 见 B 段反场景，回退发布前穷尽测试模式。

## B（边界）

- **反场景**：无法在线更新的交付型软件（盒装软件、无 OTA 的嵌入式）——"早期版本+快速迭代"的前提是能快速修复并推送，此时应回到发布前重测试模式，版本链不成立。
- **书中失败模式**：开发版被打回"不但令人郁闷，工程团队也需要再花费大量的时间去重新评估"（1.4）——打回是常态机制而非事故，但要有重评估成本预期，不能把打回当惩罚。
- **晋级标准定性无量化门槛（如实注明）**：原书各级晋级条件均为定性描述（"持续优良""通过所有质量考核"），无数字门槛；照搬者须自行定义考核项，警惕把书里的定性话术包装成"Google 标准"。
- **与附录A三级测试节奏区分**：构建级冒烟/每日 LKG/发布候选全量是测试执行频率（属 risk-based-test-plan-template 卡）；本卡是版本放量链。Chrome OS"六周三通道五平台"等具体节奏为项目特定值。
- **作者盲点**：四级链隐含"内部有足够多的工程师用户"（Google 万人规模）——小公司内部用户池太浅，测试版一级可能凑不齐使用者，dogfood 反馈量不足；且 Gmail beta 四年也提示，标签可能被当作拖延摘除的借口，需要类似"99.99% 可用性"的明确摘签定义兜底。
