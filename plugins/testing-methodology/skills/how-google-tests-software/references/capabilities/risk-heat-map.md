# 风险热图：失败频率×影响

## R（原文摘引）

> "在Google，我们确定了两个要素：失败频率（frequency of failure）和影响（impact）。测试人员用这两个要素给每项能力打分。我们发现，风险实际上是一个定性的相对值，而非一个定量的绝对值。"（第3章 3.2.2）

> "在将风险分析结果作为随后测试的依据展示给大家的时候，我们实际上是树了一个靶子供大家争论。这就是重点：与其询问他们关于某个模糊概念的看法，不如拿一个明确的结论来引起辩论。"（第3章 3.2.2）

> "如果是Google Labs Experiment，即使有一些红色的区域，只要不危及隐私或安全，也是可以发布的。如果是Gmail的一次主要发布，甚至黄色区域都是不可接受的。"（第3章 3.2.2）

## I（解释）

对 ACC 产出的每项能力做两维打分，聚合为特质×组件热图，回答"不能全测时先测什么"。

**频率四档**（偶数取值，防止打分者偷懒选中间值）：
- 罕见（rarely）：故障可能性很小、恢复容易——Chrome 下载页，内容基本静态，核心脚本崩溃也易被监视代码发现；
- 少见（seldom）：少数场景才故障——Chrome Forward 按钮，使用频率低，出了问题早期用户也会很快发现；
- 偶尔（occasionally）：场景易想象、能力较常用——Chrome Sync，跨客户端同步多类数据、跨多 OS 平台，变更合并是复杂的计算机科学问题；
- 常见（often）：使用量大、复杂度高、问题频发——Web 页面渲染，浏览器最主要用例，问题会被用户归咎于浏览器。

**影响四档**：
- 最小（minimal）：用户注意不到——chrome://labs 页面加载失败，多数用户根本不知道该特性存在；
- 一些（some）：重试或恢复机制可解——refresh 按钮失效，重输 URL 或开新标签页即可，代价很低；
- 较大（considerable）：使用受阻——扩展在新 Chrome 版本中加载失败，功能丢失；
- 最大（maximal）：永久损害声誉、导致用户流失——自动更新机制失效，安全升级无法进行甚至浏览器停摆。

**定性相对值原则**：目标是识别"A 比 B 风险更大"以决定测试顺序，不需要精确数值；打分时区分影响是针对公司还是针对用户（公司 logo 加载失败对公司是问题，用户未必注意）。

**单元格 = 简单平均**：热图中每个特质×组件交点的风险级别，是该交点各能力风险的简单平均，以红/黄/绿高亮。原书的具体偶数值在插图（图3.8）中未随文本解析——执行时自选偶数梯度（如 1/3/7/10，此为本卡约定，非原书数值），全队统一即可。

**相关方偏见清单**（打分时须知晓）：开发人员高估自己负责的特性（希望被充分测试）；PM 偏爱差异化亮点特性；销售偏爱演示拉风的特性；总监/VP 关注与主要竞品的差异。

**树靶子策略**：不向相关方解释流程再求助打分，而是自己先完成分析、把热图亮出来——各方发现偏差自然会提意见（排除容易，下定义难），通常能收获大量有效输入。

**红黄绿发布门槛**：可发布与否取决于产品类型与失败代价——实验性产品容忍红色（隐私与安全红线除外），主力产品的主要发布连黄色都不可接受；颜色标识简单到"即便是测试总监也能理解"。

**剩余风险变体**（附录A A.2，Chrome OS 式）：先评估每方面的绝对内在风险（出现频次、失效可能性、失效后果），再扣除已有缓解（现有测试用例、自动化、用户试用、OEM 测试等），按剩余风险排序所有组件。

## A1（原书案例 / 合成演练）

**原书案例一：Chrome 功能的风险打分八例（worked_example，第3章 3.2.2）**。输入：Chrome 各功能。执行：频率轴四档各配一例（罕见=下载页、少见=Forward 按钮、偶尔=Sync、常见=页面渲染）；影响轴四档各配一例（最小=labs 页面、一些=refresh 按钮、较大=扩展加载失败、最大=自动更新失效），每例附一句判定理由（如 Sync"涉及不同数据类型及多个 OS 平台，变更合并是复杂的计算机科学问题"）。结论：两轴档位均可由真实功能实例锚定，打分过程可复算；强调取值只用偶数以防偷懒。

**原书案例二：Google+ / Google Sites 热图与树靶子（worked_example，第3章 3.2.2）**。输入：Google+ 早期版本的特质-组件表（由 c12 的 ACC 产出）与测试人员的打分。执行：GTA 基于测试人员输入自动生成风险热图（单元格 = 交点内各能力风险的简单平均，红/黄/绿高亮）；随后不空泛征求意见，而是把热图直接展示给开发/PM/销售/总监——开发知道热图将决定测试优先级故参与度高，各方发现偏差即主动提出修正意见。结论：热图用于决定测试顺序、测试资源分配（组织级如决定各产品团队的测试编制）与发布建议；"知道 A 比 B 风险更大就足够"。

## A2（情境应用）

**触发场景**：
- 时间或人力不够全测，需要决定先测什么、派谁去测；
- 发布决策：这个版本带着已知的红色区域能不能发；
- 跨项目分配测试资源，需要一个统一口径的风险语言；
- 开发、PM、销售对"什么最重要"各执一词，需要一张能引发辩论的靶子。

**语言信号**：
- 中文：排优先级、先测什么、风险分析、风险热图、影响和概率、发布判断
- 英文：risk analysis、risk matrix、heat map、prioritization、impact vs frequency、go/no-go

**与相邻能力的区分**（初稿）：
- 与 acc-test-planning：ACC 产出能力清单与矩阵，本卡在其上打分——先有清单后打分；没有能力清单时先回 ACC，不直接给特性拍脑袋排序。
- 与发布计划能力（crawl-walk-run-release，U4）：本卡回答"风险够不够低、能否发布"，U4 回答"以什么节奏放量给谁"；热图给门槛，爬走跑给通道。
- 与 risk-based-test-plan-template（U12）：U12 是完整计划文档模板，本卡是其中"风险分析"一节的方法内核；大型项目做剩余风险变体（附录A 式），日常版本做频率×影响打分。
- 与 bug-lifecycle（U10）：本卡决定高风险区域后，红色能力点须补用户故事/用例并保证历史 bug 有回归用例（f25 风险缓解六步），发现的 bug 走 U10 流程。

## E（可执行步骤）

1. **对齐清单与档位**：取得能力/特性清单（来自 ACC 或用户提供的特性列表），向全队宣读两轴四档语义及各档实例。完成标准：每条打分者能复述档位含义；数值梯度（偶数，如 1/3/7/10）已约定并声明"非原书数值"。
2. **逐条两维打分**：每条能力给出频率档 + 影响档 + 一句话理由，并标注影响针对公司还是用户。完成标准：清单 100% 打完，无空项；理由可追溯到档位定义。
3. **聚合热图**：按特质×组件交点取各能力风险的平均值，映射红/黄/绿；无矩阵时按功能模块分组聚合。完成标准：任一单元格的值可由其能力分数复算。
4. **树靶子并修正**：把热图展示给开发/PM/销售/管理层，按偏见清单解读反馈并修正一轮。完成标准：至少记录一轮修正及其理由。
5. **给出排序与发布建议**：输出高风险能力排序；按产品类型（实验版/主力发布）对照红黄绿门槛给出"可发布/有条件发布/阻塞"建议。

**输入契约**：必需 = 能力或特性清单（缺失时先走 ACC 或向用户索要，不凭空给产品打分）+ 产品类型与发布语境（实验性还是主力发布）。可选 = bug 库与已有测试资产清单（做附录A 剩余风险变体时必需：内在风险 − 已有缓解）。

**输出契约**：热图表格（行 = 组件/模块，列 = 特质，单元格 = 平均风险值 + 颜色）+ 高风险能力排序列表（含打分理由）+ 发布建议（结论结构：可发布 / 有条件发布（附条件）/ 阻塞（附阻塞项））。

**判停点**：会议时间花在争论"分数是 6 还是 7"而非排序本身 → 停，退回档位语义（定性相对值原则，ce13）；能力清单不存在 → 停，先回 acc-test-planning；所有能力打分趋同（全绿或全红）→ 停，检查档位实例是否被理解、清单粒度是否过粗。

**执行约定（原书未规定，须透明声明）**：① 红/黄/绿的分数映射阈值由团队自定（如两轴乘积 ≥50 红 / 20-49 黄 / <20 绿），且任一轴取最高档时该条至少黄（防"简单平均稀释极端值"）；② 单条能力的合成方式（频率×影响 或 相加）与同分裁决规则（建议影响档优先、可恢复性次之）均为约定，输出中标注"本卡约定，非原书数值"。

## B（边界）

**反场景（何时不用）**：
- 需要精确概率与期望损失计算的场合（金融量化风控、安全合规评估）——本方法刻意定性，"风险没有数学上的精度要求"，不能替代定量风控；
- 没有能力/特性清单就空谈风险——先做 ACC，否则打分对象不存在；
- 单人闭门项目且无发布压力——树靶子环节可省，但打分与排序仍有价值。

**书中警告的失败模式**：
- ce13 试图精确定量地计算风险："试图精确地、定量地计算风险比缓解风险还要麻烦……风险实际上是一个定性的相对值，而非一个定量的绝对值"——警告信号是会议争论具体分数、热图因"重新计算太贵"而久不更新；
- 相关方偏见未修正：开发高估自己的特性、PM/销售/总监各有偏好——须用偏见清单解读反馈，而非简单取平均了事；
- 风险快照不更新：ACC/风险计划最大的失败模式是"推动了开始后就变成死文档"（f39 GTA 思想）——应随 bug、代码、测试数据的变化更新，否则退化为一次性拍脑袋。

**作者盲点/时代局限**：
- 原书具体偶数取值在插图（图3.8）中未随文本解析，本卡 1/3/7/10 梯度为约定值，不得冒充原书数值（needs-review 已登记）；
- 单元格"简单平均"会稀释交点内的极端值——一个 maximal 影响的能力可能被同交点低风险能力平均成黄色，原书未讨论此缺陷，使用时应同时查看交点内最高风险能力，不能只看颜色；
- 与发布计划能力的边界：热图给"能否发布"的建议，不回答放量节奏与用户群体选择（那是 crawl-walk-run/发布通道的事）；把热图当发布计划用是越界。
