# 测试认证分级

## R（原文摘引）

> "所有团队最初的级别都是 0。如果掌握了基本的优秀代码习惯，就达到级别1，然后继续通过水平考核，最终达到级别5，与外部的能力成熟度模型一样，例如CMM能力成熟度模型。"（2.2）

> "测试认证计划提供了小而清晰且可操作的步骤给团队去执行。级别1是做基本准备：建立测试运行的自动化机制、收集测试覆盖率、去除所有非确定性的测试、挑选冒烟测试集合。"（2.2.1 创始人访谈）

> "许多团队，特别是一些可测试性比较差且有遗留代码的团队，发现从级别 1 到级别 2 非常困难。这些团队会比较受挫，并有意向退出测试认证计划。我们在级别 1 和级别 2 之间增加了一个稍微简单的新级别。"（2.2.1 创始人访谈）

## I（解释）

对**团队代码库**（不是对人）的测试健康度分级认证，用"小而清晰且可操作的步骤"把测试变成功能开发人员的职责，再用游戏化推行形成文化变迁。

**级别门槛（书中明细）**：

- **L1（基本准备）**：使用测试覆盖率工具；使用持续集成；测试分级为小/中/大；明确标记非确定性测试；创建冒烟测试集合。
- **L2（行为约束）**：测试红色（失败）就不发布；每次代码提交前通过冒烟测试；各类测试整体增量覆盖率>50%；小型测试增量覆盖率>10%；每个功能特性至少一个集成测试用例。
- **L3（增量质量）**：所有重要代码变更都经过测试；小型测试增量覆盖率>50%；新增重要功能经集成测试验证。
- **L4（速度与存量）**：提交任何新代码前自动运行冒烟；冒烟 30 分钟内跑完；无非确定性测试；总覆盖率≥40%；小型≥25%；所有重要功能被集成测试验证。
- **L5（缺陷免疫）**：每个重要缺陷修复配套测试用例；积极使用代码分析工具；总覆盖率≥60%；小型≥40%。

设计逻辑：从基建（L1）→发布纪律（L2）→增量质量（L3）→速度与存量（L4）→缺陷免疫（L5），门槛逐级收紧；认证对象是代码库，徽章公开展示，配合教练与榜单把文化变迁变成可炫耀的竞赛。

**推行路径**：选测试友好的试点团队（三大筛选：足够感兴趣、冗余代码不多、团队里有"测试战神"）→志愿者教练一对一（测试资源稀缺的文化里，参加计划本身吸引更多测试人员关注）→神秘海报+ToTT+发光魔法球+达斯土豆头奖品的"信息闪电战"→草根病毒式扩散→增长放缓时上积分挑战赛再加速→级别最终成为团队可度量目标与工程生产力投放测试资源的参考。

**调整教训（创始人自述）**：目标定得过高，被迫下调到"空闲时间努力可达"；在 L1/L2 之间插入更容易的级别（原 4 级变 5 级，后续级别全部+1）；去掉一刀切的小/中/大比例要求，改用增量覆盖率的具体比例；标准不搞一刀切，按团队状况定制多数人可达的门槛。

## A1（原书案例 / 合成演练）

- **c07 从 15 个试点团队到全公司文化变迁**（reported_case，2.2.1 四位创始工程师访谈）：2007 年中宣布"正式启动"时有 15 个试点团队在不同级别运行；几个月后约 50 个团队加入，一批测试工程师签约成为教练；约一年后超百团队通过认证，加入放缓后由志愿者主管策划积分挑战赛（新增测试、引入新团队、提升级别均计分）再次加速；到 2011 年全公司运行，"只有很少一部分领域在使用手动测试"。初期目标过高被迫调低并插入易级；靠海报（"未来就是现在""至关重要，莫被遗弃"）、ToTT、发光魔法球、达斯土豆头做信息闪电战；认证级别后来成为经理的团队目标与工程生产力分配测试资源的依据。创始人评价："完成了它的使命，会被作为伟大的历史遗产。"

## A2（情境应用）

**触发场景**

- 团队零测试文化或低成熟度，想推动"开发写测试"但不知从哪下手
- 已有 CI 与零星单测，但无发布纪律，想引入"红色不发布"类门禁
- 管理层要看各团队测试成熟度的可比数据
- 测试资源有限，需要客观的分配/优先级依据

**语言信号**

- 中文：团队测试成熟度 / 怎么让开发写测试 / 测试文化推行 / 覆盖率门槛 / 冒烟集
- 英文：test maturity / developer testing culture / coverage gate / testing maturity model / smoke suite

**与相邻能力的区分（初稿）**

- 与 set-early-involvement：那是单个 SET 在一个项目里的介入工作流；本卡是团队级、跨组织的文化推行机制。L2"提交前冒烟"即 U7"提交前闭环"的团队化门槛。
- 与 test-size-model：L1 的"测试分级为小/中/大"直接引用 U3 的分类法——先理解规模模型，才能落 L1。
- 与 automation-scope-and-maintenance：认证推着覆盖率与用例增长，U11 提供淘汰与瘦身机制防止用例库无限膨胀、防"总是通过的测试"占位——两者互为油门与刹车。

## E（可执行步骤）

1. **判级**：对照 L1-L5 门槛逐条核对团队现状（覆盖率工具/CI/测试分级/非确定性标记/冒烟集/发布纪律/覆盖率数字），产出当前级别判定表与未达标项清单。
2. **出下一级任务清单**：只针对"当前级+1"，每条任务可验收（装什么工具、门禁加在哪条流水线、增量覆盖率从多少提到多少、谁验收）。
3. **出推行方案**：按"试点团队选择（三大筛选）→教练安排→可见激励（徽章/榜单/公开庆祝）→扩散计划"组织；预留一次"门槛下调"复盘点。

**完成标准**：判级有逐条证据而非拍脑袋；任务清单每条有验收标准与负责人；推行方案含第一支试点团队名单与教练人选。

**输入契约**：团队现状盘点（代码库规模、CI 状态、现有测试与覆盖率数据、发布纪律、人员意愿）。

**输出契约**：当前级别判定表（逐门槛勾选+证据）+ 下一级任务清单（任务×验收标准×负责人）+ 推行方案（试点/教练/激励/扩散/复盘节奏）。

**判停点**：无 CI 且无覆盖率数据 → 只能从 L1 的工具建设起步，别谈 L2 门禁；找不到自愿试点且管理层不背书 → 游戏化会沦为形式，先解决意愿再回来；推行 3 个月无一团队过 L1 → 门槛可能超出"空闲时间努力可达"，按调整教训下调或插级；团队规模小 → 直接按 B 段简化为 L1-L3，不硬上 L4/L5。

## B（边界）

- **数值门槛非固定标准**：作者明言门槛随时间多次调整（4 级改 5 级、插易级、去掉比例一刀切）；40%/60%、30 分钟等数字是 2011 年前后 Google 代码库的校准值，照搬前必须按自己产品与代码规模重校，且方向上以"增量覆盖率"为主——它对遗留代码团队远比总覆盖率公平。
- **游戏化推行依赖组织支持**：发光球/土豆头/挑战赛背后是 ToTT、VP 邮件、工程生产力团队背书，以及"认证级别与稀缺测试资源分配挂钩"的真实利益杠杆；失去利益杠杆与高层背书的组织照搬，只剩一张空表格。创始人还自嘲"Test Certified"这个名字易引来官僚主义联想。
- **对小团队可简化为 L1-L3**：L4（总覆盖率≥40%+冒烟≤30 分钟+无非确定性）与 L5（≥60%+每缺陷配套测试）维护成本高，小团队到 L3（重要变更全测+小型增量过半+重要功能有集成测试）即可停，把余力投向探索式测试与发布反馈。
- **书中失败模式**：目标过高致团队受挫欲退出（被迫下调）；L1→L2 跨度过大（插级救回）；教练访谈明言最困难一步是"所有重要代码变更都经过测试"——对可测试性差的遗留代码团队，达标前须先做可测试性重构。
- **作者盲点**：认证度量的是"测试行为的存在"而非"测试的有效性"——覆盖率可被空测试灌水，级别高不等于漏测少；它服务于"让开发写测试"这一特定历史阶段，创始人在 2011 年已宣布"完成了使命"——达成文化目标后阶梯本身会被废弃，不要把它当永久制度供奉。
