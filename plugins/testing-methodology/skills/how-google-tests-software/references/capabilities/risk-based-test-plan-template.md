# 基于风险的大型项目测试计划模板

## R（原文摘引）

> "要想合理地处理这些测试问题，必须采用基于风险的测试策略，也就是说测试团队将优先关注系统中风险最高的区域，然后按风险次序依次处理。"（附录A A.1）

> "把已经存在的能够降低这些风险的策略（如现有的测试用例、自动化测试、用户试用测试、OEM 测试等）从相应的已知风险中扣除。把所有组件根据剩余风险进行排序，然后通过开发测试用例、自动化和流程改进等措施来应对。"（附录A A.2）

> "每天都会对持续构建的最新可测试版本（LKG）执行以下测试。一系列功能验收测试的手工执行……功能回归测试自动执行……滚动式执行压力测试、可靠性测试、稳定性测试等。"（附录A A.4）

## I（解释）

本卡来自附录 A——一份真实的 Chrome OS 测试计划全文，是全书"大型/硬件类项目测试计划"的实物模板。骨架 = 栏目清单 + 三级测试节奏 + LKG 概念。

**模板栏目清单（A.1–A.24，每栏都是防遗漏检查项）**：
①主题概述——声明七条策略原则：基于风险 / 自动化硬件测试组合 / 支持快速迭代 / 开放测试用例与工具 / Chrome 为主要平台 / **测试提供数据而非保证质量**（质量取决于所有参与者，测试的目标是降低风险、提供评估与度量）/ 可测试性与乘数效应；②风险分析（见下）；③每次构建基线测试；④LKG 每日测试；⑤发布版本测试；⑥手工与自动化定位（手工在早期 UI 多变与可测试性建设期不可替代；自动化是长期成功与回归关键）；⑦开发与测试的质量关注点分工（开发=丰富单元测试集+重要系统测试；测试=端到端/集成/稳定/扩展/测试报告）；⑧发布通道（按对痛苦的容忍度区分用户群体，质量保证级别递进）；⑨用户输入（反馈扩展+已知 bug 平视显示器 HUD）；⑩测试用例库（自动化用例与被测代码同库存版本）；⑪测试仪表盘（宏观红绿灯+失败下钻）；⑫虚拟化（降低物理硬件依赖）；⑬性能（测试做测量/报告/趋势，不直接开发性能测试）；⑭压力/长时运行/稳定性（故障注入）；⑮测试执行框架（统一封装其他工具的调用接口）；⑯OEM 厂商（发布手册与自动化用例、每日测试含不同硬件）；⑰硬件实验田；⑱端到端自动化集群（多地理位置+时差不间断执行）；⑲时间线（从建设到"所有风险缓解、测试团队放松下来"的季度路线）；⑳测试驱动力（每个技术领域一个负责人）+ 相关文档清单。

**风险分析方法（A.2，剩余风险法）**：罗列所有已知产品特性和能力 → 按出现频次、失效可能性、失效后果（对用户和业务）评估每项的绝对内在风险 → 扣除已有缓解（现有测试用例/自动化/用户试用/OEM 测试）→ 按剩余风险排序 → 用新用例、自动化与流程改进应对。三个目标：质量风险被周知；测试团队始终只关注最高 ROI 任务；存在随产品演进评估新数据的框架。

**三级测试节奏（与发布版本链正交的执行频率维度）**：
- **构建级**（每次持续构建）：开发单元测试之外 + 冒烟测试（P0 自动化）+ 性能测试；
- **日级 LKG**：LKG=Last Known Good，最新可测试版本。每日对 LKG 执行：手工功能验收（可限定每天一种硬件环境）+ 自动功能回归 + 滚动式 Web 应用测试（自动+手工）+ 滚动式压力/可靠性/稳定性（反复执行到无新问题后转每周）+ 持续手工探索式与漫游测试；
- **发布级**（每个发布通道的候选版本）：站点兼容性（Top100 验证）+ 对外示例场景验证 + P0 bug 全量验证（P1 验证 80%）+ 一次全面压力稳定性 + 全部手工测试用例（分派给不同人员与硬件）。

**时间线哲学**：从建设季（定义验收测试/建实验环境/移植框架）经"通过测试和自动化降低风险"的中期，到末期"所有风险得到缓解、没有新问题发现、测试团队放松下来"——计划自带终态定义。

## A1（原书案例 / 合成演练）

**c30：Chrome OS 测试计划（附录A完整文档）。** 作者团队（Whittaker 任 Chrome OS 首任测试经理）为真实产品制定的完整计划，覆盖定制化浏览器/UX/固件/硬件/网络/数据同步/自动更新/OEM 硬件。要点式但栏目齐全：2009Q4 完成风险分析与基于风险的测试计划、2010Q1 建三地实验室+回归自动化+"能令 James 满意的日常探索式手工测试和漫游"、2010Q4"测试团队放松下来"。Chrome OS 于 2010 年 12 月发布。这份计划同时是前序能力的集成实例：A.2 用剩余风险法（risk-heat-map 变体）、A.8 用发布通道（crawl-walk-run-release）、A.4 手工探索漫游（touring-exploratory-testing）、A.15 执行框架统一封装（set-early-involvement 的基础设施思想）。

**合成演练（实例化到新领域：车载 OTA 升级平台）**：主题概述声明"基于风险+测试提供数据+车规安全第一"→ 风险分析列出 OTA 回滚失败/签名校验/弱网中断等，扣除已有 HIL 台架测试得剩余风险排序 → 三级节奏：构建级=单元+冒烟；日级 LKG=手工验收（每天一种车型环境轮换）+自动回归+滚动升级压力测试；发布级=Top 车机型全量+P0 全验证 → 栏目⑯ OEM 替换为车厂适配测试，⑰硬件实验田替换为实车+台架矩阵 → 时间线含"功能安全认证通过"里程碑。

## A2（情境应用）

**触发场景**：
- 接手操作系统、整车、机器人、手机等软硬一体产品，需要从零起草完整测试计划
- 测试计划评审被批"缺硬件环境规划 / 缺 OEM 协作 / 缺发布通道设计"
- 多团队多硬件组合下，测试执行节奏（每次构建/每日/发布各跑什么）没有共识
- 为大型项目立项书/投标书写测试方案章节
- 计划写完即过期，需要一份"随产品演进可更新"的计划骨架

**语言信号**（中英双语）：
- 中文：大型项目测试计划 / 硬件产品测试 / 操作系统测试 / 完整 test plan / 测试计划模板 / OEM 测试 / 硬件实验田 / 每日构建测试什么
- English: test plan for a large project / hardware product testing / OS testing strategy / complete test plan template / OEM test collaboration / hardware test farm / test cadence per build vs per release / last known good (LKG)

**与相邻能力的区分**（初稿）：
- 与 `acc-test-planning`（ACC 计划法）：ACC 是轻量矩阵计划（10 分钟起步、30 分钟 80% 完整性，面向多数产品）；本卡是大型/硬件项目完整计划（A.1–A.24 全栏目、季度时间线、基础设施规划）。判据：产品涉及物理硬件、OEM/多组织协作、发布通道治理 → 用本卡；纯软件迭代 → 用 ACC，勿硬套全模板（那是两种失败方向：小项目背大模板=计划膨胀；大项目只填矩阵=漏基础设施）。
- 与 `risk-heat-map`（风险热图）：本卡 A.2 栏目直接消费那张卡的产出（热图给能力级频率×影响，附录 A 变体加"扣除已有缓解"得剩余风险）。先做风险分析，再填三级节奏——节奏由风险排序决定，顺序不可倒。
- 与 `crawl-walk-run-release`（爬走跑发布）：本卡 A.8 发布通道栏目是该能力在大型计划中的落位；版本链答"哪个版本给谁用"，本卡答"测试计划里如何规划全部栏目"。
- 与 `test-org-pathologies` 缺陷三：本卡是"完整但不膨胀"的范本——各栏要点式、量化值按项目重定，避免数百页没人看的散文计划。

## E（可执行步骤）

1. **填主题概述与风险分析**：写 5–7 条策略原则（必含：基于风险、测试提供数据而非保证质量、可测试性乘数效应）；做剩余风险分析——罗列特性与能力 → 评内在风险（频次×失效可能性×后果）→ 扣除已有缓解 → 排序。完成标准：原则经团队评审确认；风险排序表每项有"内在风险-缓解=剩余风险"三列记录。
2. **定义三级节奏与分工**：构建级（单元+冒烟 P0 自动化+性能）/ 日级 LKG（手工验收+自动回归+滚动压力稳定，无新问题后降频每周）/ 发布级（兼容性+场景+P0 全量验证+全面压力+全量手工）；明确手工与自动化的边界（早期 UI 多变期手工为主）与开发/测试分工（开发=单元+系统测试；测试=端到端/集成/稳定/报告）。完成标准：每级有触发条件、测试内容与放行标准；LKG 选取规则写明；分工有双方确认。
3. **补齐基础设施与时间线栏目**：逐栏填发布通道/用户输入/用例库/仪表盘/虚拟化/性能/压力稳定/执行框架/OEM/硬件实验田/端到端集群/时间线/测试驱动力——不适用的栏目写"不适用+理由"而非删除。完成标准：A.1–A.24 每栏有内容或明确豁免说明；每栏有负责人（测试驱动力清单）；时间线含终态定义（风险缓解完毕的判定）。

**输入契约**：产品范围（特性/能力清单、硬件与 OEM 环境、发布节奏）+ 风险分析（可来自 `risk-heat-map` 卡的产出；缺失则先做步骤 1 的风险分析再继续）。
**输出契约**：逐栏目填写的计划骨架（A.1–A.24），每栏目附一句填写指引；组织级附加产出=三级节奏执行表与测试驱动力（负责人）清单。
**判停点**：①项目为中小组件或纯软件快速迭代 → 判停本模板，转 `acc-test-planning` 轻量矩阵；②风险分析未完成 → 不填节奏栏目（无排序依据的节奏是拍脑袋）；③硬件/OEM 环境信息未确认 → ⑯⑰栏目挂起并显式标注"待硬件信息"，不得虚构组合矩阵；④时间线无法给出终态判定（什么叫"测完"）→ 计划未完成，回到风险表定义出口标准。

## B（边界）

**反场景**：每周多次发布的 Web 应用不需要本模板（ACC+风险热图+漫游足够，硬套 24 栏目制造官僚产物）；客户明确要求散文式计划或法规强制格式时，本模板作底稿再套外层格式。
**书中失败模式**：传统测试计划"最早出现、最先被遗忘"（写完即扔、不评审不更新、功能变更从不触发计划更新）——本模板的解药是 A.2"存在能随产品演进评估新数据的框架"，即风险排序要绑定真实数据源持续更新，否则一样速朽；统一全公司 dashboard 的尝试在 Google 年年夭折（各团队指标观不同），⑪仪表盘栏目应止步于本项目。
**作者盲点/局限**：①量化值为 Chrome OS 特定——P1 验证 80%、Top100 站点、300 个常用站点、每六周三通道五平台等均须按项目重新确定，模板交付的是"栏目+填写指引"而非数值；②各节内容深度不均（原书多为要点式），硬件田/集群等栏目的具体建设方法书中未展开，需补充组织自己的基础设施知识；③栏目可裁剪但裁剪要留痕（写"不适用+理由"），静默删栏会丢失防遗漏价值；④OEM 栏假设厂商愿意承担部分测试责任，对强势供应商或纯自研硬件的场景需要重新谈判分工；⑤时间线以"测试团队放松下来"收尾是理想态——原书同章承认现实发布常由日期而非测试判断决定，终态定义应包含"计划中的放松"与"商业上的提前发布"两条出口。
