# SWE/SET/TE 三角色模型

## R（原文摘引）

> "对于功能代码而言，思维模式是创建，重点在考虑用户、使用场景和数据流程上；而对于测试代码来说，主要思路是去破坏，怎样写测试代码用以扰乱分离用户及其数据。"（第2章开篇）

> "测试是独立存在的部门，是与专注领域部门平行的部门（横跨各个产品专注领域），我们称为工程生产力团队。测试人员基本上以租借的方式进入产品团队……由于测试人员并不是直接向产品团队进行汇报，因此我们并不是简单地被告之某个项目急需发布就可以通过测试。"（1.3）

> "其他公司要想效仿Google的做法，应该从这四个方面做起：技能、稀缺性、自动化和迭代集成。这就是Google测试的'秘方'，照方抓药吧！"（4.12）

## I（解释）

用"三种思维"而非技能清单划分职责，组织归属服务于职责：

1. **SWE 软件开发工程师（创建思维）**：实现用户功能，创建设计文档、选数据结构与架构；同时编写并维护自己代码的测试（测试驱动设计、单元测试、参与各规模测试），对所写代码质量负全责——"还有谁能比实际写代码的人更适合做测试"。
2. **SET 软件测试开发工程师（破坏思维）**：100% 编码角色，重心是可测试性与通用测试框架；参与设计评审、为可测试性重构代码、提供 mock/fake 与单元/自动化测试框架，**让 SWE 能自己测试自己的功能**——SET 不替 SWE 兜底写用例，而是消除"写不了测试"的障碍。
3. **TE 测试工程师（用户思维）**：把用户放在第一位；组织整体质量实践（用例/用户故事/探索式测试），分析解释测试运行结果、驱动测试执行、项目后期推进发布；是产品专家、质量顾问与风险分析师，对 SWE/SET 已做的测试做"双重确认"。

边界一句话：SWE 管功能实现及其质量，SET 管可测试性与测试基础设施，TE 管模块集成后对最终用户的价值与风险。

**组织设计与为何保持独立**：SET/TE 不隶属产品团队，而属横跨各产品专注领域的工程生产力中央部门，以借调方式进入产品团队——对抗"测试为开发让路"（资深管理者多出身 PM/开发，发布时质量让位，作者称从未见过同团队模式真正做到）；产品团队不得降低招聘门槛多招测试做脏活累活；测试资源按产品优先级/复杂度跨产品比较后分配；满 18 个月可无理由转岗，让好方法随人流动（推广测试创新的最好方式是把发明者借调过来）。

**成功公式四要素（4.12）**：技能（会写代码的测试人员）、稀缺性（测试资源稀缺→逼出优先级纪律并换来开发配合）、自动化（人只做计算机做不好的事）、迭代集成（快速迭代+持续集成+尽早用户反馈）。配套心智是"资源越少，目标越明了（scarcity brings clarity）"——稀缺是聚焦机制而非缺陷。

## A1（原书案例 / 合成演练）

- **c33 Whittaker 重塑 TE 角色**（firsthand，4.12）：针对"TE 角色定义模糊、天平偏向 SET"，Whittaker 与 Pat Copeland 启动约 12 人的测试工程师工作组，第一次会议就列两个列表——TE 角色令人兴奋与感觉不爽之处；据此重新定义 TE 职位与晋升阶梯，TE 晋升由全体 TE 开放投票，最终"测试工程师已经和测试开发工程师的角色具有同样清晰的定义了"。说明角色模型不是给定答案，组织要主动修正角色模糊。
- **配套工具（第3章 3.2.5 侧栏）**：SET/TE 自检双列清单（SET 画像：看烂 API 文档比忘 API 更愤怒、测产品时想打开源码 mock；TE 画像：在已有代码中找错误、惊骇于糟糕 UI、梦想产品影响人们生活），用于个人职业定位与团队组建——"TE 不是不写代码的 SET，SET 不必为发现不了 UI 问题内疚"。

## A2（情境应用）

**触发场景**

- 新建或重组团队，划分"谁写测试、谁管质量、谁守发布"
- 招聘决策："要不要招专职测试？招几个？招什么画像？"
- 测试团队定位争论（QA 是守门人、服务方还是开发伙伴）
- 个人职业定位摇摆（我偏 SET 还是偏 TE）

**语言信号**

- 中文：测试职责分工 / 要不要招测试 / QA 定位 / SET 和 TE 的区别 / 开发测试比
- 英文：who owns testing / SDET vs QA / test-developer ratio / embedded vs centralized QA / test roles and responsibilities

**与相邻能力的区分（初稿）**

- 与 test-org-pathologies：本卡是**静态职责模型**（谁该做什么、边界在哪）；那张卡是**病理诊断**（这个组织生了什么病：测试成拐杖/角色认同压倒产品/崇拜产物/迷信专职测试者）。使用顺序：先本卡定分工，再拿 U9 做定期体检。
- 与 set-early-involvement：那是 SET 角色的具体工作流（设计评审/接口先行/提交队列）；本卡只回答"SET 是谁、产出契约是什么"。
- 与 crowd-and-dogfood-testing：TE"支持他人做测试"的放大形态（dogfooder/众包）在 U13 展开。

## E（可执行步骤）

1. 用三种思维（创建/破坏/用户）把团队现有全部测试职责归类，标出无人认领的格子与双重兜底的格子。
2. 填职责分配表：行=角色（SWE/SET/TE/其他质量伙伴），列=产出契约（必须交付什么、对什么负责、**明确不做什么**）；用 3.2.5 自检清单核对成员倾向与岗位是否错配。
3. 对照成功公式四要素自评（技能/稀缺性/自动化/迭代集成各缺什么），给出第一条补齐动作。

**完成标准**：职责分配表无空格且每行"不做什么"边界栏非空；SET/TE 自检有结论（谁在错位、是否该转岗）；四要素评分有明确的最低项与对应动作。

**输入契约**：团队规模与技能盘点、现有测试职责清单、招聘计划。

**输出契约**：职责分配表（角色×产出契约，含边界栏）+ SET/TE 自检结论 + 四要素差距与第一条动作。

**判停点**：团队 <10 人且无独立测试编制 → 只复制职责模型（三思维+产出契约），不建中央部门与借调制（见 B）；组织正处于"要不要撤并测试部"的转型争论 → 先用 test-org-pathologies 卡诊断，再回来定分工。

## B（边界）

- **小团队不可复制组织设计**：中央工程生产力+借调制+18 个月自由转岗，以 Google 万人规模、强内部流动性和稀缺的高技能测试人才池为前提；小团队只复制职责模型与思维分工，勿模仿编制与汇报线。
- **ce08 招聘太多测试人员（幸存者偏差警告）**：原书引言"当有人来问我，Google成功的关键是什么，我的第一个建议就是，不要招聘太多的测试人员"。人海战术使稀缺性失效→优先级纪律崩坏→脏活累活下沉给测试→"开发造、测试兜底"的依赖结构。注意这是 2012 年大厂语境（有海量高水平开发兜底质量），小团队或外包依赖型组织直接照搬会放大风险。
- **ce20 按 SET 标准筛 TE**：用算法/编程面试筛 TE，会淘汰"技术+用户同理心+端到端视角"的稀缺人才，并在测试团队内制造二等公民层级。
- **ce30 TE 越位做 SET 的活**：TE 沉迷写工具修框架，丢掉全局视角，端到端无人把关——角色边界由关注点定义，错位会同时削弱两个角色。
- **ce07 测试为开发让路**：测试与开发同团队汇报时，"测试总在为开发让路"——角色定义无法对抗汇报线权力，独立部门是该模型的硬前提，缺了它三角色退化为一角色半。
- **作者盲点/自我推翻**：第5章作者自曝该模型的四个致命缺陷（拐杖、角色>产品、产物崇拜、迷信专职测试者），并预言 SET 并入开发、TE 转型测试设计师——三角色模型是 2012 年时点的快照而非终态；"开发测试比无意义"的说法在有外包/众包依赖的组织中并不成立。
