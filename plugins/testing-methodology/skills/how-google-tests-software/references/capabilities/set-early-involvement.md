# SET 早期介入工作流

## R（原文摘引）

> "如果一个产品太长时间没有测试的介入，早期在可测试性上的槽糕设计在后期也很难去做改进，这样会导致自动化难以实施且测试工具极不稳定。"（2.1.3）

> "SET是第一个实现所有接口和协议的人。为了能够尽早地开始做集成测试，SET针对各个模块的依赖提供了mock或fake的实现。虽然功能模块代码还没有实现，集成测试的代码就已经可以开始编写了。"（2.1.6）

> "试图在一个测试套件中自动化所有端到端的测试用例，这是一个常见的错误。……规模更小且目的性更强的自动化计划，并存在可以提供帮助的测试框架，这些会吸引SWE一起参与测试。"（2.1.7）

## I（解释）

SET 在"概念定型之后、代码定型之前"介入的标准动作序列：

**0）时机决策**：概念期/原型期不投入（原型多半重写，"只有在软件产品变的重要的时候质量才显得重要"，给注定失败的项目建测试设施是浪费）；正式立项后、开发总监向工程生产力团队寻求资源时，测试方要求其提供当前测试状态、期望的单元测试覆盖率、发布责任划分——开发有义务证明项目值得测试投入。过晚介入则可测试性债务拖慢发布可达数年。

**1）设计文档评审（第一审阅人，六维度）**：完整性（找残缺与需背景知识处，要求补细节或外链）、正确性（语法拼写标点）、一致性（图文一致、不与其他文档矛盾）、设计（目标在资源内能否达成、框架用法是否正确、过度还是不足、可否简化）、接口与协议（定义清晰完整、跨产品统一标准）、测试（可测试性如何、是否需测试钩子、能否用已有框架、预估测试工作量写进文档）。附带收益：审完全部文档的 SET 对项目整体了解超过技术负责人，早期建议沉淀进文档即影响力。

**2）接口协议先行**：接口定义是项目第一份源码（Google 用 protocol buffer）；SET 系统审查协议代码，并**第一个实现所有接口与协议（mock/fake 版）**——集成测试因此在功能代码完成前即可编写运行；依赖服务的期望错误场景与条件异常也因 mock/fake 而易制造，同时支撑多服务并行开发。

**3）自动化计划三步 + 反面约束**：先隔离易错接口建 mock/fake 保覆盖率 → 建轻量级自动化框架控制 mock 系统的创建与执行 → SWE 提交前用 mock 接口做私有构建跑自动化，保证只有经过良好测试的代码才入库；再用报表/仪表盘向所有关心的人公开质量信息。**反面约束：不要试图在一个套件里自动化所有端到端用例**——过度投入会与未稳定的产品设计绑定，维护成本大且得不到 SWE 帮助。

**4）代码审查与提交队列闭环**：代码以 CL（变更列表）为单元封装（过大拆分）；提交审查前自动静态检查（代码风格+关联测试通过）；发给有"可读性"资格的 SWE/SET 审查，循环至双方满意；提交队列在干净环境编译并运行所有测试、全绿才入库——构建系统与版本控制之间的最后一道防线；团队成员轮值"构建警察"快速响应。

**离合点（判停）**：过早大规模自动化会因架构变化全部作废，过晚则错失塑造可测试性的时机——像手动挡起步要找离合点；TDD 是避开离合点问题的方法之一。

## A1（原书案例 / 合成演练）

- **c04 Chrome OS 原型期**（firsthand，2.1.3）：立项前只有几个开发用脚本与 fake 做原型拿演示、过立项批准（演示脚本终将被 C++ 重写，早期投入测试无价值）；正式立项后开发总监找工程生产力团队寻求测试资源，须交代已有测试状态、期望覆盖率、发布责任——时机决策两端的实证。
- **c05 AddUrl 实例**（worked_example，2.1.9）：从 addurl.proto 定义接口（AddUrlRequest/AddUrlReply/RPC）→ BUILD 构建规则 → AddUrlFrontend 类实现 → 用 FakeAddUrlService 依赖注入编写单元测试（覆盖 error_code 400 等错误流程）→ 提交 CL 走代码审查——SET 参与开发工作流的全过程演示；书中注明"有经验的敏捷测试高手会用 mock 替换或补充 fake"。
- **c06 提交队列由来**（reported_case，2.1.8 侧栏 Jeff Carollo 口述）：单元测试展板（每日全库测试报表）→ Chris/Jay 持续构建（持续运行+通知最近提交者+黄金变更列表）→ 提交队列（预提交隔离并发测试，大团队免代码冻结同分支开发），最终固化为 TAP 平台，成员轮值构建警察——"整套系统在Google存活了相当长的时间（数以年计）"。

## A2（情境应用）

**触发场景**

- 新项目立项/设计评审排期，测试方问"我们现在就该进场吗"
- 代码写完才发现依赖无法 mock、可测试性无从谈起
- 想上提交队列/CI 门禁（红色不发布）
- 自动化计划不知从哪块下手，或正打算"把所有端到端用例都自动化"

**语言信号**

- 中文：设计评审 / 可测试性 / 什么时候开始测试 / 提交队列 / mock 还是 fake / 接口先行
- 英文：design review / testability / shift-left / submit queue / pre-commit tests / contract-first / mock vs fake

**与相邻能力的区分（初稿）**

- 与 test-size-model：规模模型回答"测试怎么分级（小/中/大）与环境约束"；本卡是 SET 在开发流程里的动作序列。mock/fake 的强制性与环境约束在 U3 展开。
- 与 test-certified-ladder：认证阶梯面向团队文化推行（让开发普遍写测试）；本卡面向单个 SET 的工作流。L2 的"提交前冒烟"是本卡第 3 步的团队化版本。
- 与 automation-scope-and-maintenance：那是自动化取舍准则与维护期瘦身；本卡的"轻量优先、别端到端全自动化"是同一思想在计划期的入口。

## E（可执行步骤）

1. 判定项目阶段：概念/原型期→不投入；已立项→立即介入，交接会上索取三件事（已有测试状态、期望单元测试覆盖率、发布责任划分）。
2. 按六维度评审设计文档，产出评审问题清单；逐条审查接口/协议定义，圈出易错接口，做 mock/fake 计划（谁实现、覆盖哪些错误场景与条件异常）。
3. 定轻量自动化方案：易错接口隔离→轻量框架→提交前私有构建闭环；显式写一份"自动化不做清单"约束范围。
4. 接入 CL 审查与提交队列（或现有 CI 必要检查等价物），定义"构建警察"轮值。

**完成标准**：评审问题清单六维度各至少一问；mock/fake 计划含接口×错误场景表；提交前测试可本地一键运行；"自动化不做清单"已文档化并获团队认可。

**输入契约**：项目阶段说明 + 设计文档 + 接口/协议定义（或定义接口的承诺）。

**输出契约**：设计评审问题清单 + mock/fake 实现计划（接口×错误场景）+ 轻量自动化方案（含不做清单）+ 提交门禁方案。

**判停点（离合点）**：接口未冻结、两周内大概率重写 → 暂停大规模自动化投入，只保 mock/fake 与最小冒烟，等架构稳定再放量；功能代码已完成数周才介入 → 跳过步骤 1-2，从可测试性重构与自动化补课开始（质量债路径）；SWE 无一人愿意在提交前跑测试 → 先解决动机（回头用 test-certified-ladder 的推行机制），别先建框架。

## B（边界）

- **工具名不可迁移、机制可迁移**：Mondrian/TAP/protocol buffer 是 Google 内部生态；等价机制=现代 PR 审查流+CI 必要检查+接口描述语言（OpenAPI/gRPC IDL）+预提交钩子。"可读性"资格机制的等价物是 CODEOWNERS+代码风格门禁。
- **ce26 无小规模试验就大规模投入**："假设我们知道用户的需求，然后进行了大规模的改动……却没有进行小规模的试验。如果用户不喜欢这些改动，麻烦就大了，而针对这些特性构造的测试框架再好也是浪费"——测试投资应滞后于需求验证（先少量用户放量获反馈，再投大量自动化）。
- **ce31 自动化宏大目标**："投入人力编写那些不能经受时间检验的自动化测试是最大的一种浪费"——为远大目标花数月，产品/平台一次变化即清零；自动化须快速编写、快速执行、解决特定问题。
- **ce28/离合点（双向失败模式）**：过早写测试，架构一变全部作废；等待太久，错失良机导致测试不充分——"可测试性从未出现在设计评审中"是过晚的典型信号。
- **作者盲点**：六维度评审与"SET 第一个实现协议"默认 SET 具备与 SWE 等同的编码与架构能力（原书承认这样的人"实在太难招"），技能不足的 SET 只能做文档批注，接口先行会退化为口头承诺；流程还隐含"设计文档真实存在且持续更新"——文档缺位的团队第一步是补设计文档，否则评审无从谈起。端到端自动化反约束亦有例外：无法在线更新的产品发布前仍需较重的端到端验证（原书语境为可快速迭代的 Web 产品）。
