# 自动化取舍与维护模式瘦身

## R（原文摘引）

> "如果能够自动化，并不需要人脑的智睿与直觉来判断，那就应该以自动化的方式实现。但在一些情况下需要人类智慧的判断，例如，用户界面是否漂亮、保留的数据是否包含隐私等，这些还是需要手动测试来完成。"（第1章 1.5）

> "总是通过的测试，淘汰！在高优先级的测试都来不及做的时候，低优先级的测试，淘汰！"（第3章 3.2.7）

> "自动化测试需要能够快速编写、快速执行、解决特定的问题。如果你不能立即理解一个自动化测试用例的目的，那就说明这个用例太复杂了。"（第4章 4.5）

## I（解释）

方法骨架分两部分：投入侧的取舍准则（写不写自动化），退出侧的维护模式瘦身（项目降级时怎么撤）。

**投入侧四条准则：**
1. **判断准则（是否需要人类智慧）**：不需要人类智慧与直觉判断的，自动化（测试规模越小越应自动化）；需要人类判断的（界面美观、数据隐私等）手动做。手动测试被密切关注，日后可被自动化替代——手动测试倾向关注新功能，自动化测试反复回归。
2. **三条件 + 可理解性自检**：一条自动化用例要能快速编写、快速执行、解决特定问题；自检——若不能立即理解这个用例的目的，它就太复杂了。
3. **20/80 边界**：约 20% 的用例覆盖 80% 的使用场景，只自动化这 20%，其余留给手工——避免在长尾用例上耗尽自动化维护预算。
4. **90/10 人机分工**：让机器完成 90% 的工作（如所有设备抓屏+对比算法找差异），剩下 10% 的验证留给人力（"最后一英里"）；人力资源不浪费在计算机能完成的事上，只用在最适合人判断的场合（参照比对、组合爆炸的验证）。

**退出侧——维护模式淘汰方针**（项目降级/资源撤离时把质量维护成本压到近零）：
- 总是通过的测试，淘汰（从不失败的测试不提供信号）；
- 高优先级测试都来不及做时，低优先级测试，淘汰；
- 淘汰前从待淘汰领域挑几个代表性用例理解意图（可能的话与原作者聊），避免失误；
- 抛弃曾误报/行为反常的自动化——它们只发错误警报，浪费工程师时间。

**撤离前五件事**：①把困难的问题解决掉而不是轻易放过（遗留疑难 bug 会在无人时恶化——Google Desktop 硬盘吃满 bug 即靠请回原开发才定位）；②建立小型端到端自动化冒烟测试集（近乎零成本提供长期质量保证，没有就建）；③留 how-to 文档，使公司任何人可运行测试集（减少将来被突然打扰）；④确定问题解决通道（escalation path）并愿意承担责任；⑤时刻准备返回帮忙。

**底层原则**：代码（产品与测试）都会随时间变坏；维护模式下大部分工作是监控质量而非寻找新问题；后来者必须给测试瘦身。释放出来的时间投入自动化、高优先级测试或探索式测试。

## A1（原书案例 / 合成演练）

**c25/ce25：Gmail 脆弱的 WebDriver 测试集（反例）。** 接手时测试团队只跑一套 WebDriver 回归：每版本从绿变红，再花大力气修回绿；代码大变更时测试根本来不及改。"开发团队没过多质疑这种做法，因为测试通常还能发现一些重要问题"——低效模式因偶发价值而延续。判断标准：让它最终发挥作用所需的工作量超出产出，即为过度投入。教训指向 20/80：识别覆盖 80% 场景的 20% 用例自动化，其余手工。

**Google Desktop 2500→150（维护模式正例，第3章 3.2.7）。** 项目转维护时遗留约 2500 个用例：大量引用已死特性的暗语、假设隐式机器状态，知识只存在于外包人员脑中，回归周期一周以上。处置：逐条审读 2500 个用例（基于对产品的认识保留最重要最有意义的）→ 只剩约 150 个（数量级缩减）；与外包一起重写描述至"任何用过一会儿产品的人都能执行"；建立小型自动化冒烟集覆盖高优先级功能；撤离前解决 Outlook 用户硬盘被索引吃满的疑难 bug（督促 PM/开发、请回原开发定位）；对下线功能设定时提醒并简化实现；留 how-to 文档+随叫随到外包。此后发布顺利，自动化测试长期运行。

**c32：RPF"重录比修复快"（维护经济学）。** Chrome 网上商店的 Selenium 脚本因产品频繁变化经常失效。RPF 实战第一周：77% 功能获覆盖、生成脚本比 Selenium/WebDriver 快约 8 倍、发现 6 个功能回归。意外发现：作者精心开发的"模糊匹配自动修复"几乎没被用到——测试失效时直接重新录制一遍反而更快（反正要手工验证功能，顺手重录）。维护成本的比价对象不是"零成本"而是"重录成本"。

## A2（情境应用）

**触发场景**：
- 规划期争论"哪些测试该自动化、自动化到什么程度"
- 自动化维护成本失控：每发布固定节目是"修红"，团队大部分时间在改测试而非测新功能
- 遗留用例库膨胀多年：只有特定某人能跑回归、用例引用已死特性、从不失败的测试占据执行时间
- 项目降级/团队转岗/产品进入维护期，需要标准化撤离
- 平台或 UI 大改版前夕，评估既有自动化资产保留多少

**语言信号**（中英双语）：
- 中文：哪些测试该自动化 / 自动化维护成本 / 遗留用例清理 / 项目转维护 / 测试瘦身 / 冒烟测试集 / 自动化投入产出 / 测试总是通过要不要删
- English: what should we automate / test maintenance cost / legacy test suite cleanup / maintenance mode testing / test suite slimming / smoke test suite / automation ROI / tests that always pass / brittle UI tests

**与相邻能力的区分**（初稿）：
- 与 `test-size-model`（测试规模模型）：规模模型回答"这条测试属于小/中/大型"（分类口径与执行约束）；本卡回答"这条测试值不值得自动化、什么时候该淘汰"（投资与退出决策）。小测试默认自动化是本卡准则1在规模维度上的投影。
- 与 `set-early-involvement`（SET 早期介入）：那张卡管自动化的"生"（何时开始建、建多轻）；本卡管自动化的"死"与"边界"（何时停止扩张、如何撤退）。二者共用"离合点"判停：产品剧烈变化期不做大规模端到端自动化。
- 与 `bug-lifecycle`：误报侵蚀公信力（红了就当异常跳过）是 bug 定级失真的上游原因；本卡"抛弃曾误报的自动化"既是瘦身方针也是公信力修复。

## E（可执行步骤）

1. **自动化候选筛选**：对候选用例先问"是否需要人类智慧判断"（美观/隐私类排除）；通过者再过三条件（快速编写/快速执行/解决特定问题）+ 可理解性自检（能否立即说出目的）；最后用 20/80 聚焦——从覆盖 80% 使用场景的约 20% 核心用例开始。完成标准：自动化候选清单每条有三条件判定记录与目的一句话。
2. **淘汰决策**：对既有用例集执行淘汰方针——总是通过的进淘汰表；高优先级来不及做时低优先级进淘汰表；曾误报/行为反常的自动化直接抛弃。淘汰前从待淘汰领域抽代表性用例理解意图（能找到原作者就聊一次）。完成标准：淘汰决策表逐条可复核（每条有淘汰理由），保留用例的描述改写到"任何用过一会儿产品的人都能执行"。
3. **维护模式撤离（项目降级时）**：按五件事清单执行——解决遗留疑难 bug → 建小型端到端自动化冒烟集 → 写 how-to 文档 → 确定 escalation 通道并担责 → 承诺可返回帮忙。完成标准：五项全部勾选；冒烟集可一键执行且覆盖高优先级功能；无文档依赖的口头知识残留。

**输入契约**：用例集（手工+自动化，含执行频率与近次结果）+ 维护痛点描述（修测试耗时占比、误报率、执行时长、能否独立运行）。
**输出契约**：自动化候选清单（含三条件判定）+ 淘汰决策表（含理由）+ 小型冒烟测试集 + how-to 文档。
**判停点**：①产品仍处剧烈变化期（UI 频繁改版、架构未稳）→ 判停大规模端到端自动化（离合点：过早=架构一变全部作废）；②修某条测试的时间超过该测试创造的价值 → 进淘汰表而非修复队列；③淘汰会移除某高风险能力点唯一覆盖时 → 保留并补冒烟集，宁可多留不可裸奔（与风险热图联动核对）。

## B（边界）

**反场景**：强监管领域（医疗/航空）的合规测试集不能按"总是通过就淘汰"处理——通过记录本身就是审计证据；安全关键路径的冗余测试即便从不失败也须保留。20/80 不适用于正确性优于长尾覆盖的协议/编译器类软件。
**书中失败模式**：ce19 重型 UI 端到端——测试金字塔倒置，每次 DOM 变动成片失败，维护吞掉新功能测试产能（"只保留少数验证端到端集成场景的高级别冒烟测试，其余尽可能底层"）；ce25 脆弱测试集——因偶尔发现重要问题而延续低效模式；ce31 自动化宏大目标——数月热情投入，平台一次变化全部付之一炬，"投入人力编写不能经受时间检验的自动化测试是最大的一种浪费"；误报导致"标记异常放行提交"，测试体系名存实亡。
**作者盲点/局限**：①比例依赖产品理解——20/80、90/10、2500→150 是经验数量级而非固定百分比，Gmail 的 20% 与一个内部工具的 20% 内涵完全不同，切勿当 KPI 硬套；②"维护模式"触发条件（项目何时算进入维护）原书未定义，需组织自定（常见信号：特性冻结、团队转岗、仅安全补丁）；③RPF"重录比修复快"仅验证于数据驱动 UI 的 Web 场景，文件上传/安全检出等需本地代码的场景无法纯 Web 自动化；④淘汰"总是通过的测试"隐含假设：历史通过=未来无风险。对即将大改的模块，从不失败的测试恰是变更后的预警资产，应在淘汰前与变更计划核对。
