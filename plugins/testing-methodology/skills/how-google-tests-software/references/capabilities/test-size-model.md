# 测试规模模型：小/中/大

## R（原文摘引）

> "Google并没有使用代码测试、集成测试、系统测试这些命名方式，而是使用小型测试、中型测试、大型测试这样的称谓，着重强调测试的范畴规模而非形式。"（第1章 1.5）

> "小型测试是为了验证一个代码单元的功能。中型测试验证两个或多个模块应用之间的交互。大型测试是为了验证整个系统作为一个整体是如何工作的。"（第2章 2.1.11）

> "小型测试带来优秀的代码质量、良好的异常处理、优雅的错误报告；大中型测试带来整体产品质量和数据验证。单一的测试类型不能解决所有项目需求。"（第2章 2.1.13）

## I（解释）

按**范畴规模**（涉及多少模块、环境真实度）而非形式给测试分类，三档定义：

- **小型**：验证单个代码单元（一个类或一组相关函数），范畴隔离、无外部依赖。外部服务（文件系统、网络、数据库）**必须**用 mock 或 fake；必要时被测类所在模块的内部服务也可模拟。运行秒级（定性），最频繁执行——开发改完功能代码立刻跑，反馈最快、错误隔离最容易，是边界场景与错误条件（如空指针）的专长。
- **中型**：验证两个或多个模块之间的交互（Google 之外的"集成测试"）。mock 是**鼓励但不强制**——出于性能考虑可以不用，可用轻量 fake（如常驻内存的数据库）替代。运行更久，执行频率受控，一般由 SET 组织运行。
- **大型**：端到端验证系统整体如何工作（Google 之外的"系统测试/端到端测试"），涉及一个或所有子系统、从前端到后端数据存储，可依赖真实外部资源（数据库、文件系统、网络服务）。数小时级（定性），因外部依赖而具非确定性。

时间与资源的精确上限在原书表 2.1/2.2 插图中未解析（needs-review 已登记），只用定性量级：小型秒级、中型更久、大型数小时。规模标签供共享测试平台调度：超时或超资源即取消并报错，迫使工程师打准标签。

**三类优缺点要点**：小型带来代码质量、异常处理、错误报告，且快速、可靠、易隔离错误——但不做模块间集成（那是中型的事），子系统有时难以模拟，mock/fake 可能与真实环境不同步。中型是大型与小型之间的过渡、较快速可频繁运行、在标准开发环境中开发人员也能跑——但依赖外部系统、有不确定性、不如小型快。大型验证最根本的"考虑外部系统时应用如何工作"——但非确定性、失败根源难定位、测试数据准备耗时、想走到特定代码路径不切实际。

**70/20/10 经验法则**：70% 小型、20% 中型、10% 大型；面向用户、集成度高、UI 复杂的产品应有更多中大测试，基础平台或数据类项目（索引、网络爬虫）应以小型为主。

**覆盖率组合诊断**：分别生成小型测试与中大型测试的覆盖率报告——小型近 100% 而中大型仅 20%，说明项目缺乏端到端的功能验证；数字反过来，说明项目难升级扩展和维护（小型太少，大量时间耗在底层调试查错）。

**两条铁律与排障**（公用执行环境）：每个测试与其他测试独立（可任意顺序、可并发执行）；不做数据持久化（退出时环境状态与进入前一致）。资源冲突症状：并发时用例互相失败、连累守规矩的用例（两个测试绑同一端口/同一路径建相同目录/一个建表一个删表）。操作：执行系统为每用例分配未使用端口并让被测系统动态绑定、临时目录 + 唯一目录名、每用例独立数据库实例。验证：随机顺序执行暴露对顺序有依赖的用例。

## A1（原书案例 / 合成演练）

**原书案例：AddUrl 网络应用（worked_example，第2章 2.1.9）**。输入：一个允许用户向 Google 提交 URL 并加入索引的简单网络应用。执行：从 addurl.proto 协议定义接口 → 实现 AddUrlFrontend 类 → 用 FakeAddUrlService 依赖注入编写单元测试（googletest 风格），覆盖期望分支与错误流程（如 error_code 400）；书中明确说明中型、大型测试与环境隔离，原书还提醒"有经验的敏捷测试高手会指出所有测试只用 fake 有点单一，也可以用 mock 替换"。结论：单函数级验证走小型（全 fake）；跨模块交互走中型；整个提交流程的端到端验证走大型——同一功能在三档中各有归属，标签即调度契约。

**合成演练（已标记，源自阶段 1.5 V2 walkthrough）**。输入：三个新测试——(a) 纯函数 isLeapYear 的年份判断；(b) 下单流程走常驻内存 DB 的订单处理；(c) 真实浏览器中从登录到支付完成的完整购买。执行：(a) 单函数、无外部依赖 → 小型；(b) 多模块交互 + 内存 fake DB（性能考虑不用 mock）→ 中型；(c) 端到端、真实环境真实数据 → 大型。组合诊断：若 (a) 类测试覆盖率近 100% 而 (c) 类场景缺失 → 缺端到端功能验证，应补大型测试。结论：三例归类无歧义，诊断结论可从覆盖率数字直接复算。

## A2（情境应用）

**触发场景**：
- 写一个新测试前决定它的规模标签与执行环境（要不要 mock）；
- CI 时长失控、测试互相拖累、调度队列被长测试占满；
- 拿到覆盖率报告，判断项目测试组合是否失衡；
- 团队在"单元测试 vs 集成测试"的术语上争论不休，需要统一口径。

**语言信号**：
- 中文：该写哪种测试、测试分类、测试规模、小中大、单元/集成/端到端、测试金字塔
- 英文：unit vs integration、test size、end-to-end test、test pyramid、test classification

**与相邻能力的区分**（初稿）：
- 与测试金字塔（行业通行说法）：本书按**规模**（范畴 + 环境真实度 + 时长约束）分类而非按形式/层次——三档都可通过共享平台调度并施加超时/资源硬约束，这是"称谓"差异背后的实质差异；70/20/10 与金字塔形状相通，但口径不同。
- 与 automation-scope-and-maintenance（U11）：U11 回答"要不要自动化、自动化到哪停、维护期怎么瘦身"，本卡回答"这个测试属于哪一档、组合比例是否健康"；比例诊断失衡时才轮到 U11 决定增删。
- 与 set-early-involvement（U7）：U7 讲谁在什么时机写测试，本卡讲写出来的测试贴什么标签、受什么约束。

## E（可执行步骤）

1. **逐个定标签**：对每个（新）测试按三问判定——涉及几个模块？外部依赖是 mock/fake 还是真实资源？预期运行时长量级（秒级/更久/数小时）？完成标准：每个测试有规模标签且满足该档约束（小型必须无外部真实依赖；中型 mock 可省但需说明性能理由）。
2. **检查比例健康度**：统计三档数量比例；分别生成小型与中大型两份覆盖率报告（构建/运行工具加一个选项即可，结果应存团队可访问处）。完成标准：得出比例数字与两个覆盖率数字。
3. **诊断并调整**：对照 70/20/10 与产品类型（面向用户高集成 → 偏中大；平台/数据 → 偏小型）判定失衡方向；小型≈100% + 中大 20% → 补端到端；反向 → 补小型。完成标准：写出诊断结论（缺端到端 / 难维护）与补测方向清单。
4. **（排障，按需）处理冲突用例**：以随机顺序执行暴露顺序依赖；对互相失败的用例依次检查端口占用、目录路径、数据库实例三项，按"分配未使用端口 / 临时唯一目录 / 独立数据库实例"处置。完成标准：并发执行无互相失败，或已定位到具体冲突资源。

**输入契约**：必需 = 待分类的测试描述（新测试：被测对象、涉及模块、外部依赖）或既有测试清单 + 各测试的规模标记；做诊断时必需 = 分规模覆盖率数据（拿不到时先问，不猜）。缺失规模标记的既有测试清单 → 先执行步骤 1 补标签。

**输出契约**：分类表（测试名 / 规模标签 / 判定理由：模块数 + 环境 + 时长）或诊断报告（三档比例数字 + 小型与中大型两个覆盖率 + 结论（缺端到端 / 难升级维护 / 健康）+ 补测方向）。排障时输出冲突用例清单与处置记录。

**判停点**：一个测试无法归入任何档（如"单函数却要跨真实网络"）→ 停，先拆分或改造测试本身，分类不接受骑墙；覆盖率数据拿不到 → 停在步骤 2，只报告比例不做失衡结论；团队想照搬精确数值上限 → 停，说明原书数值在插图中未解析（needs-review），以定性量级约定替代。

## B（边界）

**反场景（何时不用）**：
- 全部单一类型都是错的："如果全部使用大型的端到端自动化测试是错误的，全部使用小型的单元测试同样也是错误的"——任何"只写某一档"的策略直接违反本模型；
- 无共享执行平台的小团队，规模标签的调度价值减弱——三档定义与环境约束仍适用，但"标签供调度"一条可降权；
- 一次性验证脚本、演示代码——不是注册在案的测试，不必打标签。

**书中警告的失败模式**：
- ce19 重型 UI 端到端测试（70/20/10 的由来，第3章 YouTube 访谈）："UI 测试的执行比较慢，非常脆弱，维护成本也很高。一个教训是，只保留少数几个用来验证端到端的集成场景的高级别冒烟测试，除此之外尽可能编写底层的测试用例"——金字塔倒置是本模型要诊断的头号失衡；
- 规模标签打错：该小的标大浪费公用资源、该大的标小失去环境真实度——共享平台以超时/超资源取消来倒逼；
- 违反两条铁律：资源冲突不仅自己失败，还连累执行系统中其他正在运行的用例（绑同端口/同目录/建删同表）。

**作者盲点/时代局限**：
- 精确的时间/资源上限（表 2.1/2.2、中型测试的具体分钟上限）在原书插图中未随文本解析，needs-review 已登记——本卡只使用定性量级（秒级/更久/数小时），任何具体数值须由团队自定并声明非原书数值；
- 2012 年成书，"大型测试数小时"以当时 Google 的单体体系为背景；现代云原生与契约测试环境下端到端时长被大幅压缩，但"范畴 + 环境真实度 + 组合健康度"的三档结构逻辑仍然成立；
- 与自动化取舍能力（U11）的边界：本卡只管分类、比例与失衡诊断，"哪些测试该自动化、自动化何时收手"由 U11（f05 判断准则、20/80、90/10）回答，两卡不要混用。
