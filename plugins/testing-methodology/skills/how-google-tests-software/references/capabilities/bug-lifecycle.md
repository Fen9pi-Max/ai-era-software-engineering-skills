# bug 生命周期与双维定级

## R（原文摘引）

> "发现bug、分类bug、修复bug、回归测试是软件质量的心跳和运作模式。"（第3章 3.2.4）

> "在搜索页的图标中的'Google'的错误拼写的严重程度（severity）比较低（页面功能不受影响），但是优先级（priority）高（这将是一件非常糟糕的事情）。填写这两个字段能帮助修复团队更合理的安排时间。"（第3章 3.2.4）

> "许多团队在bug到达的速度超过了其修复能力的时候，干脆不再进行新功能特性的开发。我们强烈推荐这种实践，而反对那种只盯着特性或者代码完成的里程碑的做法。"（第3章 3.2.4）

## I（解释）

方法骨架分四层：状态机、双轴定级、单个 bug 的处理节奏、组织级治理回路。

**状态机（Buganizer 模型）**：New（新建，未指派）→ Assigned（已指派）→ Accepted（已接受）→〔Fix later（以后修复）| Will not fix（不修复）〕→ Fixed（已修复，未验证）→ Verifier assigned（验证者已确定）→ Verified（已验证，关闭）。Resolution（解决方案）枚举：不可行 / 设计如此 / 无法重现 / 废弃 / 重复 / 已修复。字段哲学：只有少数必填（组件/优先级/严重性/状态/摘要/类型/验证者），字段定义故意不明确，留给各团队自定义适配自己的工作流。

**严重性 × 优先级双轴独立**：严重性 = 对产品正常使用的影响程度（S0 系统不可用 ~ S4 无影响）；优先级 = 希望多快被修复、投入多少资源（P0 最高）。两轴必须独立填写：品牌性小问题可以"严重性低 + 优先级高"（Google 图标拼写错误反例——页面功能不受影响，但对公司是糟糕透顶的事）。双轴帮助修复团队同时排"多严重"与"先修谁"。

**单个 bug 的处理节奏（"bug 的一生"侧栏，父母照顾生病孩子类比）**：发现 → 细细品味（是否在用户可达之路上？这些路径被走到的概率？是否还有其他路径导致同样问题？有无影响数据或其他应用的副作用？有无隐私/安全/性能/可访问性影响？）→ 找同事演示讨论定级（曾以为的 P0 可能无关紧要，避免"狼来了"）→ 用工具完整记录证据（截屏、按键记录、stack trace、DOM dump——"开发得到的信息越多，修复起来就越不可怕"）→ 提交报告触发通知 → 修复产生 CL，走评审与构建 → 新构建就绪后重新执行原用例 → 纳入回归集并尽量自动化（系统对该问题获得"免疫力"）。

**组织级治理**：①"到达速度超修复力则停新功能"——bug 到达速度超过修复能力时，停止新功能开发，集中精力消化存量，反对只盯特性/代码完成里程碑；②无自顶向下的正式 triage——谁评审、怎么定级由团队自定（一人、桌边两人、周会、立会均可）；③人人都是 bug 来源（PM/开发/线上/众包/外包/社区经理/一键报告/API 自动创建）。

**从漏测学习回路（第4章 4.8）**：漏测的 bug 不能止于个案修复——若根因是配置或数据变更未经测试（搜索结果变差事故），就把"配置变更纳入质量流程"：针对出问题的配置及类似变化编写检验测试，每次数据和配置变更时执行，此类 bug 即大幅减少。

## A1（原书案例 / 合成演练）

**合成演练（按原书节奏走一遍）：** 发现"登录页在 Safari 点击无响应"。品味：登录是所有用户的必经之路（可达概率极高）；检查其他浏览器正常，问题限定 Safari+某版本；无数据副作用但阻断主流程。找同事演示后定级：严重性 S1（主功能受阻）× 优先级 P1（登录主路径，须尽快修）——两轴独立填写。用插件采集截图、操作录制、console 日志提交。修复 CL 入库后在新构建上重执行原用例，通过即关闭，并把"Safari 登录点击"加入自动回归集。

**c17：Google Feedback（用户侧 bug 通道）。** 各团队反馈表单每天涌入数千条信息不全的重复报告，无法处理。Google Feedback 用 point-and-click 提交：JS 重实现渲染引擎截取屏幕快照（绕过浏览器不能截自己屏幕的安全限制），用户高亮问题区域+文字描述，可先删掉隐私区域再提交；服务端聚类算法自动识别重复并按报告量排序——新应用上线数万条问题精简到约 10 个主要共性问题，triage 不被重复报告拖垮。

**c08（工具史佐证）：** Buganizer 的前身 BugDB 因 UI 延迟、笨拙工作流"阻碍开发流程的运转"而被重造——教训：bug 库的数据模型和 UI 必须反映真实开发过程（状态机+双轴+自动通知），否则工程师会绕开它。

## A2（情境应用）

**触发场景**：
- 团队争论"这个 bug 算严重还是不严重、先修谁"，定级口径混乱
- bug 报告信息不全，开发反复找报告人复现，或大量 bug 被标"无法重现"
- bug 积压持续增长，团队一边喊缺人一边继续堆新功能
- 用户反馈渠道与内部 bug 库割裂，重复报告淹没 triage
- 同一个 bug 修完又复发，没人建回归用例

**语言信号**（中英双语）：
- 中文：bug 怎么定级 / 优先级和严重性怎么区分 / bug 流程 / bug 状态机 / bug 积压怎么治理 / 回归用例 / bug 描述规范
- English: how to triage bugs / priority vs severity / bug workflow / bug lifecycle states / bug backlog out of control / regression test for the fix / reproducible bug report

**与相邻能力的区分**（初稿）：
- 与 `acc-test-planning` / `risk-heat-map`：那两张卡面向"测什么、先测什么"（能力与风险排序）；本卡面向"发现缺陷之后怎么处置"。风险热图定 P0 概念（能力级），本卡定 P0/S0（单个 bug 级），粒度不同。
- 与 `test-org-pathologies`：本卡缺陷三警告"以 bug 数论英雄"是崇拜产物的症状；本卡只负责让 bug 处置高效，不评价"该不该用 bug 数考核"。
- 与 `automation-scope-and-maintenance`：本卡的"回归免疫"（用例入回归集并自动化）在该卡中决定"哪些回归值得自动化、哪些该淘汰"。

## E（可执行步骤）

1. **双轴定级**：对 bug 独立填两个值——严重性（对正常使用的影响：完全不可用/受阻/需重试可绕过/无感）与优先级（多快修、投入多少资源）。用"Google 拼写错误"反例自检：低严重+高优先是否说得通？若两个值总是同步变化，说明两轴没有真正分开。完成标准：每个 bug 两轴都有值且各自可独立辩护。
2. **全证据记录与提交**：按节奏走——先品味（可达路径/概率/其他致败路径/副作用），再找一位同事演示并校准定级（防"狼来了"），然后采集截图、操作录制、日志等完整证据提交，报告触发通知。完成标准：开发无需联系报告人即可复现（证据链自足）；报告经过至少一次双人校准。
3. **闭环回归免疫 + 漏测学习**：修复验证通过后，把发现 bug 的用例纳入回归集并尽量自动化；对漏测类 bug 追问根因，若涉及配置/数据变更，则把该类变更纳入质量流程（变更即触发对应检验测试）。完成标准：每个已验证 bug 有回归用例（自动化或手工入库）；漏测 bug 有"流程改进"结论而非仅"已修复"。

**输入契约**：bug 描述（现象、复现路径、环境/版本信息；允许粗糙，后续步骤补全证据）。
**输出契约**：双轴定级 + 证据完备的 bug 报告（含状态流转记录）+ 回归用例；组织级附加产出为"停新功能"决策建议与配置变更检验清单。
**判停点**：①无法复现 → 如实标 Not repeatable，不得靠猜测定级；②bug 到达速度持续超过修复能力 → 触发"停新功能"判断并上报决策，不要由测试团队默默消化（那是拐杖化的开端）；③同事演示后认定"无关紧要" → 撤回或降级报告，避免狼来了消耗公信力。

## B（边界）

**反场景**：跟踪工单/客户支持请求的"bug"不在本卡范围（原书明言忽略工单类 bug，只讨论反映代码问题的 bug）；强流程合规组织（要求完整审批链）可加状态但不应破坏"少数必填字段"的轻量原则。
**书中失败模式**：BugDB 因工作流笨拙被工程师绕开（工具反映不了真实开发过程即死）；统一全公司 bug dashboard 的尝试年年夭折——各团队对健康指标的看法不同，强行统一是过度工程（书中明示）；"狼来了"式夸大定级会永久损耗测试公信力；误报/不可重现的报告会让 triage 拖垮（Google Feedback 聚类是解法）。
**作者盲点/局限**：①Buganizer 字段细节属工具史，不迁移——状态机、双轴、回归免疫、停新功能原则这些机制可迁移，具体枚举值、字段名、P0 平均年龄等数据观察是 Google 特定产物；②定级粒度（S0-S4、P0-P4）按组织自定，小团队可简化为三档，但两轴独立性不可省；③"停新功能"原则依赖管理层授权——若测试无此话语权，该原则只是建议而非机制，使用时应先谈妥触发条件（如连续两周到达>修复）与决策人；④P0 bug 平均年龄反常地长（反映严重设计/部署问题）这类统计洞察需要足够 bug 量才有意义，小样本团队勿过度解读。
