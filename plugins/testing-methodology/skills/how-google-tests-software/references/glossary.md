# GLOSSARY — 《Google软件测试之道》术语词典

> 依据全书正文与附录D官方术语表（epub 中为整页图片，已视觉转录核对）。定义句均取自正文原文。
> 此文件同时复制到 `.cangjie/capabilities/book/glossary.md` 供编译打包。

| 术语 | 作者的用法（原文要点） | 与常识的差异 |
|---|---|---|
| **SWE**（软件开发工程师） | 实现用户功能代码的传统开发角色，但"需要编写与测试代码，包括测试驱动的设计、单元测试、参与构建各种大小规模的测试"，对自己写的代码承担质量责任 | ≠ 只写功能不管测试的开发；第2章概括"SWE 是功能开发人员" |
| **SET**（软件测试开发工程师） | 也是开发角色（100% 写代码），重心在可测试性与通用测试基础框架；参与设计评审、为可测试性重构代码；"SET 写代码的目的是可以让 SWE 测试自己的功能" | ≠ 写用例/执行测试的测试员；是让开发能自助测试的赋能者（全书出现 221 次，频率最高） |
| **TE**（测试工程师） | "把用户放在第一位来思考，代表用户的利益"；重点在评估对用户的影响与产品整体风险；做测试计划(ACC)、风险分析、探索式测试、端到端验证、发布判断 | ≠ 执行用例报 bug 的测试员；"Google 的 TE 是用户开发人员" |
| **工程生产力**（Engineering Productivity） | 测试所属的中心组织部门，横跨工具研发、发布、各级测试；SET/TE 隶属它而非产品线，以借调方式进入产品团队以保持测试独立性 | ≠ 泛指"提升工程效率"；是具体组织实体；第5章预言被拆分融入产品团队 |
| **测试规模**（小/中/大型测试） | 按测试范畴规模（涉及模块数+环境真实度）而非形式分类：小型=单函数/全 mock/fake/秒级；中型=多模块交互（"功能近邻区"）/fake 可用；大型=端到端/真实环境/真实数据 | ≠ 单元/集成/系统测试的形式分类；分类自带调度约束（超时/超资源即取消） |
| **功能近邻区** | 作者自造词：多个交互模块构成的区域，中型测试的覆盖对象 | 无行业通用义 |
| **mock / fake** | mock=运行时按假设提供期望结果的模拟（可制造期望错误场景）；fake=固定数据/逻辑的轻量虚假实现（如常驻内存数据库） | 本书刻意区分两者且与测试规模绑定：小型必须 mock&fake，中型鼓励不强制 |
| **ACC** | Attribute/Component/Capacity 三步测试计划替代法：特质×组件交点产生能力，能力直接关联用例与风险打分 | ≠ 散文式测试计划文档；"复杂项目 ACC 分解不到半小时" |
| **特质**（Attribute） | "系统的形容词"，产品区别于竞品的原因（Chrome：快速/安全/稳定/优雅）；目标约12个，1-2小时内完成 | ≠ property-based testing 的属性；来自产品定位/销售话术视角 |
| **组件**（Component） | "系统的名词"，构成系统的模块、测试对象；约10个为宜，20个太多 | ≠ 任意技术拆分；常出现在设计文档/架构图大框 |
| **能力**（Capability） | "系统的动词"，用户指令下系统完成的动作，处于特质×组件交点；"最重要的特点是可测试性"；大型应用可达数百个（Chrome OS 300+） | ≠ CMM 能力成熟度；是风险打分与用例关联的最小单元 |
| **风险 = 失败频率×影响** | 定性相对值而非定量绝对值：频率4档（罕见/少见/偶尔/常见）×影响4档（最小/一些/较大/最大），偶数取值防偷懒，单元格=简单平均出红黄绿热图，只用于排序 | ≠ 概率×损失的数学期望——作者明确反对精确定量 |
| **树靶子策略** | 收集风险意见的沟通法：自己先完成热图再展示，"拿一个明确的结论来引起辩论"，而非空泛征求意见 | — |
| **漫游测试**（Tour） | 用游客漫游隐喻给探索式测试主题与结构：购物/学生/国际长途/地标/通宵/公务/危险地带/个性化八种 | ≠ 无结构随机探索；源自 Whittaker 探索式测试体系 |
| **爬、走、跑**（Crawl, Walk, Run） | 金丝雀→开发→测试→beta/发布四级版本放量节奏，以版本换逐级真实反馈 | ≠ 阶段门式流程；Gmail beta 标签挂了四年 |
| **金丝雀版本** | 每日构建，用来排除明显不宜版本；构建失败=流程出了严重问题；仅产品工程师与管理层使用 | ≠ 任意每日构建的产品发布 |
| **LKG**（Last Known Good） | "最近一次已知可用"的持续构建版本，每日基线测试（手工验收+自动回归+滚动压力稳定）的对象 | ≠ 金丝雀（那是排雷，这是基线） |
| **内部试用者**（dogfooder） | 团队以外真实使用产品的内部员工；"我们想象自己是用户，而内部试用者就是真实的用户"；Google+ 最好的 bug 多由他们发现 | ≠ 内部 QA 环境/演示 |
| **测试产物**（test artifact） | 作者贬义：测试计划/用例/bug 报告都是次要的，"测试的价值在于测试的动作，而不是测试产物"；崇拜它是第三大致命缺陷 | ≠ 中性"测试交付物" |
| **测试认证**（Test Certified） | 对团队代码库测试健康度的分级认证（级别 0-5，逐级有量化门槛如 L4 冒烟≤30分钟/总覆盖≥40%），游戏化推行 | ≠ 对个人的资质认证；官方名 Test Certified |
| **提交队列**（submit queue） | 代码入库前的最后防线：干净环境编译+全测试通过才放行，"构建系统和版本控制系统之间的最后一道防线" | ≠ 事后验证的一般 CI；是前置门禁 |
| **零成本测试**（zero-cost testing） | 限定 Web 领域的理想形态：成本≈0、结果即时、几乎无人为干预；支撑 TE 转型"组织近乎免费的测试资源" | ≠ 一般降本口号 |
