# 需求可测试性审查与优先级

## R（原文摘引）
> 如果需求规格说明中没有足够的信息，不能用相关的测试用例为有关的路径创建完整的测试过程，那么就不能认为需求规格说明书是可测试的。（第1章 第3条）

> 一条需求的整体价值或者在需求涉众心中的重要性等于惩罚分和奖励分之和。（第1章 第2条，Pardee）

## I（解释）
1. **可测试性判定**：能为需求设计出"输入+步骤+可预知预期输出"的完整测试过程 → 可测试；否则标注风险并要求补充/修改需求。
2. **十属性审查清单**：正确性、完整性（功能需求须附非功能性需求）、一致性（术语定义唯一）、可测试性、可行性、必要性、优先级、明确性（"快速响应"须量化为秒数）、可追溯性、质量测度标准。
3. **质量测度标准**（Alexander）：给每条需求一个测度，把候选方案分成满足/不满足两类；模糊大需求拆成若干带测度的小需求。
4. **优先级打分**（Pardee）：奖励分(1-5，存在时的正面价值) + 惩罚分(1-5，缺失时的负面影响) = 价值，按价值排序。
5. **变更控制**：一切变更经变更请求表 → CCB 评估批准 → 基线化版本号 → 设计/编码/测试文档连锁修改 → 传达所有涉众。

## A1（原书案例）
- "系统必须快速响应查询"：客户认为 5 秒、开发认为 3 分钟/2 秒——用质量测度标准（如"95% 查询 <5 秒"）消除歧义。
- "系统必须值得购买"拆成若干可测量小需求。
- 过程崩溃三场景：变更未形成文档 / 用过期需求文档 / 开发私自实现错误。

## A2（情境应用）
接到一份需求文档时：①逐条跑十属性清单，标出失败项；②对不可测试条目写出"缺什么信息才能设计测试过程"；③为每条需求定质量测度标准；④用奖励+惩罚打分排优先级，输出审查报告供需求评审会使用。

## E（评测）
- 输入：任意真实需求列表（含模糊条目）。
- 输出：十属性审查表 + 优先级排序 + 每条不可测试需求的具体缺口。
- 通过标准：每条模糊需求都被拆解或标注了测度标准；排序可复算。

## B（边界）
不替代需求工程本身（只做测试视角审查）；无法立即验证的需求（如"数据存档保留3年"）标注例外而非强判不可测试；遗留系统作需求基线的特殊工作法见原书第5条。
