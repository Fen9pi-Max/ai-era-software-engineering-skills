# 缺陷生命周期与测试执行度量

## R（原文摘引）
> 只根据发现缺陷的数量来评价一个测试工程师的表现绝不是一个好办法。（第3章 第15条）

## I（解释）
**缺陷报告规范**：一报告一缺陷（相关的交叉引用）；属性：主标题（前缀=系统部分名）、工作版本号、OS 与配置、附件（截屏/日志入中心库）、再现性（总可/随机/不能重现）、重现步骤（含特殊数据；禁"显示不正确信息"式模糊语，须写实际与预期）、分类（缺陷/增强/变更请求）。
**六级优先级**：导致运行中断/紧急/高级/中级/低级/N/A——等级不宜过多否则失去特征；重大缺陷提交 CCB 且测试人员须参加。
**状态机**：新→评估分派（打开/关闭-重复/增强）→正在开发→修改完毕→新版本→返测→关闭-改正 或 返测失败（新循环）。规则：仅测试组有权关闭且须文档化原因；关闭不删除（保留历史与编号连续）；**缺陷重复出现须开新报告引用旧"已关闭-但相关"报告**（度量重新引入率）；修正记录须含修正描述与受影响区域（否则测试不知返测什么）。
**入口/出口标准**：入口（单元/集成通过、生成无错、过烟雾、待返测缺陷已修、源码入版本控制）；出口（全部测试过程执行完+1/2/3 级问题全部解决，或 1/2 级全解+90% 的 3 级；可带已知低优先级缺陷发货）。
**度量集（含口径）**：①测试过程执行%→细化到步骤级（25 步停在第 24 步比"整体失败"信息量大）；②缺陷持续时间=发现→改正（100 缺陷÷20/天=5 天，拖到 10-15 天威胁截止期）；③纠正→返测时长（测组响应）；④缺陷趋势（后期新发现应下降；相同代码上缺陷随版本升→修正不正确/覆盖不全/此前被阻塞）；⑤修改质量=修正后在原正常功能上新引入/重现缺陷比例；⑥缺陷密度=每需求缺陷数÷为该需求执行的测试过程数（结合优先级解读）。

## A1（原书案例）
- 缺陷工作流程全例与六级分类（第49条表）。
- "高层测试过程 vs 有效测试过程"：不止 GUI 验证添加记录，还用 SQL 验证入库、类型、重复记录行为（第15条，评估测试深度）。

## A2（情境应用）
建立/审计缺陷流程时：①按状态机核对工具配置（关闭权限、强制重现步骤与实际/预期字段、附件库）；②落地六级优先级口径与 CCB 通道；③定义入口/出口标准并写入测试计划；④搭建度量看板：执行%到步骤级、持续时间、趋势、修改质量、密度六指标，配阈值告警（如趋势不降、重现率升高即通报）。

## E（评测）
- 输入：一份缺陷记录样例 + 一段时间的缺陷数据表。
- 输出：记录质量审查意见 + 六度量计算结果与解读。
- 通过标准：六度量算术可复算；趋势/重现率异常能被指出并给出原书三归因；缺陷记录缺字段被点名。

## B（边界）
不覆盖具体工具（Jira 等）配置操作；测试人员绩效评估维度更广（原书第15条），度量仅是输入之一；发布管理的商业决策不在范围内。
