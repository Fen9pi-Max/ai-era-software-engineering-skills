# 实用单元测试（分层·先写·接入生成）

## R（原文摘引）
> 通过单元测试可以推测开发人员的实现目标……如果开发人员对需求的理解有问题，那么这种误解会在单元测试代码中有所反映。（第6章 第29条）

> 磨刀不误砍柴工，用很短的时间来更新单元测试，就能在随后的调试和查找缺陷中节省许多时间。（第6章 第30条）

## I（解释）
原书主张**实用单元测试**而非"纯粹单元测试"（为所有依赖建存根太贵、维护代价高）：
1. **不隔离底层组件**（前提：底层已有自己的单元测试），失败可定位到具体层次。层次：数据库抽象→域对象→商业处理→用户界面，每层配单元测试程序。
2. **需求映射**：一条需求跨多层时，每个受影响层都须有该需求的代表性测试（各层都有"测试废止账目"）；正常之外必测异常（30 字符限界用 31 字符测）。
3. **责任**：代码作者编写并随代码变化更新单元测试；用与被测代码相容的语言。
4. **实现前开发**（基于接口）：先定接口（函数名/输入/输出），存根返回 true 支持测试先行；接口不足在写测试时暴露并精化。需求变更三步：先改单元测试→接口加存根→更新组件本体。
5. **纳入自动生成**：每日/夜间构建中"编译+单元测试全过"才算生成成功，失败即停在失败层；统一返回值约定（0 成功/1 失败）；用单元测试框架统一加载与报告。

## A1（原书案例）
- Customer/Order/Item 域对象与 OrderProcessingBP 的层次化单元测试伪代码（第28条）。
- Order 类 Create/Delete/AddItemToOrder 接口 + return true 存根（第29条）。
- Framework.AddTest(CreateOrderTest) 单元测试框架（第30条）。

## A2（情境应用）
在现代项目落地：①按分层（repo/service/api）组织测试目录，每层测自己层的职责；②新功能先写测试（接口+最小存根），全部通过才算完成；③把单元测试接入 CI——编译失败或任一测试失败即阻断流水线；④统一测试退出码与报告格式；⑤需求变更时先改测试再改实现。

## E（评测）
- 输入：一个小型分层模块的需求与接口。
- 输出：每层代表性测试（含异常用例）+ CI 阻断配置。
- 通过标准：跨层需求在每层有测试；非法输入有用例；CI 失败可定位到层。

## B（边界）
不主张为一切依赖造 mock/stub 的纯粹隔离路线（原书明确反对）；不覆盖 TDD 细节流派之争；性能测试不在单元测试层。
