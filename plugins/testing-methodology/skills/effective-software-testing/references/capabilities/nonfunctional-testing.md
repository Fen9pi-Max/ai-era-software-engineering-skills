# 非功能测试框架（性能·并发·安全·兼容）

## R（原文摘引）
> 糟糕的性能、不兼容性、缺乏安全性、缺乏可使用性——权衡这种风险是非常重要的。（第9章 第41条）

## I（解释）
**前置原则**：非功能需求与功能需求在需求阶段一起定义；两级文档化——系统级全局规格（如浏览器兼容版本）+ 每条需求内"非功能性需求"小节（记录与全局不同者）。
**性能梯度测试**：按数据规模梯度（1/100/500/1,000/5,000/10,000/50,000/100,000 条）测性能画曲线，得"上限"（性能可接受的最大库规模）；从客户处获取实际数据规模范围建最小/中间/最大测试库；性能测试尽早开始；硬件降级外推只能是粗略估计。
**并发三模型判定与测试**：保守（加锁拒绝他人）——测锁的获得（近同时请求只应一个成功）/效用（一人编辑时所有路径的修改企图都被拒）/释放（含客户端崩溃后锁恢复）；开放（保存时检测冲突）——第一人成功、第二人须收"已被更新"；无保护——最后保存者获胜，关注数据完整性与更新错误处理。同一数据可经不同界面更新时复杂度上升，须测所有访问路径。
**安全双层**：系统级全局需求（加密存储、全传输 SSL——逐条验证含抓包）+ 每功能安全需求（登录重试次数、输入最大长度防溢出）；验证手段分级：UI→网络监视→服务器数据检查；第三方产品不得把机密写日志；紧跟安全补丁并回归。
**兼容性**：商业案例规定全部目标 OS/浏览器/硬件/共存软件；含版本升级（旧数据向下兼容、保留用户设置）；按出现频率排序配置（最高频重点测，罕见降为烟雾）；用与最终用户完全相同的安装方式；测试平台不装开发工具。

## A1（原书案例）
- 订单系统客户数据规模 1,000–100,000 的调查与三档测试库（第42条）。
- 保守锁模型下脚本发起 1,000+ 近同时编辑请求（第45条）。
- 支付服务器不得把机密信息写日志、SSL 抓包验证（第44条）。

## A2（情境应用）
规划非功能测试时：①从需求阶段挖出全局+逐条两级非功能需求清单；②性能：定数据规模梯度与三档库，画性能-规模曲线找上限；③并发：先判定系统采用的模型，按对应测试点设计（锁三测点/保存冲突/数据完整性），并枚举所有能改同一数据的入口；④安全：双层清单+验证手段分级+第三方审计点；⑤兼容：配置按用户频率排序，环境与生产保真。

## E（评测）
- 输入：系统描述（功能清单、技术栈、目标用户环境）。
- 输出：非功能需求两级清单 + 四类测试方案（性能梯度/并发用例/安全验证点/兼容矩阵）。
- 通过标准：性能方案含规模梯度与上限判据；并发用例覆盖模型全部测试点；安全点逐条可验证；兼容矩阵按频率排序。

## B（边界）
不做渗透测试实操（高风险系统原书建议外购专业服务）；可用性测试方法（专题组/观察）仅概览；性能调优本身不在范围内。
