# 回归·烟雾·自动生成流水线

## R（原文摘引）
> 烟雾测试是回归测试套件的精简版本。（第8章 第40条）

## I（解释）
**流水线**（任一步失败即中断、改正后重启）：软件生成（编译，可含单元测试）→ 烟雾测试 → 回归测试。
**烟雾测试构造**：①确定使用最频繁的高层"主要"功能（登录、增删记录、生成报告）；②为主要部分开发自动测试；③扩展验证：数据库指向正确环境、版本正确、会话可启动、所有界面菜单可访问、数据可输入编辑。通过=版本进入测试的**入口标准**；失败自动通知责任人（邮件/寻呼）。
**回归测试三问**：何时执行（每次改动/改错后）；包含什么（先高风险功能与最频繁路径）；如何优化（循环：套件通过但错误事后暴露→把发现该错误的测试及相关场景加入套件→以错误数/类型度量持续扩充）。
**回归冲击矩阵**：记录每次改动影响的模块，还须覆盖**使用改动模块数据的其他模块**（典型回归错误藏在意想不到处）；测试组据此评估覆盖是否足够并增改测试。
**前置条件**：系统稳定（功能/技术/实现不总在变化），否则自动化维护量吞没收益。回归用例须可追溯到原始需求；迭代开发中回归套件渐进开发。

## A1（原书案例）
- A 模块改动影响使用其数据的 B 模块，只测 A 漏掉回归缺陷（第39条矩阵案例）。
- 编译(+单元测试)→烟雾→回归的生成顺序与失败中断（第40、47条）。

## A2（情境应用）
搭建 CI 流水线时：①在构建后加烟雾作业（5-15 分钟内跑完主要功能+环境 sanity），设为测试环境准入门禁；②回归套件按"高风险+高频路径"优先排入夜间作业；③建立改动→影响模块的冲击矩阵模板，每次合入要求开发标注；④每出一个逃逸缺陷，把复现它的测试加入套件；⑤失败即阻断并自动通知。

## E（评测）
- 输入：应用功能清单与一次真实代码改动描述。
- 输出：烟雾用例集 + 回归选择（依据冲击矩阵）+ 流水线阶段图。
- 通过标准：烟雾覆盖全部"主要"功能且时长可作门禁；对给定改动，回归集包含数据依赖方模块，不只直接改动模块。

## B（边界）
系统剧变期应先手动回归、推迟自动化（原书明确前置条件）；性能/并发类回归见非功能测试能力；发布出口标准的整体治理见缺陷与度量能力。
