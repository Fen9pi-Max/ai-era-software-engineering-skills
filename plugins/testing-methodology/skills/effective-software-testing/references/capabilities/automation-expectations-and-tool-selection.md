# 自动化期望纠偏与工具选择

## R（原文摘引）
> 自动测试工具决不能代替指导测试工作的分析技能，也不能代替手动测试。（第7章 第33条）

> 定制的工具本身也需要测试和维护，所以从零开始制作工具可能与购买工具一样昂贵，甚至比购买还要贵。（第7章 第32条）

## I（解释）
**十项期望纠偏**：①经常需要多个工具（无一工具兼容所有环境）；②测试工作量首用反而增加（学习曲线）；③时间不会立即缩短；④自动化有自己的微型开发生命周期；⑤需要相对稳定的应用；⑥并非所有测试都该自动化（有些必须人眼）；⑦一个工具测不了所有组合；⑧总费用=购买+培训+脚本开发+维护；⑨即买即用不高效（录制脚本必须手工改造才健壮）；⑩培训须及早安放为里程碑。插入式工具风险：测试钩子可能带缺陷→发行前用干净代码回归。
**工具选择组织需求框架**：确定工具类型（听取所有涉众）→制定选择标准（全组织用时须兼容尽可能多 OS/语言/技术）→确定系统构架（中间件/DB/OS/GUI/第三方插件）→是否需要多种工具→数据管理方式支持→帮助台问题报告聚焦高频问题→测试类型→进度（时间不够学习则推迟引入）→预算（含培训与人力）。
**原型验证**：让供应商在代表关键技术的原型上演示；重点验证对第三方定制控件（日历/表格等）的识别；不能识别时决定用工作区方法还是手动。
**自制工具决策**：仅当 OS/应用不兼容或专项测试需要；实施须当正式软件开发：预定资源、管理层批准、源码入版本控制、自制工具本身也要测试（不产生误识别/漏识别）。另考虑免费/共享工具与厂商轻量版。

## A1（原书案例）
- VB/PowerBuilder 应用含第三方 grid/日历/spin 控件，记录/回放工具无法识别——原型验证暴露（第35条）。
- 只依据单项目选工具，项目结束工具即闲置（第34条反例）。

## A2（情境应用）
组织要引入自动化工具时：①先用十项纠偏清单对齐干系人期望（写入决策记录）；②跑选择框架九步产出标准清单与候选打分；③要求候选工具在自有原型/试用环境实测核心场景（含最难识别的控件与数据验证）；④对比"购买+培训+维护"与"自制"总成本；⑤输出选型建议+引入里程碑（培训前置）。

## E（评测）
- 输入：组织环境描述（技术栈、测试类型、预算、进度）。
- 输出：期望纠偏记录 + 选择标准打分表 + 原型验证结论。
- 通过标准：每项期望都有原书依据的纠偏表述；打分可复算；原型验证含失败路径处理。

## B（边界）
不做具体工具（Selenium/Playwright 等）用法教程；不替代 POC 的实际执行；ROI 多周期算账属 ROI 评估能力时引用本书成本口径。
