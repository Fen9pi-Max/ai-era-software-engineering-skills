# 自动化脚本工程五技术

## R（原文摘引）
> 测试技术是一种选择测试条件的正规方法……而不是瞎猜应该选择什么样的测试用例。（第8章 第37条）

## I（解释）
**记录/回放三大病**：硬编码数值（输入值/坐标/标题/日期戳一变即坏）、非模块化难维护、缺可重用标准。**五项修正技术**：
1. **数据驱动**：数值从电子表格/数据池/文件/数据库读取，替换硬编码（与 test-data-design 的数据外置同源）。
2. **模块化开发**：按独立任务分模块，多处调用，改一处生效。
3. **模块化 UI 导航**：导航函数独立成模块；**禁止**依赖 TAB 顺序/快捷键/x-y 坐标，优先用对象名/唯一标识（不受焦点影响）；对象信息集中存 GUI Map/对象库。
4. **可重用函数库**：按功能分文件建库（数据读写与确认、导航、逻辑、错误检查）；可利用社区现成库。
5. **版本控制**：全部脚本入库，标签分组对应软件版本。
**自制工具+适配器模式**（计算引擎/新旧系统对照）：每个被测系统配一个适配器直接对核心组件执行用例绕过 UI；结果存统一格式（如 XML）→旧系统结果为基线→比较工具按规则评差异→差异跟踪至解决。用例管理四策略：正式测试技术创建用例；**公共起点**（每次执行初始数据相同、结束后恢复初始态）；基线结果直接文件比较；差异入缺陷追踪。

## A1（原书案例）
- WinRunner 公共函数库（Array/File/String/Menu 等）作为可重用库实例（第38条）。
- 遗留系统与新系统各配适配器、同一批用例双跑、XML 结果比对（第37条）。

## A2（情境应用）
重构脆脚或新建框架时：①审查现有脚本，标出硬编码数据/坐标导航/重复逻辑三类问题；②数据迁到外部数据表（数据驱动）；③导航封装为按对象名寻址的函数并集中对象库；④抽公共函数库（导航/校验/数据读写）；⑤全部入版本控制并打版本标签；⑥对计算核心加适配器层绕过 UI。

## E（评测）
- 输入：一套存在硬编码与坐标导航的脚本样例。
- 输出：问题清单 + 重构方案（数据表/模块/对象库结构）。
- 通过标准：模拟"URL 变更/界面布局变更"只影响 1 处；数据新增场景不改脚本只加数据行。

## B（边界）
不解决"该不该自动化"（见自动化期望能力）；不指定具体工具 API；框架分层架构的完整设计另见 test-design 与脚本组织结合部。
